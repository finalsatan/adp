## 2. 两个项目的定位

**万悟 wanwu**：面向企业的一站式智能体平台。
- 能力：模型纳管、MCP 广场、联网检索、可视化工作流、RAG / GraphRAG、本体智能体、GUI 智能体、通用智能体 + Skill、多租户
- 信创：已获认证，支持鲲鹏 CPU、麒麟 / 欧拉，TiDB / OceanBase
- 依赖：MySQL、Redis、MinIO、Kafka、Elasticsearch，外加 RAG、工作流、沙箱等多个容器

**WeKnora**：以知识库为核心的 LLM 知识管理框架。
- 能力：混合检索 RAG（多模态解析、原文引用）、Agent（技能、沙箱、本机浏览器、MCP、长期记忆）、Wiki 整理
- 数据源同步：飞书、Confluence、GitLab、Notion、语雀、钉钉文档等
- 渠道：企微、飞书、钉钉、Slack、Telegram 等 IM；网页嵌入 Widget；内置 MCP Server
- 运维：多空间 RBAC、审计日志、Langfuse 链路追踪；支持 Docker Compose / Helm / Lite 单二进制（SQLite）

## 3. 代码层面对比

### 3.1 规模与工程质量

| | 万悟（主仓库 + 工作流仓库） | WeKnora |
|---|---|---|
| 后端 | 主仓库约 19 万行 Go（11 个 gRPC 微服务）；工作流仓库约 71 万行 Go | 约 63 万行 Go，单体（含大量测试） |
| Python | 约 2.5 万行，RAG 核心（`rag/rag_open_source`） | 约 1.7 万行，仅文档解析（`docreader`） |
| 前端 | **两套**：主站 Vue 2 + Element UI（约 11 万行）；工作流画布 React（Coze 前端，约 100 万行） | 一套：Vue 3 + TDesign（约 27 万行） |
| 测试文件 | **1 个** | **1423 个** |
| 活跃度 | 活跃 | 非常活跃 |

结论：WeKnora 的工程质量明显更高；万悟功能更广，但几乎没有测试，Vue 2 也已停止维护。

### 3.2 关键模块

| 模块 | 万悟 | WeKnora |
|---|---|---|
| Agent 引擎 | 基于 CloudWeGo **eino ADK**（`internal/agent-service/service/single_agent.go`、`multi_agent.go`） | **手写 ReAct 循环**（`internal/agent/engine.go`），think / act / observe 分文件；含上下文压缩、工具审批、运行中追加要求、检查点回滚、中止时用已有结果合成答案、每轮 Langfuse span |
| RAG | 独立 Python 服务，基于 ES，含 GraphRAG | 可插拔流水线（`internal/application/service/chat_pipeline/`）：查询理解、扩展、并行检索、重排、合并、FAQ、Wiki 加权；关键词 + 向量混合检索，支持 pgvector / Qdrant / Milvus / Weaviate / Doris |
| 工作流 | Coze Studio fork（基于 eino compose），加了 `wanwu-agent`、`wanwu-mcp`、`wanwu-skill`、`wanwu-gui` 等自定义节点 | 无 |
| 模型接入 | 很薄（约 1300 行），以 OpenAI 兼容和元景为主 | 30+ 厂商适配（`internal/models/providers/`） |
| 沙箱 | 单个 `wga-sandbox` 容器 | Docker / E2B / Cube 多后端，带快照、闲置回收、终端和桌面 |
| 账号权限 | 独立 iam-service，多租户和组织 | 内置 OIDC（compose 中带 Dex），多空间 RBAC |

## 4. 决策

1. **自研**，参考上述仓库的设计和实现，不直接 fork。
2. **以 WeKnora 为主要实现参考**（Agent 引擎、RAG、工程实践）；万悟和 wanwu-workflow 用来参考功能范围、eino 写法和工作流设计。
3. **使用 TypeScript 全栈开发**，不用 Go。

### 为什么 TypeScript 可行

- 前后端同一语言，接口类型和 zod 校验可共享
- AI 生态成熟：MCP 官方 SDK 就是 TS；Vercel AI SDK、LangChain.js、LangGraph.js、Mastra、E2B、Langfuse 都有 TS 版本
- 平台负载以 I/O 为主（等大模型、调工具、推流式输出），适合 Node 的异步模型
- 短板是 CPU 密集任务（PDF 解析、OCR），交给独立的 Python 服务处理

## 5. 技术栈

| 层 | 参考仓库用的 | 我们的选择 |
|---|---|---|
| 后端框架 | Gin | **NestJS**（模块化 + 依赖注入）；备选 Fastify / Hono |
| ORM | GORM | **Drizzle**（原生支持 pgvector） |
| 模型层 | eino、WK `models/providers` | **Vercel AI SDK** |
| Agent 循环 | WK `engine.go`、eino ADK | 参照 WK **手写 ReAct 循环** |
| MCP | mcp-go | **`@modelcontextprotocol/sdk`** |
| 异步任务 | asynq（WK）、Kafka（万悟） | **BullMQ**（Redis） |
| 工作流引擎 | eino compose（Coze） | 自研 DAG 执行器，或 LangGraph.js |
| 前端 | Vue 3 / React | **React + Vite + shadcn/ui**；画布用 **React Flow** |
| 工程组织 | — | pnpm workspace + Turborepo |
| 存储 | — | PostgreSQL + pgvector、Redis、MinIO |
| 文档解析 | WK `docreader`（Python） | 独立 Python 服务（docling / MinerU） |
| 沙箱 / 追踪 | WK `sandbox`、Langfuse | E2B TS SDK、Langfuse JS SDK |

### 架构原则

- **模块化单体起步**，不拆微服务；分层参考 WeKnora：Controller → Service → Repository
- 关系数据和向量都放 Postgres，起步阶段组件最少；规模上来再引入 Milvus / ES

### 项目结构

```
apps/
  server/     NestJS 后端
  web/        React 前端
  docreader/  Python 文档解析服务
packages/
  shared/     前后端共享的 zod schema 和类型
```

## 6. 分阶段计划

### 6.1 排序原则（第一性原理）

平台要同时做到三件事，且依赖顺序固定：**可信**（答得准、有出处）→ **可用**（业务人员能自己搭）→ **可管**（看得见用量和质量）。不可信则后两者没有意义。

首个场景是内部知识问答，决定成败的是**回答质量**，不是功能完整度。因此：

1. **先垂直打通，再横向拓宽**：每个阶段结束都是一个能给真人用的东西。
2. **评测集第一周就建**：没有它，任何检索改动都无法判断变好还是变坏。
3. **用量与链路记录第一天就写入**：事后补记录的成本远高于一开始就记（只存库，看板后做）。
4. **不提前抽象**：模型只支持 OpenAI 兼容协议、向量库只用 pgvector、队列只用 BullMQ。参考仓库支持二三十种，是因为它们已有大量用户。
5. **留好接缝但不填满**：`tenant_id` 强制过滤、模型调用前后的审核钩子、配置 schema 版本号、品牌从 `/api/branding` 读取。
6. **固定流程先于 ReAct**：先做"检索 → 回答"的固定流程；评测集证明固定流程答不了某类问题，再上 Agent 循环。

### 阶段 A：证明"能答准"（第 1–4 周）

**目标**：拿一个真实部门的真实文档，回答准确率达到团队认可的线。未达到之前不做别的。

| 周 | 做什么 | 交付物 |
|---|---|---|
| 1 | 与试点部门确认 **50 个真实问题 + 标准答案 + 原文位置**；搭最小工程骨架（Postgres + pgvector、单个云端模型接入、API Key 鉴权） | 评测集 v1；能跑的空项目 |
| 2 | 上传 → 解析（保留标题层级、页码）→ 切片 → 向量化 → 入库（异步任务）；检索测试页（输入问题，看命中切片和分数，不调用大模型） | 能看到"为什么答不准"的工具 |
| 3 | 混合检索 + 重排 + 带引用生成 + 检索不到时拒答；自动跑评测集出分数 | 第一个准确率数字 |
| 4 | 对着评测集失败案例迭代：切片策略、查询改写、Excel / 表格处理、提示词 | 准确率达标，或明确卡在哪 |

- **刻意不做**：多租户 UI、角色、智能体配置、工具、发布、品牌。账号只保留单管理员，表结构保留 `tenant_id`。
- **同步记录**：每次模型调用的用量、每次对话的链路（检索命中、模型输入输出、耗时）。
- **退出条件**：评测集准确率达到约定值，且每条回答都有可点击的原文引用。
- **参考**：
  - 解析：`WeKnora/docreader`、`wanwu/rag/rag_open_source/rag_core/textsplitter`
  - 检索：`WeKnora/internal/application/service/retriever`（`keywords_vector_hybrid_indexer.go`）
  - 流水线：`WeKnora/internal/application/service/chat_pipeline`
  - 模型与流式：`WeKnora/internal/models/{chat,providers}`、`WeKnora/internal/stream`

### 阶段 B：让业务人员能自己搭（第 5–8 周）

**目标**：满足 PRD 成功标准"30 分钟内从上传文档到发布一个问答智能体"。

- **知识库管理**：批量上传、版本替换、切片预览与编辑、解析失败原因
- **智能体配置**：一份 zod schema（提示词、模型、挂载知识库、检索参数）；表单编辑 + 草稿 / 发布版本 + YAML 导入导出（同一份 schema，研发人员用）
- **调试面板**：每次回答可展开链路（检索了什么、分数、提示词、Token）
- **对话界面**：流式、引用展示、点赞点踩
- **账号**：用户名密码 + JWT、空间成员、知识库级权限
- **工具**：HTTP 工具 + MCP 接入（智能体模式），证明可接公司内部系统
- **Agent 循环**：仅当评测集显示固定流程答不了某类问题时再做（手写 ReAct：think → act → observe，最大轮数、超时、取消）
- **退出条件**：找一个**没参与开发的业务同事**独立完成一次搭建，记录卡点并修掉
- **参考**：
  - 循环：`WeKnora/internal/agent/engine.go`（`executeLoop` / `runReActIteration`）、`think.go` / `act.go` / `observe.go`
  - 工具：`WeKnora/internal/agent/tools/{registry,tool,definitions,mcp_tool}.go`、`WeKnora/internal/mcp`
  - 账号：`WeKnora/internal/types/tenant*.go`、`wanwu/internal/iam-service`
  - 应用类型与配置习惯：`wanwu/internal/{assistant-service,app-service}`

### 阶段 C：内部推广与"可管"（第 9–12 周）

**目标**：从一个部门扩到多个部门，同时具备向外交付的基本条件。

- **发布**：OpenAPI + API Key、独立分享页、网页嵌入组件；IM 机器人先接**一个**（企微 / 飞书 / 钉钉，看公司实际用哪个）
- **监控**：用量看板、质量指标（点踩率、检索为空率）、未解决问题列表 → 一键加入评测集 / FAQ
- **运维**：Prometheus `/metrics`、健康检查、结构化日志
- **交付**：docker compose 一键部署、离线安装包、品牌定制（运行时生效）、数据库自动迁移
- **退出条件**：在**另一套干净环境**中，不靠开发者本人，别人按文档能完成安装并跑通
- **参考**：`WeKnora/internal/im`、`WeKnora/internal/application/service/embed_*.go`、`WeKnora/internal/tracing`、`wanwu/internal/app-service`

### 阶段 D：外部交付准备（第 3–6 个月，按客户需求拉动）

SSO / LDAP、审计日志、告警与用量上限、模板、模型备用与限流、多租户管理界面、上下文压缩、评测集对比不同版本。

**原则**：第一个外部客户明确提出要求才做，不预先做。

- **参考**：`WeKnora/internal/agent/{compaction,approval}`、`WeKnora/internal/application/service/{audit_log,evaluation}.go`

### 阶段 E：拓展能力（有证据再做）

| 能力 | 触发条件 | 参考 |
|---|---|---|
| 数据源同步（飞书、Confluence 等） | 客户反馈"上传太累、文档总过期" | `WeKnora/internal/datasource` |
| Excel 数据表问答（结构化 + SQL） | 评测集中统计类问题答不准且占比明显 | `WeKnora/internal/agent/tools/data_analysis.go` |
| 可视化工作流 | 出现固定流程 / 审批 / 分支的场景，且 ReAct 不稳定 | `wanwu-workflow/backend/domain/workflow/internal/{compose,nodes,canvas,execute}` |
| 沙箱 / Skill | 出现需要执行代码或处理文件的需求 | `WeKnora/internal/sandbox`、`WeKnora/internal/agent/skills` |
| 多智能体 | 单智能体工具太多、经常选错 | `wanwu/internal/agent-service/service/multi_agent.go` |
| 本体智能体 | 用户频繁问"某指标是多少、趋势如何"（见第 10 节） | `wanwu` 决策智能体 |

可视化工作流是整个项目中**单项最贵**的功能（wanwu-workflow 约 71 万行 Go + 约 100 万行前端），放最后，很可能只需实现很小的 DAG 子集。

### 里程碑与风险

| 时间点 | 里程碑 |
|---|---|
| 第 4 周 | 评测集准确率达标，可对试点部门做小范围试用 |
| 第 8 周 | 业务人员可自己搭建并发布智能体 |
| 第 12 周 | 多部门推广 + 具备向第一个外部客户交付的条件 |

以上周期按 **3 人团队**估算。**已确认团队为 1 人**（2026-10-10），阶段 A–C 按 1 人重排为约 22 周（5–6 个月），见 `智能体开发平台-总体技术方案.md` 第 13 节。

| 风险 | 影响 | 应对 |
|---|---|---|
| 评测集无人准备 | 阶段 A 无法起步 | 第 1 周前落实负责人；至少先用 20 条起步 |
| 试点文档质量差（扫描件多、表格多、版本混乱） | 阶段 A 工期可能翻倍 | 先抽样 20 份文档评估，决定是否提前引入 MinerU / 多模态解析 |
| 向量维度存储方案未定 | 阶段 A 第 2 周受阻 | 第 1 周内定：按维度分表，或表达式索引 |

## 8. 注意事项

- **许可证**：直接复制代码片段需保留原版权声明（MIT、Apache 2.0 都要求）；只参考设计、自己重写则不受限制
- **评测集**：从阶段 A 第 1 周起准备 50 个真实问题 + 标准答案 + 原文位置，用于判断 RAG 改动的效果
- **安全**：以私有化部署为主，通常在客户内网；仍需做好租户隔离测试、限流、上传文件安全检查、提示词注入防护
- **私有化约束**：不依赖任何外网服务（CDN、遥测、外部追踪），支持离线安装，升级时自动执行数据库迁移

## 9. 已确认的需求方向（2026-10-10）

| 问题 | 结论 |
|---|---|
| 首个落地场景 | 内部知识问答 |
| 谁来搭智能体 | 业务人员和研发人员都会用，侧重点不同（业务偏界面配置，研发偏 API / 配置即代码） |
| 多租户 | 需要，平台从一开始按多租户设计；**租户 = 公司** |
| 推广范围 | 先公司内部使用，之后**向外部公司推广** |
| 文档权限 | 问答暂不按文档权限过滤，只做知识库级别的权限 |
| 文档来源 | 零散的 Word、Excel、PPT、PDF 文件，以上传为主，数据源同步往后放 |
| 对外交付方式 | **私有化部署**为主（每个客户一套实例） |
| 模型费用 | 由客户承担（客户自己配置模型 API Key / 地址）；平台**不做**定价、账单、余额 |
| 监控 | 平台需要**详细的监控**：用量、质量、调用链路、系统运行状况 |
| License 授权 | 暂不需要 |
| 品牌定制 | 需要（Logo、系统名称等可由客户替换） |
| 合规要求 | 暂不考虑（不做内容审核、信创） |
| 模型部署 | 以云端模型 API 为主 |
| 团队规模 | **1 人**，平台用 TypeScript，解析服务用 Python |
| 画布式 Pipeline | 推迟到阶段 E；代码内部按节点组织，界面只做表单 |

仍待确认：
- 私有化部署下多租户的定位：建议保留数据模型，用于集团 / 子公司场景
- 对外后是否需要补做合规（生成式 AI 备案、内容审核）
- 最终用户在哪里提问（平台网页 / 企微 / 飞书 / 钉钉）
- 账号体系：LDAP / SSO / 企微 / 飞书

## 10. 专题：本体智能体（wanwu「决策智能体」）

> 调研日期 2026-10-10。依据：wanwu 仓库代码与手册（`configs/microservice/bff-service/static/manual/9.决策智能体`、`configs/.../wga/agents/Ontology`、`docker-compose.ontology.yaml`、`internal/bff-service/service/wga_ontology.go`）+ 一轮网络检索。业内部分多为厂商博客和分析师转述，不是独立评测，只当方向参考。

### 10.1 一句话定义

**本体智能体 = 以"业务本体（知识网络 BKN）"为认知底座的智能体。** 它面对的不是原始表和文档，而是由「对象 / 关系 / 行动 / 指标」组成的业务世界模型，在这个模型上做查询、推理和执行。

wanwu 里有两层含义：

| 层面 | 是什么 | 位置 |
|---|---|---|
| 建模者：本体智能体（`DIP Agent`，默认数字员工"本体自动构建专员"） | 帮用户创建、维护知识网络 | `wga/agents/Ontology/{config.yaml,prompt.md}` |
| 使用者：数字员工 | 绑定一个知识网络 + 技能，基于本体问数、分析、决策 | 手册 `3.数字员工` |

命名注意：release notes 写明"原本体智能体升级为决策智能体"，README 里的"本体智能体"是旧名。

### 10.2 wanwu 的实现构成

| 层 | 内容 |
|---|---|
| 数据连接 | 接 MySQL 等数据源 → 扫描生成原子视图 → 可叠加过滤去重的自定义视图（服务：`vega-data-connection`、`vega-gateway`、`vega-backend`） |
| 本体建模 | **对象类**（绑定数据视图，配主键 / 标题 / 增量键）、**逻辑属性**（由沙箱里的 Python `@tool` 实时计算）、**关系类**、**行动类**（绑定一个工具，带触发条件和影响对象）、**指标**（聚合 + 过滤 + 分组 + 时间属性，支持即时值 / 趋势 / 同环比 / 占比）、**概念分组**、**索引构建任务**（全量 / 增量 / 定时） |
| 运行时 | `bkn-backend`、`ontology-query`、`bkn-mcp`（把知识网络暴露为 MCP）、`agent-operator-integration`、`wga-sandbox-ontology` |
| 智能体 | 建模 Agent：强制先调 `bkn-creator` skill，流程 `discover → preview → confirm → execute → verify → report`，写操作必须确认，CLI 委托 `ontology-core` skill，无关请求礼貌拒绝。数字员工：角色 / 任务 / 工作流程 / 技能优先级 + 技能 + 关联一个知识网络；可嵌入第三方站点、可定时任务（邮件 / IM 推送）；通用智能体里可 `@数字员工` 注入 |

要点：
- 底表与 BKN 索引是**两层独立存储**，不会自动同步，必须靠索引构建任务（定时）刷新。
- 本体能力主要来自上游 KWeaver Core（`kweaver-ai`），wanwu 做集成；`vega-*`、`bkn-backend` 是镜像，源码不在仓库里，运行时内部机制是推断，未实证。

### 10.3 与 RAG / 通用 Agent 的区别

| 对比项 | 知识库 RAG | 通用 Agent + 工具 | 本体智能体 |
|---|---|---|---|
| 认知对象 | 文本片段 | 工具列表 | 业务对象、关系、指标、行动 |
| 擅长 | 文档问答 | 执行任务 | 结构化数据的多步推理 + 闭环行动 |
| "懂业务"来源 | 向量相似度 | prompt 描述 | 显式、可审阅的语义模型 |
| 动作约束 | 无 | 靠模型自觉 | 行动类声明了绑定对象、触发条件、参数来源 |
| 口径一致性 | 弱 | 弱 | 指标定义固定 |

### 10.4 示例：库存分析

以下为按手册流程补全的演示（表名、指标名、对话是演示用，手册只有 `inventory_event` 示例表）。

**建模**（对"本体自动构建专员"说"根据库存管理需求文档建知识网络"，每阶段确认后推进）：

| 概念 | 内容 |
|---|---|
| 对象类 | 仓库、物料、库存事件、供应商 |
| 关系类 | 物料 —存放于→ 仓库；物料 —由→ 供应商供应；库存事件 —涉及→ 物料 |
| 逻辑属性 | 物料的"预计缺货天数"：当前库存 ÷ 近 30 天出库速率，由工具实时算 |
| 指标 | "库存周转率"：口径、过滤、分组固定，支持趋势和同环比 |
| 行动类 | "发起补货"：触发条件为预计缺货天数 < 7，绑定补货工具 |

**使用**（数字员工"库存分析员"）：

> 用户：华东仓库存周转率这个月比上月怎么样？哪些物料快断货了？
> 1. 命中预定义指标"库存周转率"，用同环比模式、按仓库分组查询，口径固定，不是临场写 SQL
> 2. 对华东仓物料批量试算逻辑属性"预计缺货天数"
> 3. 沿"物料 → 供应商"关系找出供应商，判断是否集中
> 4. 给出结论，并询问是否发起补货；用户确认后才调用行动类

### 10.5 应用场景

**仓库里明确出现的：**
1. 业务数据问数与分析（指标查询，趋势 / 同环比 / 占比）
2. 周期性报告自动推送（数字员工定时任务，如每日库存日报、每周巡检汇总，推送到钉钉 / 微信 / 邮件）
3. 嵌入业务系统的问答助手（脚本嵌入第三方站点，浮窗或全屏）
4. 作为外部通用智能体的业务知识后端（经 MCP 接入 DeepSeek Harness、元景 UniClaw 等）
5. 文档到知识网络的自动建模（PRD / 业务文档 / 表结构 → 对象类、关系类）

**按同一模式推演的（仓库未写，属推断）：** 供应链与库存、设备运维与工单、运营商网络运维（站点 / 告警 / 客户影响面）、财务经营分析、客户与订单分析。适用条件：数据结构化、概念关系稳定、有明确行动出口。

**不适合：** 纯文档问答（RAG 即可）；概念口径频繁变动；既无结构化数据也无可执行动作。

### 10.6 业内进展

- **Palantir Ontology + AIP**：该范式的原型。Ontology 表示企业的"决策"而不只是数据；Agent 操作受权限控制的业务对象、触发工作流并留痕；Scenarios 提供基于 Ontology 的模拟沙箱，让 Agent 在碰生产数据前先模拟决策。wanwu 的对象 / 行动 / 指标与之对应，但目前没有"模拟沙箱"层。
- **动态本体（OaK，2026-08）**：*Toward Effective and Reliable LLM Agents via Dynamic Ontology*，在 LLM 与工具间加任务相关的本体 + 知识图谱，用 judge 反馈持续修正，在 TravelPlanner / CRMArenaPro / ToolQA 上提升可靠性；指出手工建本体依赖专家、难扩展——对应 wanwu 的"自动构建专员"。
- **KG 落地 LLM 推理**（arXiv:2502.13247）、**能力问题驱动本体构建**（CEUR-WS Vol-3841）：先有语义约束，再让模型在约束内生成。
- **Ora Lassila（2026）**：真正的 Agent 需要本体、知识图谱与规划并存，可信系统要说清依据的知识来源。

### 10.7 评估与对本平台的建议

- **本质**：不是新的模型能力，而是"语义层 + 行动层 + 受控编排"，价值在口径可治理、动作可约束。
- **代价**：建模成本高；索引与底表需定时同步，时效靠定时任务保证；自动建模质量取决于输入文档，所以必须保留每阶段人工确认。
- **安全**：该模块的 release notes 修过 RCE（callback 组无鉴权 + 沙箱执行任意命令）、任意文件读取、SSRF、未授权调用、用户名枚举。"沙箱执行 Python + 回调接口"攻击面大，借鉴需重点设计鉴权和隔离。
- **对本平台的取舍**：当前首个场景是内部知识问答，RAG 足够，本体放在阶段 E（按触发条件再做）。优先借鉴两点：① **指标口径固定化**（指标定义 + 数据视图），② **行动的声明式约束**（绑定对象、触发条件、参数来源、确认门禁）。不必照搬整套 Java 微服务。触发信号：用户开始频繁问"某指标是多少、趋势如何"。
