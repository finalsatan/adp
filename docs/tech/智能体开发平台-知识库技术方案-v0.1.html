1. 范围

本版要做：文档库、问答库、入库方案；独立的解析服务；入库流水线（转换、解析、分块、分块增强、向量化）；检索与命中测试；引用定位与原文预览；对应的部署变更。

本版不做：问答应用（M3：查询改写、多轮问题合并、问答库直接回答等），以及需求 4.1.12 列出的同义词、图片描述、知识图谱、外部数据源、文档历史版本等。MinerU 的快速、基础档随平台默认部署；MinerU 的标准、高级档和 PaddleOCR 只写对接方式（自建 GPU 服务或云端 API），不进默认部署清单。

2. 主流 RAG 产品的做法

Dify 的两项和 RAGFlow 的融合打分依据各自 GitHub 仓库的源码（2026-10-22 查看），WeKnora 依据本地 repos/WeKnora 的文档和迁移脚本；其余来自公开资料，未逐一核对源码。

设计点主流做法本方案
解析RAGFlow 自研 DeepDoc（版面、表格识别）；WeKnora 用轻量解析服务，MinerU、PaddleOCR-VL 作为可选“解析引擎”，填自建地址或云端密钥；Dify 内置提取器，可切换到 Unstructured独立解析服务；Docling 和 MinerU（CPU 上的快速、基础档）默认部署；MinerU 的标准、高级档和 PaddleOCR 接自建 GPU 服务或云端 API
分块RAGFlow 按文档类型选模板（法规、书籍、问答、表格、演示文稿、整篇等）；Dify 分“通用”和“父子”两种；WeKnora 按标题、启发式、递归自动选择，也支持父子入库方案（相当于可自定义、可跨库复用的 RAGFlow 模板），7 种分块方式 + 父子分块
一块多索引FastGPT 一条数据可有多个索引（自定义索引、自动生成的问题）；WeKnora 生成问题、摘要、表格摘要一个分块对应多条“索引条目”（分块本身、假设问题、摘要），检索后按分块去重
向量存储Dify 用 pgvector 时每个知识库一张表 embedding_{collection}，维度超过 2000 不建 HNSW 索引；WeKnora 单表（halfvec），按维度建 HNSW 部分索引；RAGFlow 用 Elasticsearch 或 InfinityPostgreSQL（ParadeDB 镜像，自带 pgvector），每个知识库一张索引表（同 Dify）；维度超过 2000 改用 halfvec，仍建 HNSW
中文全文检索Dify 用 PostgreSQL 默认的 tsvector（不切中文）或 pg_bigm 二元组索引；WeKnora 用 ParadeDB pg_search（BM25 + Lindera 中文分词器，AGPL）；RAGFlow 用 ES/Infinity + 自研分词ParadeDB pg_search：BM25 + 内置 jieba 分词器（见 K4）
混合融合Dify 向量分与关键词分加权求和（或交给重排）；RAGFlow 的 ES/OpenSearch 只负责召回，最终分 = 词项相似度 × 权重 + 向量相似度 × 权重，阈值作用于这个分数；WeKnora 加权 RRF，再按理论最大值归一化到 0–1BM25 负责召回，融合分按 RAGFlow 的方式在程序里算，分数有绝对含义，阈值能过滤不相关内容（见 K5）
任务队列Dify 用 Celery，并有“按租户隔离的等待队列”：每个租户同时只放少量任务进 Celery，做完一个再取下一个，防止一个租户的大批上传堵住别人；WeKnora 用 asynq，分多个 worker 池；RAGFlow 把大 PDF 按页段拆成多个任务并行Celery；按知识库限制同时在跑的文档数（Dify 的思路，但以数据库中的文档状态为准）
引用定位WeKnora 解析时记录每段对应的原文位置（PDF 页和区域、Word 段落、Excel 行范围）；RAGFlow 分块带页码和坐标统一用 DoclingDocument 中每个元素的页码和坐标，分块记录它来自哪些元素

3. 关键技术决策

以下决策均已于 2026-10-22 确认；K1、K2、K4 分别记为 ADR 0005、0006、0004。

编号决策理由放弃的方案
K1所有解析引擎的输出都转换成 DoclingDocument（docling-core 的文档模型），作为统一的解析结果它带标题层级、表格结构、阅读顺序、每个元素的页码和坐标；docling-core 现成提供基于它的分块器和 Markdown 导出；换引擎不影响下游各引擎各自输出 Markdown，另建一张“Markdown 区间 → 原文位置”表（WeKnora DocReader 的做法），位置映射要自己维护
K2不引入 RAG 框架（Haystack、LlamaIndex、LangChain 的管线），入库和检索流程自己编排，每一步用成熟库完成Dify、RAGFlow、WeKnora、FastGPT 的核心流程都是自己写的。我们需要逐步落库、从失败步骤继续、逐步显示进度、命中测试逐步展示、按库隔离存储，框架在这些地方帮不上忙，反而多一层抽象。真正费事的组件（解析、分块、向量索引、分词、重排）都直接用成熟库Haystack 管线（早先的开源复用调研建议过）：它的 PgvectorDocumentStore 是单表、关键词检索不支持中文，大部分组件要自定义
K3任务队列用 Celery + Redis；同一知识库同时在跑的文档数有上限，下一个跑谁由数据库中的文档状态决定Dify、Onyx 等主流产品都用 Celery；Redis 已在栈中；数据库做唯一事实来源，排队位次、重启恢复都简单arq（维护放缓）、Dramatiq / Taskiq（生态小）、以 PostgreSQL 做队列的 Procrastinate（不支持“按组限制并发数”）
K4向量和全文检索都放在 PostgreSQL，数据库镜像换成 ParadeDB 官方镜像（PostgreSQL 16，自带 pgvector 和 pg_search）。每个知识库一张索引表：向量用 pgvector 的 HNSW 索引；全文用 pg_search 的 BM25 索引，中文用它内置的 jieba 分词器（ADR 0004）不增加独立服务；真正的 BM25（词频饱和、逆文档频率）；索引更新随事务提交，新旧两代切换仍在一个事务里完成；官方镜像基于官方 postgres:16，不用自己编译；WeKnora 也用 ParadeDB。一库一表：向量维度固定，删除知识库直接删表，检索按库隔离，BM25 的词频统计也按库计算OpenSearch / Elasticsearch（多一个 Java 服务，内存占用大，还要与数据库保持同步，团队认为太重）；tsvector + 应用侧 jieba（没有 BM25）；zhparser / pg_jieba（要自己编译镜像）；ParadeDB 自带的向量索引（0.25 起的 beta 功能）；单表 + 按维度部分索引（WeKnora 做法，按库过滤时召回率会下降）
K5混合检索两路召回（pgvector 向量召回、BM25 全文召回），融合分在程序里算：向量权重 × 余弦相似度 + 全文权重 × 关键词分。关键词分 = 条目中出现的查询词的权重之和 ÷ 全部查询词的权重之和（0–1），词权重取 jieba 自带的 IDF 词典（12.2）分数有绝对含义，“分数阈值”能过滤掉不相关的内容，问答拒答依赖这一点。RAGFlow 同样如此：ES/OpenSearch 只负责召回，最终分由词项相似度和向量相似度加权，阈值作用于这个分数（已核对源码）。BM25 分数没有上限，不能直接与余弦相似度相加RRF（按名次融合）；BM25 按本次结果的最高分归一化（WeKnora、OpenSearch 自带的混合检索）：排第一的结果总接近满分，无关的问题也能“命中”，阈值失去意义
K6解析服务是独立的 HTTP 服务（FastAPI），提供异步作业接口，直接读写对象存储解析依赖重、资源占用大，要与主服务隔离（ADR 0002）；异步作业避免长时间占着连接；大文件不经接口传输做成 Celery worker（与主服务代码和 Celery 版本耦合）；直接用 docling-serve（只覆盖 Docling，格式转换和其他引擎还要另起服务）
K7格式转换放在解析服务里，用 LibreOffice + unoserver：一是给 Word、PPT 类文件生成预览 PDF；二是选 Docling、MarkItDown、内置表格解析时，把旧格式和开放文档格式（doc、rtf、odt、ppt、odp、xls、ods）转成 docx、pptx、xlsx。预览生成失败不影响入库浏览器不能直接显示 Office 文件，PPT 引用跳页也要靠预览 PDF。MinerU 能导出 PDF，但 Office 来源的 PDF 是重新排版的，页码与原文对不上，不能当预览。unoserver 让 LibreOffice 常驻，避免每次冷启动Gotenberg（只输出 PDF，不能转 docx）；用 MinerU 导出的 PDF 做预览（重新排版）；去掉 Word、PPT 的原文预览（PPT 无法跳页）
K8人工修改解析结果用 Markdown 编辑；保存时把新旧内容按段落对齐（Python difflib），对得上的段落沿用原来的页码和坐标编辑体验简单；对齐只用标准库；满足需求 4.1.8“能定位的照常定位”按元素逐块编辑（界面复杂）
K9MinerU 与 Docling 并列为默认部署的解析引擎：单独的 mineru 服务（自建 CPU 镜像），提供快速、基础两档；标准、高级档发往系统设置中配置的自建 GPU 服务或官方云端 API。Word、PPT、HTML、EPUB、OFD 由 MinerU 直接解析MinerU 4.0 原生解析 Office 等格式（由其依赖的 DocVortex 完成，MIT），旧格式不需要转换；基础档用 ONNX 在 CPU 上运行；自建服务与官方云端是同一套 V1 接口，一个适配器即可；独立容器与 Docling 的依赖互不干扰MinerU 作为可选组件（原方案）；把 MinerU 装进解析服务镜像（与 Docling 的依赖混在一起，镜像更大）；直接用 MinerU 官方 Docker 镜像（只面向 NVIDIA GPU）

代码位置：主服务新增 backend/app/kb/（api、documents、ingest、chunking、enhance、indexing、retrieval、schemes、qa、storage）；解析服务是独立项目 parser/（自己的 pyproject.toml 和镜像），按引擎分目录 parser/engines/，MinerU 适配器在 parser/engines/mineru/；mineru 镜像的 Dockerfile 放在 deploy/mineru/。

6. 解析服务

6.1 职责与接口

只做三件事：格式转换；调用各引擎把文件解析成 DoclingDocument 并导出 Markdown；抽取图片。分块、向量化、增强都在 worker 里做。

6.3 并发、资源与离线部署

  • 进程池：PARSER_WORKERS 个子进程，每个进程启动时加载一次 Docling 模型；作业排队，队列满时返回 429，worker 稍后重试。
  • mineru 服务用 --concurrency 限制同时解析的文档数，超出的在它内部排队；解析服务等待它时不占 Docling 进程。
  • 保护参数（本方案补充，用环境变量配置）：单个作业超时默认 30 分钟，单个文档最多 2000 页；超过时作业失败并写明原因。
  • 离线：Docling 的版面、表格、RapidOCR 模型默认在首次运行时联网下载，客户内网部署会失败。构建镜像时用 Docling 提供的模型下载命令预先下载，运行时通过 artifacts_path（或 DOCLING_ARTIFACTS_PATH）指向镜像内目录。MinerU 同理：构建 mineru 镜像时下载基础档模型（约 0.8GB），运行时不联网。具体命令以锁定版本的 --help 为准。
  • mineru 镜像：基于 Python 3.12 安装 mineru>=4.0,<5 的基础包（ONNX + llama.cpp，不装 PyTorch），启动 mineru-kit api-server --tier basic，用 --api-key 认证。官方 Docker 镜像只面向 NVIDIA GPU，有 GPU 时用它部署标准、高级档。
  • 资源：Docling 和 MinerU 在 CPU 上耗时和内存都不小，需要用试点文档实测后确定 PARSER_WORKERS、mineru 的并发和两个容器的配额（见 19.1）。

6.4 安全

  • 只接受来自 worker 的请求；容器不出网，只放行系统设置中配置的云端引擎地址（由部署方的网络策略或代理实现）。
  • mineru 服务只在内网，只接受解析服务的请求（API Key）。
  • 上传时用 filetype 按文件头校验真实类型；docx、xlsx、pptx、odt、ods、odp、epub 本质是压缩包，解析前检查解压后的总大小，防止压缩炸弹。
  • 容器限制 CPU 和内存；单个作业有超时。
  • HTML、mhtml、EPUB 不执行脚本、不抓取远程图片和资源，避免借文档探测内网。

7. 统一的解析结果

  • 格式：DoclingDocument 的 JSON（K1），连同导出的 Markdown 一起存入对象存储。Markdown 用于“解析结果对照”页面的展示和编辑。
  • 位置：每个文字、表格、图片元素带 prov：页码、坐标（PDF 坐标系，单位为点，原点在左下）、字符区间。Excel、CSV 的表格元素保留工作表名和原始行号。
  • 版本：原始解析结果始终保留；人工修改后另存一份“修改版”，只保留最新一份（需求 4.1.5 不要求完整历史）。表 document_parses 记录两份各自的路径、修改人和时间。
  • 保存人工修改的处理（K8）：
    1. 把编辑后的 Markdown 交给解析服务的 Markdown 引擎，转成 DoclingDocument；
    2. 把新旧两份的段落文字规范化（去空白和标点）后用 difflib.SequenceMatcher 对齐，相似度不低于 0.6 的视为同一段，沿用原来的位置；
    3. 对不上的段落没有位置，含有它们的分块在引用时按“人工修改内容”处理（需求 4.1.8）；
    4. 存为修改版，按入库方案重新分块（见 8.5）。
  • 界面上的“高亮处为人工修改”：前端用 jsdiff 比较原始与修改版的 Markdown。
  • “恢复为原始解析结果”：删除修改版，用原始结果重新分块。

8.2 调度：按知识库公平

  • 文档表就是队列的唯一事实来源。调度函数 dispatch(kb_id)：先取该知识库的事务级咨询锁（pg_advisory_xact_lock），统计正在处理的文档数，如果小于“每个知识库最多占用的解析并发”（需求 10.8 系统设置），就按入队时间用 FOR UPDATE SKIP LOCKED 取出排队中的文档，改为处理中并投递 Celery 任务。
  • 调度在三个时机触发：上传后；一个文档处理结束时（成功或失败）；beat 每 30 秒对所有有排队文档的知识库补发一次，作为兜底。
  • 效果：每个知识库在 Celery 队列里最多只有 N 个任务，Celery 按先来先处理，自然在各知识库之间轮流；大批量上传只会拖慢自己的知识库（需求 4.1.10）。这是 Dify 按租户隔离队列的思路，改为按知识库、以数据库为准。
  • 全局的“同时解析的文档数”：转换和解析两步要先拿到 Redis 中的解析并发令牌（租约方式，与模型并发限流相同）；拿不到时任务 10–30 秒后重试，不算失败。
  • 排队位次：“排队中（本库第 N 位）”按入队时间在本库排队文档中的名次计算。
  • Celery 队列：ingest（入库流水线）、maintenance（删除清理、批量操作、旧数据清理）由 worker 消费；interactive（试运行、分块或问答对编辑后的重建）由 worker-interactive 消费，不会被批量入库挤占。

8.3 失败、重试与取消

  • 从失败步骤继续：每一步的产物都已持久化，文档记录失败步骤；“重试”从该步骤继续，不重复前面已完成的步骤（例如不会重新 OCR）。
  • 临时性错误（网络、超时、5xx、云端引擎 429）自动重试 3 次，间隔指数增长；仍失败则标为失败。业务性错误立即失败，失败原因面向用户书写，例如：文件已损坏或加密、超过页数上限、第 N 个分块超长（第 X 页）、模型已停用、解析引擎未配置、解析超时。
  • 入库额度限流（技术方案 v0.1 的 9.3）：任务稍后重试，不算失败，也不计入自动重试次数。
  • worker 崩溃：Celery 用 acks_late，任务会被重新投递；beat 每分钟检查心跳超时的文档，把它们重新放回调度。
  • 取消：删除文档或发起重新解析时，文档的 run_id 换成新值；正在跑的任务在每一步开始前检查 run_id，不一致就退出，并取消解析服务上的作业。
  • 增强失败不让整个文档失败（本方案补充）：某个分块的增强调用重试后仍失败，该分块不带增强内容，文档标记“部分分块增强失败”，可单独重试。

8.4 新旧两代切换

  • 分块和索引条目都有 generation 字段；索引条目另有 active。重新入库时写入的是新一代，active = false。
  • 生效时在一个事务里：本文档旧一代的索引条目 active 置为 false、新一代置为 true，文档的 current_generation 改为新值。旧一代的分块和索引条目由 maintenance 任务异步删除。
  • 检索只看 active = true 的条目，因此“重新入库期间，旧分块在被替换前仍可被检索”（需求 4.1.5）。向量索引和 BM25 索引都随事务提交生效，不需要另外同步。
  • active 同时包含文档和分块的启用状态：启停文档或分块时更新对应条目的 active。
  • 文档处理中时，接口拒绝编辑它的解析结果和分块。

8.5 重新解析与批量操作

  • 重新解析：从步骤 1 开始，可改选方案；快照中的解析设置和分块设置都更新。
  • 仅重新分块：从步骤 3 开始，使用当前解析结果（有修改版时用修改版）；快照中的解析设置不变，只更新分块设置和分块增强（需求 4.1.5）。
  • 保存解析结果的修改、恢复原始解析结果：都走“仅重新分块”。
  • 批量重新解析、批量重试：maintenance 任务把选中的文档改为排队中，再触发调度；不一次性投递，仍受按库并发上限约束。

9. 分块实现

9.1 元素流与位置映射

  • 先用 docling-core 的 HierarchicalChunker 把 DoclingDocument 拆成“元素流”：每个段落、列表、表格、图片是一个元素，带标题路径和来源元素（含页码和坐标）。表格序列化为 Markdown 表格（docling-core 默认序列化为“行, 列 = 值”的三元组，要换成 Markdown 表格序列化器）。
  • 把元素按顺序拼成全文，同时记录每个元素在全文中的起止位置。切分器返回的每块起止位置，按这张表映射回覆盖到的元素，就得到分块的页码、坐标或元素引用。所有分块方式共用这一机制，不在各方式里各写一遍位置处理。

9.2 七种分块方式

方式实现
自动解析结果有标题元素时按标题（切到 2 级）；文件类型为 PPT 时按页；否则按长度
按标题按标题路径截到第 N 级分组；短于最小长度的组并入下一组；超长的组在元素边界上累积切分，单个元素仍超长时交给 RecursiveCharacterTextSplitter
按长度整篇文本交给 RecursiveCharacterTextSplitter：方案中的分隔符（按顺序逐级尝试）、最大长度、重叠长度，tiktoken 计长度，add_start_index 取起始位置
按规则对全文执行正则 finditer 找切分点（任一条规则匹配即切）；匹配到的文字作为分块标题；超长再按长度切

9.3 表格、父子分块、标题路径

  • 文档中的表格：整表一块；超过最大长度时按行拆分，每块带表头。
  • Excel、CSV：不使用分块方式，每 N 行一块，每块带表头；位置记录工作表和行范围。
  • 父子分块：父块按所选方式切分（最大长度、重叠长度换成父块最大长度）；在每个父块内用 RecursiveCharacterTextSplitter 按子块的分隔符、最大长度、重叠长度切出子块，起始位置同样映射回元素。只给子块建索引，命中后返回父块。分块表用 kind（parent / child）和 parent_id 表示层级。
  • 标题路径：取自元素的标题，拼成“第三章 > 3.2 差旅”，单独存一列；方案开启“附带标题路径”时作为向量化文本和全文索引的前缀。

9.4 超长检查与试运行

  • 向量化文本 = 标题路径 + 上下文说明 + 分块内容。它的 token 数超过知识库向量化模型最大输入长度的 90% 时，文档入库失败，失败原因写明是第几个分块、在第几页（需求 4.1.4）。分块后先按上下文说明的预留长度检查一次，增强后再按实际内容检查一次。
  • 上传预检（需求 4.1.3）：方案最大长度（开启父子分块时取子块最大长度）+ 标题路径预留 + 上下文说明预留，与 90% 上限比较。两项预留各取 100 tokens（本方案补充，实测后调整）。
  • 试运行：在 interactive 队列执行步骤 1–4，不写知识库的表。样例文件放在对象存储的临时目录，24 小时后由 beat 清理。语义分块和超长检查用界面上选的向量化模型。为控制费用，增强只对前 10 个分块执行（本方案补充）。结果（解析结果、分块、增强结果）存到临时目录，前端按作业 ID 轮询获取。

增强生成方式用途

-- 另有 doc_id、chunk_id 的 B-tree

  • ParadeDB 索引中带上 entry_type、doc_id、active，过滤条件可以在索引内完成。它的索引遵循 PostgreSQL 的 MVCC，随事务提交生效，与表数据始终一致。
  • 表结构升级：knowledge_bases.index_schema_version 记录每张索引表的版本；需要变更时，Alembic 迁移调用辅助函数遍历所有索引表执行。ParadeDB 索引是覆盖索引，增删字段要重建索引（REINDEX），所以字段一次定全，变更尽量少。

11.4 中文全文检索

  • 建索引：title、body、keywords 三个字段都用 ParadeDB 内置的 jieba 分词器（pdb.jieba）。它默认开启搜索模式，长词会同时拆出短词（如“长江大桥”另拆出“长江”“大桥”）。应用里不分词。
  • 召回：title ||| :q::pdb.boost(2) OR body ||| :q OR keywords ||| :q::pdb.boost(2)，加上 active 和文档过滤条件，按 pdb.score(id) 降序取前 N 条。查询串由 pg_search 用同一个分词器切分。标题和关键词加权 2 倍是初始值（本方案补充），实测后调整。
  • 查询词与权重（用于关键词分，见 12.2）：
    • 在数据库里用同一个分词器切出问题的原词：SELECT :q::pdb.jieba('search_mode=false')::text[]，再去掉停用词（停用词表随代码发布）。
    • 每个词的权重取 jieba 自带 IDF 词典中的值；词典里没有的词取词典的中位数（jieba 关键词提取的做法）。
  • 查询词的切分和权重封装在 QueryTerms 接口后面；以后做同义词（需求 4.1.12 本阶段不做）时在这里展开。
  • ParadeDB 的 jieba 分词器文档里没有自定义词典。专有名词切分不准时的退路：在应用里用 jieba（可加自定义词典）预先分词，索引字段改用按空格切分的分词器（RAGFlow 的做法）。

12. 检索实现

12.1 流程

检索是 kb/retrieval 中的一个服务函数，命中测试和以后的问答应用（M3）都调用它。

  1. 确定参与的知识库和检索配置（知识库默认值，被调用方覆盖）。知识库已停用时跳过；向量化模型已停用时返回“模型不可用”（需求 3.4）。
  2. 把元数据、文件夹（或问答库分类）条件转成文档子查询。
  3. 用各知识库的向量化模型把问题向量化（同一模型在一次请求内只调一次）。
  4. 每个知识库并行执行两路召回：向量召回（pgvector）和全文召回（ParadeDB BM25），各取召回数的 3 倍条目（同一分块可能有多条索引条目，要留出去重余量）。
  5. 条目按分块（问答库按问答对）去重，每路取该分块的最高分；对只出现在一路的候选，补算另一路的分数。
  6. 计算融合分（12.2）。父子分块：子块替换为父块，同一父块只保留一个，分数取子块最高分。
  7. 未开启重排：按融合分过阈值，取前 Top K。开启重排：对前 Top K 个候选调用重排模型（文本为标题路径 + 内容，父子分块用父块内容），保留指定条数，阈值作用于重排分数。
  8. 相邻分块扩展：按 seq 取同一文档当前一代的前后 N 块，与命中块合并成一段返回。
  9. 返回分块内容、所属文档、位置、各阶段分数和耗时。

12.2 分数与阈值

检索方式分数
向量余弦相似度（1 − 余弦距离）
全文召回时按 BM25（pdb.score）排序取候选；参与融合和阈值的是关键词分：条目文字中出现的查询词的权重之和 ÷ 全部查询词的权重之和，0–1
混合向量权重 × 向量分 + 全文权重 × 关键词分，两个权重之和为 1（与 RAGFlow 相同）
重排重排模型返回的相关度
  • 关键词分只对候选计算：查询词是否出现在条目的 title、body、keywords 中，用 SQL 的 strpos 判断。
  • 不直接用 BM25 分数参与融合：BM25 没有上限，随问题和知识库变化，不能和余弦相似度相加，也不能设固定阈值；按本次结果的最高分归一化（WeKnora、OpenSearch 自带混合检索的做法）会让第一名总接近满分，阈值失去意义（K5）。
  • 阈值的作用对象按需求 4.1.7：开启重排时作用于重排分数，否则作用于融合分（只用一路时即该路分数；只用全文时按 BM25 排序，阈值作用于关键词分）。
  • 不同向量化模型的相似度分布差别很大，默认阈值要按所接入的模型实测给出。
  • 多个使用不同向量化模型的知识库一起检索时，分数不能直接比较，要靠重排统一打分；需求 5.1.3 规定，应用所选文档库的向量化模型不同时必须开启重排才能保存。

12.3 过滤、问答库、命中测试

  • 元数据过滤：前端提交“且 / 或”可嵌套的条件树，后端按字段类型转成对 documents.metadata（jsonb）的 SQLAlchemy 表达式；文件夹过滤按物化路径前缀匹配（含下级）。停用的文档和分块通过索引条目的 active 排除。
  • 问答库：每个问答对的标准问和每个相似问各是一条索引条目；命中后按问答对去重，返回问答对和命中的那个问法。答案不参与检索（需求 4.1.6）。分类过滤按分类路径前缀匹配。
  • 命中测试：调用同一个检索函数并打开调试输出，按步骤返回向量召回、全文召回、融合、重排各自的结果、分数和耗时；可临时覆盖检索配置；模型用量来源记为“命中测试”；记录不保存。
  • 性能目标（实测后调整）：单个知识库 100 万条索引条目以内，检索本身 P95 小于 500 毫秒，不含模型调用（向量化、重排）。

方案配置存为 JSON，用 Pydantic 校验（分块方式用判别联合，不同方式只接受各自的参数）：

{

  "file_type": "pdf",

    "scan_mode": "auto",
    "preprocess": {"merge_whitespace": true, "remove_header_footer": true, "remove_links_emails": false}

19.3 测试要点

  • 解析：每种文件类型准备样例（含扫描 PDF、多级标题 Word、合并单元格 Excel、GBK 编码 TXT、doc / ppt / xls 旧格式、rtf、odt、odp、ods、EPUB、OFD、mhtml），对标题数、表格数、页数、坐标做快照测试；升级 Docling、MinerU 时重跑。
  • MinerU 适配器：用 MinerU 实际输出的 middle_json 样例做快照测试，覆盖标题级别、合并单元格表格、图片、公式、PDF 坐标换算；模拟 mineru 服务重启导致作业丢失、云端上传地址不带密钥。
  • 分块：7 种方式、父子分块、表格，对固定的 DoclingDocument 做快照测试；验证位置映射正确；超长检查报出正确的分块和页码。
  • 流水线：用模拟的解析服务和固定向量的模型，覆盖排队位次、按库并发上限、全局解析并发、限流等待不算失败、失败后从失败步骤继续、删除或重新解析时正在跑的任务退出、两代切换期间检索不中断、worker 被杀后任务恢复、预览转换失败不影响入库。
  • 检索：在 ParadeDB 镜像上跑，用固定向量的小数据集，验证三种检索方式的分数、关键词分的计算、阈值、重排、父子替换、相邻扩展、元数据“且 / 或”过滤、文件夹含下级、停用的文档和分块不被检索、问答库按问答对去重；中文召回覆盖长词拆短词（搜索模式）、标题和关键词加权。
  • 人工修改：改一段后其他段落的位置不变，改过的段落按“人工修改内容”处理；恢复原始后位置全部恢复。
  • 安全：伪造扩展名的文件被拒；解压后超限的文件被拒；HTML、mhtml、EPUB 中的脚本不执行、远程资源不被抓取；导出 Excel 的公式被转义。
  • 端到端（Playwright）：建库 → 上传 PDF → 等待完成 → 命中测试 → 点击结果打开原文并高亮。

20. 风险

  • Docling、MinerU 在 CPU 上的速度和内存：大批量扫描件入库可能很慢。对策：开工前实测；有 GPU 时启用 GPU，或用 MinerU 标准档、PaddleOCR；以后可参考 RAGFlow 把大 PDF 按页段拆成多个作业并行。
  • MinerU 4.0 刚发布，DocVortex 项目很新：Office、旧格式、EPUB、OFD 的解析质量要靠试点验证。对策：锁定版本，适配器有快照测试；Word、PPT 仍可改选 Docling、MarkItDown。
  • MinerU 许可证的标注要求：平台向第三方（如外部客户）提供在线服务时，须在界面或公开文档中标明使用了 MinerU，否则许可自动终止。本阶段暂不加开源组件声明（2026-10-22 确认），对外提供服务前要补上。
  • ParadeDB 社区版的许可证和限制：
    • AGPL-3.0：我们不修改它的代码，应用通过 SQL 访问；私有化交付时随附它的许可证和源码获取方式。对应用代码的影响以法务意见为准。客户不接受时，退回 tsvector + 应用侧 jieba（检索层接口不变），或采购企业版。
    • 只支持单机：BM25 索引不随物理复制同步到备库。做高可用时，用企业版，或切换后重建索引。
    • 0.x 版本迭代快（0.25 改了索引名称和语法）：锁定版本，升级前跑检索测试。
    • jieba 分词器没有自定义词典：退路见 11.4。
  • 每库一张表的结构升级：变更要遍历所有索引表，ParadeDB 索引增删字段还要重建。对策：索引表版本号 + 迁移辅助函数，字段一次定全。
  • RustFS 项目较新：对策：只用基础 S3 接口，可随时换成 MinIO 或客户已有的对象存储。
  • 人工修改后的定位是近似的：按段落对齐，大幅改写的段落会失去位置；已按需求 4.1.8 降级处理。
  • Docling、docling-core 迭代快：锁定版本，升级时跑解析和分块的快照测试。
  • 文档中的隐藏文字可能被用来做提示词注入：pypdfium 引擎参考 DocReader 过滤不可见文字；Docling、MinerU 是否过滤需要实测；问答提示词层面的防护在 M3 处理。
