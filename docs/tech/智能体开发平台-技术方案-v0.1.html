1. 范围

1.1 本版要做

  • 可部署的平台骨架：前端控制台、后端服务、数据库、缓存、部署脚本。
  • M8 系统管理：登录与首次改密、账号锁定、用户、组织、角色与权限、资源总览、审计日志。
  • M1 模型服务：模型管理、连通测试、停用影响检查、删除引用检查、模型体验（多模型对比、流式输出）、每次模型调用的用量记录。

1.2 本版不做

  • 知识库、应用开发、工作流、探索广场、系统观测页面、通用智能体、API Key 管理。
  • Kubernetes 部署清单、高可用部署。
  • A2UI 生成式界面（只在流式事件格式上预留，见 9.6）。

2. 已定的技术决策

编号决策理由
D1后端使用 Python（FastAPI）后续最重的模块依赖的库都是 Python：LiteLLM（模型）、Docling / MinerU（解析）、Haystack（检索管线）、LangGraph（工作流）。一门后端语言，不需要额外的跨语言服务调用。
D2LiteLLM 以 Python SDK 方式嵌入后端，不部署 LiteLLM Proxy租户、密钥、可见范围、限流由平台自己管，避免两套配置互相同步；少一个服务。
D3不单独建租户，顶级组织相当于一家公司需求只有组织树；对外交付是每家客户一套私有化部署。
D4部署先只支持 Docker Compose 单机私有化交付最简单；后端无状态，以后可以直接加副本。
D5认证使用 JWT：短期访问令牌 + 刷新令牌停用用户、修改密码不要求立即失效（需求 10.6）。
D6同一组织内一个用户可有多个角色，权限取并集需求 10.4。
D7审计日志不放在业务事务中，业务提交后单独写入审计写入不影响业务成功与否。代价见 8.2。
D8模型密钥用 AES-GCM 加密存储需求 3.3：界面和接口不返回明文。
D9模型输出使用 SSE，事件带类型，命名参照 AG-UI以后加入工具调用、A2UI 界面描述时只增加事件类型，不改传输方式。

4. 总体架构

浏览器（React + Ant Design 控制台）
  │  HTTPS，Cookie 携带 JWT
  ▼
nginx：托管前端静态文件；转发 /api/*（SSE 接口关闭缓冲）
  │
  ▼
api（FastAPI，无状态，可多副本）
  ├─ auth       登录、刷新、改密、锁定
  ├─ iam        用户、组织、角色、权限计算
  ├─ resources  统一资源登记、可见范围、授权
  ├─ audit      审计日志（业务提交后写入）
  ├─ models     模型登记、密钥加密、引用检查
  └─ gateway    模型调用：鉴权 → 限流 → LiteLLM → 记用量
        │
        ├──► PostgreSQL   全部业务数据、审计日志、用量记录
        ├──► Redis        权限缓存、限流计数
        └──► 云端模型供应商（HTTPS 出网，仅 gateway 调用）

Compose 中共 4 个容器：nginx、api、postgres、redis。数据只在 PostgreSQL 中持久化，Redis 数据丢失不影响正确性（缓存会重建，限流计数会重新开始）。

6. 数据模型

所有表主键为 bigint 自增；时间字段均为 timestamptz。下表只列关键字段。

6.1 用户、组织、角色

表关键字段说明
usersusername（唯一）、password_hash、name、email、phone、remark、status（active/disabled）、is_sys_admin、must_change_password、failed_login_count、locked_until、token_version、last_login_at、created_by、created_at只停用不删除。token_version 在停用、改密、重置密码时加 1，用于作废刷新令牌。
orgsparent_id、path、name、remark、status、created_by、created_atpath 为物化路径，如 /1/5/12/；查“某组织及下级”用 path LIKE '/1/5/%'。
rolesorg_id（为空表示全局角色）、name、remark、status、builtin每个组织创建时自动建一个 builtin=true 的“组织管理员”角色，不可删除。
role_permissionsrole_id、perm_code权限码见 7.1。
membershipsuser_id、org_id（联合唯一）、joined_at用户属于哪些组织。
membership_rolesuser_id、org_id、role_id（联合唯一）同一组织内可有多个角色。
refresh_tokensuser_id、token_hash、token_version、expires_at、revoked_at、ip、user_agent只存哈希。
settingskey、value（jsonb）密码策略、锁定阈值、令牌有效期等管理员可调参数。

6.2 资源与授权

表关键字段说明
resourcestype（model / kb / app …）、name、org_id、owner_id、visibility（private / org / platform）、status、created_at统一资源登记表。各类资源的明细表用同一个 id 关联到这里。资源总览、可见范围判断、授权都只查这张表，新模块上线自动进入资源总览。
resource_grantsresource_id、user_id、level（view / edit / grant）本版只有知识库会用；表结构对所有资源通用。
resource_refsresource_id（被引用方）、ref_resource_id（引用方）记录“应用引用了某模型”“知识库引用了某 Embedding 模型”。用于停用影响清单和删除前检查。本版没有应用和知识库，此表为空，检查逻辑照样上线。

6.3 模型与用量

表关键字段说明
modelsid（= resources.id）、model_type（chat / embedding / rerank / ocr）、litellm_model、api_base、api_key_cipher、api_key_last4、description、context_length、max_output、cap_vision、cap_tools、cap_thinking、embedding_dim、default_params（jsonb）、timeout_s、max_retries、rate_qps、rate_concurrency、last_test_at、last_test_ok、last_test_message名称、所属组织、可见范围、状态在 resources 中。模型的可见范围只允许 org / platform。
model_usageat、model_id、user_id、org_id、source（playground / app / api）、source_id、input_tokens、output_tokens、first_token_ms、total_ms、ok、error_code每次调用一条，供以后的 M5 用量统计使用。本版先建普通表，数据量上来后再按月分区。

6.4 审计日志

表关键字段说明
audit_logsat、actor_id、actor_name、org_id、action、target_type、target_id、target_desc、result（success / failure）、ip、detail（jsonb）数据库层面只给应用账号 INSERT 和 SELECT 权限，保证只增不改。actor_name、target_desc 冗余存储，对象改名后日志仍可读。

7. 权限

7.1 权限码

权限码在代码中注册（iam/permissions.py），不入库维护；角色只存勾选了哪些码。每个码标注是否可授予普通角色。

权限码含义可授予普通角色
org.manage管理下级组织、组织成员否（组织管理员内置）
user.manage创建、编辑、停用用户，重置密码否（组织管理员内置）
role.manage创建、编辑、删除组织角色否（组织管理员内置）
audit.view查看本组织审计日志否（组织管理员内置）
overview.view查看资源总览否（组织管理员内置）
model.manage添加、编辑、停用、删除本组织模型否（组织管理员内置）
model.use使用模型体验、在应用中选择模型所有登录用户默认拥有

后续模块（知识库、应用等）上线时在注册表中追加权限码，例如 kb.create、kb.edit、kb.delete。

7.2 权限计算

  1. 请求头 X-Org-Id 携带当前组织；后端校验用户是该组织成员（系统管理员除外）。
  2. 有效权限 = 用户在当前组织所有角色的权限码并集。系统管理员拥有全部权限。
  3. 组织管理员对下级组织的管理：操作对象所在组织的 path 以当前组织的 path 开头，且当前组织下有对应权限码，即允许。
  4. 结果缓存在 Redis：键为 perm:{user_id}:{org_id}:{perm_version}，有效期 10 分钟。任何角色、成员关系、权限变更都把全局计数 perm_version 加 1，旧缓存自然失效。因此权限变更立即生效，不受 JWT 有效期影响。
  5. 所有接口通过 FastAPI 依赖 require_perm("xxx") 声明所需权限，不依赖前端隐藏入口。
  6. 创建或编辑角色时，服务端校验所勾选的权限码都在操作者自己的有效权限内，且都是“可授予普通角色”的码。

7.3 资源可见性

用户能看到某资源，当且仅当满足以下任一条件：

  • 是系统管理员；
  • visibility = platform；
  • visibility = org 且资源的 org_id 等于当前组织（下级组织不继承上级组织的资源）；
  • 是资源创建人；
  • 在 resource_grants 中有授权记录。

列表查询把这些条件拼成一条 SQL 的 WHERE 子句，不在内存里过滤。资源总览：系统管理员不加条件；组织管理员限定 org_id 在本组织及下级组织内，且只读。

8. 认证与审计

8.1 登录与令牌

  • 密码用 argon2id 哈希。强度校验：至少 8 位、4 类字符中至少 3 类、不等于用户名、不在内置弱密码表中（随代码发布一份常见弱密码表，约 1 万条）。
  • 登录失败：failed_login_count 加 1，达到 5 次设置 locked_until = 当前时间 + 15 分钟；成功后清零。用户名不存在与密码错误返回相同提示。
  • 访问令牌：HS256 签名，有效期 15 分钟，载荷只有 sub（用户 id）、tv（token_version）、mcp（是否必须改密）、exp、jti。不放角色和权限。
  • 刷新令牌：随机 32 字节，库中存哈希，有效期 7 天；每次刷新签发新的并作废旧的。刷新时检查用户状态为启用且 token_version 一致，否则拒绝。
  • 停用用户、修改密码、管理员重置密码：token_version 加 1，并作废该用户全部刷新令牌。已签发的访问令牌最迟 15 分钟后失效。
  • 两个令牌都放在 Cookie 中：HttpOnly、Secure、SameSite=Strict；访问令牌路径为 /api，刷新令牌路径为 /api/v1/auth/refresh。前后端同域部署，不开放跨域。
  • 首次登录或被重置密码后，访问令牌带 mcp=true，除改密和登出接口外一律返回 403 PASSWORD_CHANGE_REQUIRED，前端据此跳转到改密页。
  • 初始系统管理员通过命令行创建：python -m app.cli create-admin --username admin，首次登录强制改密。

8.2 审计日志写入

  • 业务事务提交成功后，用独立的数据库会话写入一条审计记录；业务失败（如权限不足、校验失败）也记录一条 result=failure。
  • 写入失败不影响业务返回，记 ERROR 日志并立即重试一次。
  • 已知代价：进程恰好在业务提交后、审计写入前崩溃时，该条审计会丢失。若以后审计量大到影响接口延迟，改为写入 Redis Stream、后台批量入库。
  • 业务代码统一调用 audit.record(action, target, result, detail)，由请求上下文自动补上操作人、组织、IP。
  • 记录范围按需求 10.7；模型相关新增：添加、编辑、停用、启用、删除模型，更换模型密钥。

9. 模型服务实现

9.1 模型登记

  • 模型 ID 使用 LiteLLM 格式 供应商/模型，如 dashscope/qwen-max、openai/gpt-4o；接口地址为空时由 LiteLLM 使用供应商默认地址。
  • 组织管理员只能创建 visibility=org 的模型；只有系统管理员能创建或改为 platform。限流 QPS 与并发只对 platform 模型生效。
  • 模型类型创建后不可修改。

9.2 密钥加密

  • 主密钥来自环境变量 MASTER_KEY（32 字节，Base64）。每个模型密钥用 AES-256-GCM 加密，随机 12 字节 nonce，与密文一起存入 api_key_cipher，密文前加 1 字节版本号，便于以后轮换主密钥。
  • api_key_last4 单独存储，用于界面显示 sk-••••a3f9。
  • 所有接口的响应模型都不包含密钥字段；只有模型调用层在调用前解密，明文不写日志。
  • 主密钥丢失则已存的模型密钥全部无法解密，部署文档要求客户备份。

9.3 模型调用层

所有模型调用（体验页、以后的应用、连通测试）都走 gateway 的同一入口，按顺序执行：

  1. 鉴权：按 7.3 判断当前用户能否使用该模型；模型必须为启用状态，否则返回 MODEL_UNAVAILABLE。
  2. 限流（仅 platform 模型）：Redis 计数。QPS 用按秒的计数键；并发用计数加减，键带 60 秒过期防止进程崩溃后计数卡住。超限返回 MODEL_RATE_LIMITED。
  3. 调用：解密密钥，调用 litellm.acompletion / aembedding / arerank，传入 timeout、num_retries、api_base、api_key；流式时请求返回用量。
  4. 记录用量：调用结束（成功或失败）写一条 model_usage。

LiteLLM 的设置：关闭遥测和所有回调；设置 LITELLM_LOCAL_MODEL_COST_MAP=True，不在启动时联网拉取模型价格表，适应内网部署。

9.4 连通测试

  • 对话、OCR/视觉模型：发送一条固定的短消息，最大输出 8 token。
  • 向量化模型：向量化一个短句，并校验返回维度与登记的 embedding_dim 一致。
  • 重排模型：对两个短文本重排。
  • 结果写回 last_test_* 字段，界面显示“连通 / 失败 + 原因 + 时间”。保存前也可测试（用表单中的参数，不落库）。

9.5 停用与删除

  • 停用前接口返回 resource_refs 中引用该模型的资源清单，前端在确认弹窗中展示；确认后停用。
  • 删除时若存在引用，返回 409 RESOURCE_IN_USE 及引用清单。

9.6 流式输出（SSE）

  • 接口：POST /api/v1/models/{id}/chat，响应 text/event-stream。因为是 POST，前端用 fetch 读取流，不用浏览器自带的 EventSource。
  • 事件类型（命名参照 AG-UI）：
    • RUN_STARTED：开始，带 run_id。
    • TEXT_DELTA：文本片段。
    • REASONING_DELTA：深度思考内容片段（模型支持时）。
    • RUN_FINISHED：结束，带输入输出 token 数、首字耗时、总耗时。
    • RUN_ERROR：出错，带错误码和说明。
  • 以后的工具调用、A2UI 界面描述作为新的事件类型加入，前端遇到不认识的事件类型直接忽略，保证向前兼容。
  • 多模型对比：前端对每个模型各发一个请求，互不影响；体验页不保存对话，消息历史由前端随请求带上。
  • nginx 对该路径关闭代理缓冲（proxy_buffering off），读超时设为 300 秒。

10. 接口约定

  • 前缀 /api/v1，JSON，资源名用复数，如 /api/v1/users、/api/v1/orgs/{id}/members。
  • 分页：请求 page、page_size；响应 {"items": [...], "total": n}。
  • 错误：HTTP 状态码 + {"code": "RESOURCE_IN_USE", "message": "中文说明", "detail": {...}}。错误码在 core/errors.py 统一定义。
  • OpenAPI 文档由 FastAPI 自动生成；前端执行 pnpm gen:api 生成类型，CI 检查生成结果与提交一致。

11. 前端

  • 页面、字段、操作以 A1 原型为准；布局为左侧菜单 + 顶栏（面包屑、组织切换、用户菜单）。
  • 组织切换：当前组织存在本地并写入请求头 X-Org-Id；切换后清空 TanStack Query 缓存并重新拉取。
  • 菜单和按钮根据 GET /api/v1/me 返回的有效权限码显示或隐藏，仅用于体验，安全以后端校验为准。
  • 访问令牌过期时，请求拦截器自动调用刷新接口后重试一次；刷新失败跳转登录页。
  • 手机宽度下侧栏收起，表格在卡片内横向滚动。

12. 部署

  • 一个 deploy/docker-compose.yml 启动 nginx、api、postgres、redis；PostgreSQL 数据目录挂载到宿主机卷。
  • api 容器启动时先执行 alembic upgrade head，再启动 Uvicorn。
  • HTTPS 证书由客户提供，挂载到 nginx 容器。
  • 环境变量（deploy/.env.example 给出示例）：
    • DATABASE_URL、REDIS_URL：连接串。
    • JWT_SECRET：JWT 签名密钥，部署时随机生成。
    • MASTER_KEY：模型密钥加密主密钥，部署时随机生成，必须备份。
    • LITELLM_LOCAL_MODEL_COST_MAP=True。
  • api 容器需要能出网访问所用的云模型供应商；客户网络需要代理时通过 HTTPS_PROXY 配置。

13. 交付与验收

13.1 分两期，每期独立可用

期内容交付后可用的状态
第一期仓库骨架、部署脚本、登录与改密、用户、组织、角色与权限、资源总览（空列表也可用）、审计日志可部署、可登录的管理后台
第二期模型管理、密钥加密、连通测试、停用与删除检查、模型调用层、模型体验、用量记录可接入云模型并在线体验对比

13.2 测试要点

  • 认证：连续失败 5 次锁定、15 分钟后解锁；首次登录未改密时访问其他接口返回 403；停用后刷新令牌立即不可用；刷新令牌复用旧的被拒绝。
  • 密码：不足 8 位、类别不足、等于用户名、在弱密码表中，均被拒绝。
  • 权限：无权限码时接口返回 403；多角色时权限为并集；改角色权限后无需重新登录即生效；创建角色时授出自己没有的权限被拒绝；组织管理员能管理下级组织、不能管理平级组织。
  • 可见性：下级组织看不到上级组织的 org 级资源；组织管理员不能编辑 platform 模型。
  • 组织删除：有下级、有成员、有资源时被拒绝。
  • 密钥：所有模型相关接口的响应中都不出现明文；数据库中的密文用错误主密钥无法解密。
  • 模型调用：用 LiteLLM 的 mock_response 参数模拟成功、超时、报错，验证重试次数、RUN_ERROR 事件、用量记录；platform 模型超过 QPS 返回 MODEL_RATE_LIMITED；被引用模型删除返回 409。
  • 审计：每类关键动作各产生一条记录；应用账号执行 UPDATE / DELETE 审计表失败。
  • 端到端（Playwright）：登录 → 首次改密 → 新建用户；添加模型 → 测试连通 → 体验页两模型对比。

13.3 开发和测试需要的凭据

  • 至少一个云模型供应商的 API Key，覆盖对话、向量化、重排三种类型（如阿里云百炼 DashScope），用于连通测试和体验页的人工验收。自动化测试使用模拟响应，不需要真实密钥。

15. 风险

  • LiteLLM 依赖风险：包大、发版频繁、出过投毒事件。对策：锁版本和哈希，升级单独评审；只在 gateway 中调用，以后要替换只改这一处。
  • 令牌失效窗口：停用、改密后旧访问令牌最多还能用 15 分钟，是 D5 接受的代价。
  • 审计丢失窗口：见 8.2，是 D7 接受的代价。
  • 主密钥丢失：模型密钥全部失效，需要重新录入。部署文档必须写明备份要求。
