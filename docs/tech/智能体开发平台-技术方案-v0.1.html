1. 范围

1.1 本版要做

  • 可部署的平台骨架：前端控制台、后端服务、数据库、缓存、部署脚本。
  • M8 系统管理：登录与首次改密、账号锁定、用户、组织、固定角色与资源权限（可见范围、协作者）、资源总览、审计日志、系统设置、个人中心。
  • M1 模型服务：模型管理、连通测试、停用影响检查、删除引用检查、模型体验（多模型对比、流式输出）、每次模型调用的用量记录。

1.2 本版不做

  • 知识库、应用开发、工作流、探索广场、系统观测页面、通用智能体、API Key 管理。
  • Kubernetes 部署清单、高可用部署。
  • A2UI 生成式界面（只在流式事件格式上预留，见 9.6）。

2. 已定的技术决策

编号决策理由
D1后端使用 Python（FastAPI）后续最重的模块依赖的库都是 Python：LiteLLM（模型）、Docling / MinerU（解析），检索管线、工作流的候选库（如 Haystack、LangGraph）也都是 Python，具体选型待定。一门后端语言，不需要额外的跨语言服务调用。
D2LiteLLM 以 Python SDK 方式嵌入后端，不部署 LiteLLM Proxy组织、权限、密钥、限流由平台自己管，避免两套配置互相同步；少一个服务。
D3不单独建租户，顶级组织相当于一家公司需求只有组织树；对外交付是每家客户一套私有化部署。
D4部署先只支持 Docker Compose 单机私有化交付最简单；后端无状态，以后可以直接加副本。
D5认证使用 JWT：短期访问令牌 + 刷新令牌停用用户、修改密码不要求立即失效（需求 10.5）。
D6每个用户只属于一个组织，角色固定为四个；资源统一用可见范围加协作者控制规则简单，账号由谁管理没有歧义，避免组织管理员借“邀请进组织 + 重置密码”接管他人账号（需求 10.1、10.4，ADR 0003）。
D7审计日志不放在业务事务中，业务提交后单独写入审计写入不影响业务成功与否。代价见 8.2。
D8模型密钥用 AES-GCM 加密存储需求 3.3：界面和接口不返回明文。
D9模型输出使用 SSE，事件带类型，命名参照 AG-UI以后加入工具调用、A2UI 界面描述时只增加事件类型，不改传输方式。

3. 技术选型

层选型说明
前端TypeScript、React 18、Vite、Ant Design 5、React Router 6、TanStack Query 5原型选定 Ant Design 风格，直接用官方组件库，默认主题即与原型一致。

数据访问SQLAlchemy 2.0（异步）+ asyncpg、AlembicAlembic 管理表结构迁移。
数据库PostgreSQL 16以后知识库直接加 pgvector 扩展，不换库。
缓存Redis 7权限缓存、限流计数、登录相关计数。
模型调用LiteLLM（Python SDK）统一对话、向量化、重排调用。
安全argon2-cffi（密码哈希）、PyJWT、cryptography（AES-GCM）
依赖管理后端 uv（锁文件带哈希）；前端 pnpmLiteLLM 曾出现过发布包被投毒的事件，依赖必须锁版本、校验哈希，升级要人工审查变更。
反向代理nginx托管前端静态文件、转发 /api、终止 HTTPS。
测试pytest + httpx；Playwright后端接口测试连真实的 PostgreSQL 和 Redis；前端做关键流程的端到端测试。

4. 总体架构

浏览器（React + Ant Design 控制台）
  │  HTTPS，Cookie 携带 JWT
  ▼
nginx：托管前端静态文件；转发 /api/*（SSE 接口关闭缓冲）
  │
  ▼
api（FastAPI，无状态，可多副本）
  ├─ auth       登录、刷新、改密、锁定
  ├─ iam        用户、组织、固定角色、权限计算
  ├─ resources  统一资源登记、可见范围、协作者
  ├─ audit      审计日志（业务提交后写入）
  ├─ models     模型登记、密钥加密、引用检查
  └─ gateway    模型调用：鉴权 → 限流 → LiteLLM → 记用量
        │
        ├──► PostgreSQL   全部业务数据、审计日志、用量记录
        ├──► Redis        权限缓存、限流计数
        └──► 云端模型供应商（HTTPS 出网，仅 gateway 调用）

Compose 中共 4 个常驻容器：nginx、api、postgres、redis，另有一个执行完即退出的 migrate（见第 12 节）。数据只在 PostgreSQL 中持久化，Redis 数据丢失不影响正确性（缓存会重建，限流计数和登录失败计数会重新开始）。

6. 数据模型

所有表主键为 bigint 自增；时间字段均为 timestamptz。下表只列关键字段。

6.1 用户与组织

表关键字段说明
usersusername（唯一，存小写）、password_hash、name、email、phone、remark、status（active/disabled）、role（sys_admin / org_admin / builder / end_user）、org_id（系统管理员为空）、must_change_password、token_version、last_login_at、created_by、created_at只停用不删除。每个用户只属于一个组织、只有一个角色，角色固定为四个（需求 10.1，ADR 0003）。token_version 在停用、改密、重置密码时加 1，用于作废刷新令牌。
orgsparent_id、path、name、remark、created_by、created_at、deleted_atpath 为物化路径，如 /1/5/12/；查“某组织及下级”用 path LIKE '/1/5/%'（建 text_pattern_ops 索引）。parent_id 创建后不可修改（需求 10.3），因此 path 不会变。不做组织停用；删除前要求无下级、无用户、无资源，删除为软删除，用量记录里的组织仍能显示名称。
refresh_tokensuser_id、session_id、token_hash、token_version、expires_at、revoked_at、ip、user_agent只存哈希。session_id 标识一次登录，同一次登录轮换出来的刷新令牌共用它，用于登出和发现令牌被盗用（见 8.1）。
settingskey、value（jsonb）系统设置页的参数（需求 10.8）：密码策略、锁定阈值、令牌有效期、上传与解析参数、入库限流比例、模型地址白名单、解析引擎地址和密钥（密钥按 9.2 加密）。

6.2 资源与协作者

表关键字段说明
resourcestype（kb / scheme / app …）、name、org_id、owner_id、visibility（private / org / platform）、status、created_at统一资源登记表。各类资源的明细表用同一个 id 关联到这里。资源总览、可见范围判断、协作者都只查这张表，新模块上线自动进入资源总览。模型不属于任何组织，不登记在这里；入库方案登记在这里，但 visibility 固定为 platform（需求 4.4）。
resource_membersresource_id、user_id（联合唯一）、added_by、added_at协作者，所有资源类型通用，只有“可编辑”一档（需求 10.4）。
resource_refstarget_type（model / resource）、target_id（被引用方）、ref_resource_id（引用方）记录“应用引用了某模型”“知识库引用了某 Embedding 模型”“检索配置引用了某重排模型”“入库方案引用了某对话模型（分块增强）”“应用引用了某知识库”。用于停用影响清单、删除前检查，以及缩小可见范围、移除协作者前的检查。本版没有应用和知识库，此表为空，检查逻辑照样上线。

6.3 模型与用量

表关键字段说明
modelsname、status（enabled / disabled）、created_by、created_at、model_type（chat / embedding / rerank）、litellm_model、api_base、api_key_cipher、api_key_last4、description、context_length、max_output、cap_vision、cap_tools、cap_thinking、embedding_dim、embedding_max_input、embedding_batch_size、default_params（jsonb）、first_token_timeout_s、total_timeout_s、max_retries、rate_qps、rate_concurrency、last_test_at、last_test_ok、last_test_message、deleted_at模型单独成表，没有所属组织和可见范围，全平台可用（需求 3.3）。删除为软删除（写 deleted_at），列表和选择器不再显示，但用量记录仍能关联到模型名称。

6.4 审计日志

表关键字段说明
audit_logsat、actor_id、actor_name、actor_org_id、actor_org_name、action、target_type、target_id、target_desc、target_org_id、target_org_name、result（success / failure）、ip、detail（jsonb）数据库层面只给应用账号 INSERT 和 SELECT 权限，保证只增不改；表结构迁移用另一个有建表权限的账号执行（见第 12 节）。组织管理员能看到 actor_org_id 或 target_org_id 在其管理范围内的记录（需求 10.6），因此其他组织的协作者改了本组织的资源也能被看到。名称类字段冗余存储，对象改名、组织删除后日志仍可读。

7. 权限

7.1 角色与权限码

四个角色固定（需求 10.1）。权限码和“角色 → 权限码”的对应关系都写在代码里（iam/permissions.py），不入库。接口一律用权限码声明，以后增加自定义角色时只需加角色表，接口不用改。

权限码含义拥有的角色
settings.manage修改系统设置系统管理员
model.manage添加、编辑、停用、删除模型，更换密钥系统管理员
org.manage创建、修改、删除下级组织系统管理员；组织管理员（管理范围内）
user.manage创建用户、改资料、启用停用、重置密码、解锁、调整所属组织和角色系统管理员；组织管理员（管理范围内，另有 7.2 的限制）
audit.view查看审计日志系统管理员；组织管理员（管理范围内）
overview.view资源总览系统管理员；组织管理员（管理范围内）
resource.create创建知识库、入库方案、应用等资源系统管理员、组织管理员、搭建者
console.use进入控制台；查看模型列表、测试连通、使用模型体验系统管理员、组织管理员、搭建者

终端用户没有任何控制台权限码，只能使用发布给自己的应用（M3 定义）。

7.2 权限计算

  1. 请求上下文：从访问令牌取用户 id，查出用户的角色、状态、所属组织及其 path。结果缓存在 Redis，键为 user_ctx:{user_id}:{perm_version}，有效期 10 分钟；任何用户的角色、所属组织、状态变更都把全局计数 perm_version 加 1，旧缓存自然失效，因此变更立即生效，不受 JWT 有效期影响。请求不需要携带组织。
  2. 功能权限：所有接口通过 FastAPI 依赖 require_perm("xxx") 声明，按角色对应的权限码判断，不依赖前端隐藏入口。
  3. 管理范围：组织管理员的管理范围是 path 以自己组织 path 开头的所有组织（含本组织）。操作对象（组织、用户、资源）的所属组织在范围内才允许。
  4. 账号管理的额外限制（防止接管账号）：目标是系统管理员时拒绝；目标是组织管理员时，其所属组织必须严格在操作人组织之下（path 以操作人的 path 开头且不相等），即不能操作同级、上级组织管理员。把用户设为组织管理员时同样只允许下级组织的用户。系统管理员不受这些限制。
  5. 调整用户的所属组织：原组织和新组织都要在操作人的管理范围内。

7.3 资源权限

“创建人权限”只在创建人仍属于资源所属组织时有效（调走后失去，需求 10.2）。“范围内的组织管理员”指资源所属组织在其管理范围内。

操作满足任一条件即可
查看、引用系统管理员；visibility = platform；visibility = org 且用户所属组织的 path 以资源所属组织的 path 开头（本组织含下级）；创建人；协作者（resource_members）；范围内的组织管理员
编辑内容系统管理员；创建人；协作者；范围内的组织管理员
修改可见范围、增减协作者、停用、删除系统管理员；创建人；范围内的组织管理员

列表查询把这些条件拼成一条 SQL 的 WHERE 子句，不在内存里过滤。资源总览：系统管理员不加条件；组织管理员限定 org_id 在管理范围内，并可执行管理操作。缩小可见范围、移除协作者前，检查 resource_refs 中引用它的应用是否会因此不能再引用（具体判断等 M3 定义应用的引用规则，需求 4.13）。

8. 认证与审计

8.1 登录与令牌

  • 密码用 argon2id 哈希。强度校验：至少 8 位、4 类字符中至少 3 类、不等于用户名、不在内置弱密码表中（随代码发布一份常见弱密码表，约 1 万条）。
  • 用户名保存和比对时一律去掉首尾空格并转小写，唯一性按小写判断；登录失败计数、锁定也用小写后的用户名，改大小写不能绕过锁定。
  • 登录失败：按“用户名 + 来源 IP”计数，存 Redis 键 login_fail:{username}:{ip}，有效期 15 分钟；达到 5 次写入锁定键 login_lock:{username}:{ip}，有效期 15 分钟；登录成功清除该 IP 的计数。按用户名字符串计数，不管用户是否存在，因此不存在的用户名与存在的用户名表现一致。其他 IP 不受锁定影响，他人无法故意把账号锁住。来源 IP 只取 nginx 写入的 X-Real-IP（nginx 用 $remote_addr 覆盖），不信任客户端传来的 X-Forwarded-For，否则伪造请求头就能绕过锁定；客户在 nginx 前还有负载均衡时，用 nginx 的 real_ip 模块只信任该负载均衡的地址。
  • 提示：密码错误和用户名不存在统一返回“用户名或密码错误”，不返回剩余次数；被锁定时返回“尝试次数过多，请 15 分钟后再试”。
  • 锁定时把该 IP 加入集合 login_locked:{username}（有效期 15 分钟），用户列表据此显示“已锁定”，不用按模式扫描键。管理员解锁：删除该集合，以及集合中各 IP 对应的锁定键和计数键。
  • 访问令牌：HS256 签名，有效期 15 分钟，载荷只有 sub（用户 id）、sid（session_id）、tv（token_version）、pwc（是否必须改密）、exp、jti。不放角色和权限。
  • 刷新令牌：随机 32 字节，库中存哈希，有效期 7 天；每次刷新签发新的并作废旧的。刷新时检查用户状态为启用且 token_version 一致，否则拒绝。
  • 刷新宽限期：旧令牌作废后 30 秒内再拿它刷新，返回刚签发的那个新令牌（新令牌在 Redis 中缓存 30 秒），避免多个标签页同时刷新时互相把对方踢回登录页。超过宽限期再用旧令牌，视为令牌被盗用，作废该 session_id 下的全部刷新令牌。
  • 登出：按访问令牌中的 sid 作废这次登录的全部刷新令牌，并清除两个 Cookie。刷新令牌 Cookie 只发往刷新接口，所以登出不依赖读取它。
  • 停用用户、修改密码、管理员重置密码：token_version 加 1，并作废该用户全部刷新令牌。已签发的访问令牌最迟 15 分钟后失效。
  • 用户本人改密（包括首次登录和被重置后的强制改密）成功后，接口立即为当前会话签发新的访问令牌（pwc=false，新的 tv）和刷新令牌，当前页面不用重新登录；其他会话的刷新令牌照常作废。否则当前访问令牌仍带 pwc=true、刷新令牌又已作废，用户会被卡在 403。
  • 两个令牌都放在 Cookie 中：HttpOnly、Secure、SameSite=Strict；访问令牌路径为 /api，刷新令牌路径为 /api/v1/auth/refresh。前后端同域部署，不开放跨域。
  • 首次登录或被重置密码后，访问令牌带 pwc=true，除改密和登出接口外一律返回 403 PASSWORD_CHANGE_REQUIRED，前端据此跳转到改密页。
  • 初始系统管理员通过命令行创建：python -m app.cli create-admin --username admin，首次登录强制改密。

8.2 审计日志写入

  • 业务事务提交成功后，用独立的数据库会话写入一条审计记录。需审计的动作（范围见需求 10.6）失败时（如权限不足、校验失败）也记录一条 result=failure；不在审计范围内的接口失败只写应用日志，不进审计表。
  • 写入失败不影响业务返回，记 ERROR 日志并立即重试一次。
  • 已知代价：进程恰好在业务提交后、审计写入前崩溃时，该条审计会丢失。若以后审计量大到影响接口延迟，改为写入 Redis Stream、后台批量入库。
  • 业务代码统一调用 audit.record(action, target, result, detail)，由请求上下文自动补上操作人及其所属组织、IP；对象所属组织从 target 带出。
  • 记录范围按需求 10.6；模型相关新增：添加、编辑、停用、启用、删除模型，更换模型密钥。

9. 模型服务实现

9.1 模型登记

  • 模型 ID 使用 LiteLLM 格式 供应商/模型，如 dashscope/qwen-max、openai/gpt-4o；接口地址为空时由 LiteLLM 使用供应商默认地址。
  • 只有系统管理员能添加、编辑、停用、删除模型。限流 QPS 与并发按模型设置，留空表示不限流。
  • 接口地址校验（防 SSRF）：保存、测试和每次调用前解析域名，任一解析结果不是公网地址时拒绝，除非该地址在系统管理员配置的白名单（settings.model_host_allowlist）中。判断用 Python ipaddress：私有、本机、链路本地、保留、组播、未指定地址，以及 100.64/10 共享地址、IPv4 映射的 IPv6 地址（如 ::ffff:10.0.0.1）都算非公网。调用时不跟随重定向（各供应商客户端的默认行为要在实现时逐一确认）。
  • 已知限制：校验时和 LiteLLM 实际连接时各解析一次域名，中间解析结果可能被换成内网地址（DNS 重绑定），这一步校验防不住。因为只有系统管理员能填写接口地址，本版接受这个风险；需要更严时，让 api 容器只能经出网代理访问外部。
  • 模型类型创建后不可修改。向量化模型被知识库引用（resource_refs 中有记录）后，litellm_model 和 embedding_dim 也不可修改，接口返回 409 MODEL_FIELD_LOCKED；名称、密钥、调用设置等仍可改（需求 3.4）。

9.2 密钥加密

  • 主密钥来自环境变量 MASTER_KEY（32 字节，Base64）。每个模型密钥用 AES-256-GCM 加密，随机 12 字节 nonce，与密文一起存入 api_key_cipher，密文前加 1 字节版本号，便于以后轮换主密钥。
  • api_key_last4 单独存储，用于界面显示 sk-••••a3f9。
  • 所有接口的响应模型都不包含密钥字段；只有模型调用层在调用前解密，明文不写日志。
  • 主密钥丢失则已存的模型密钥全部无法解密，部署文档要求客户备份。

9.3 模型调用层

所有模型调用（体验页、以后的应用、连通测试）都走 gateway 的同一入口，按顺序执行：

  1. 检查：模型不按组织隔离，只检查模型为启用状态，否则返回 MODEL_UNAVAILABLE。用户直接调用（模型体验、连通测试）还要求已登录；应用问答、知识库检索、入库由调用它的应用或后台任务发起，不再检查提问人或上传人。每次调用记下来源（source、source_id），用于用量统计。
  2. 限流（模型设置了限流时）：
    • QPS：按秒的计数键。
    • 并发：每个模型一个 Redis 有序集合，成员为请求 id，分值为租约到期时间（当前时间 + 60 秒）。请求开始时先删除已到期的成员，再统计数量，未超限则加入；这三步放在一个 Lua 脚本里原子执行，否则并发请求会同时通过检查而超限（QPS 计数同样用 Lua 把 INCR 和 EXPIRE 一起执行）。流式输出期间每 20 秒续约一次；结束时删除。进程崩溃时租约最多 60 秒后自动失效，长时间的流式输出也不会被提前清掉。
    • 入库与在线分开：每个模型有两组计数，“总额度”（上限为模型的 QPS 和并发）和“入库额度”（上限为总额度乘以入库比例 settings.ingest_rate_ratio，默认 0.5）。入库请求（source=ingest）两组都要占用、都未超限才放行；在线请求只占总额度。这样入库和在线合计不超过模型限额，入库最多占一半，在线至少能用另一半。入库超限时任务等待后重试，不报错；在线请求超限返回 MODEL_RATE_LIMITED。模型未设限流时两组都不检查。
  3. 调用：解密密钥，调用 litellm.acompletion / aembedding / arerank，传入 api_base、api_key；流式时请求返回用量。超时分两段：等第一个片段用首字超时，整次调用用总超时。重试由 gateway 自己做，只在还没收到任何片段时重试，不使用 LiteLLM 的 num_retries（它无法区分流式输出是否已开始）。总超时包含重试在内：每次重试前检查剩余时间，不够一次首字超时就不再重试，直接报错。
  4. 记录用量：调用结束（成功或失败）写一条 model_usage。

LiteLLM 的设置：关闭遥测和所有回调；设置 LITELLM_LOCAL_MODEL_COST_MAP=True，不在启动时联网拉取模型价格表，适应内网部署。

9.4 连通测试

  • 对话模型：发送“你好”，最大输出 16 token；支持深度思考的模型在测试时关闭深度思考，避免思考内容占满输出上限导致返回为空。
  • 向量化模型：向量化一个短句，并校验返回维度与登记的 embedding_dim 一致。
  • 重排模型：对两个短文本重排。
  • 结果写回 last_test_* 字段，界面显示“连通 / 失败 + 原因 + 时间”。保存前也可测试（用表单中的参数，不落库）。编辑已有模型时表单中密钥为空，表示沿用库中已保存的密钥。

9.5 停用与删除

  • 停用前接口返回 resource_refs 中引用该模型的资源清单，前端在确认弹窗中展示；确认后停用。
  • 删除时若存在引用，返回 409 RESOURCE_IN_USE 及引用清单。

9.6 流式输出（SSE）

  • 接口：POST /api/v1/models/{id}/chat，响应 text/event-stream。因为是 POST，前端用 fetch 读取流，不用浏览器自带的 EventSource。
  • 事件类型（命名参照 AG-UI）：
    • RUN_STARTED：开始，带 run_id。
    • TEXT_DELTA：文本片段。
    • REASONING_DELTA：深度思考内容片段（模型支持时）。
    • RUN_FINISHED：结束，带输入输出 token 数、首字耗时、总耗时。
    • RUN_ERROR：出错，带错误码和说明。
  • 以后的工具调用、A2UI 界面描述作为新的事件类型加入，前端遇到不认识的事件类型直接忽略，保证向前兼容。
  • 多模型对比：前端对每个模型各发一个请求，互不影响；体验页不保存对话，消息历史由前端随请求带上。
  • 停止生成：前端中止 fetch；后端检测到客户端断开后取消向上游的请求，释放并发租约，照常写一条 model_usage（error_code=CANCELLED，token 数取上游已返回的用量，没有时按已输出内容估算）。
  • 心跳：后端每 15 秒发一条 SSE 注释（: ping），等待首字和重试期间也照发，避免客户网络里的代理因长时间没有数据而断开连接。前端忽略注释行。
  • nginx 对该路径关闭代理缓冲（proxy_buffering off）。nginx 的读超时按两次读之间的间隔计算，有心跳就不会触发，保持 60 秒即可；整次调用的时长由后端的总超时控制，超时后发出 RUN_ERROR。

10. 接口约定

  • 前缀 /api/v1，JSON，资源名用复数，如 /api/v1/users、/api/v1/orgs/{id}/members。
  • 分页：请求 page、page_size；响应 {"items": [...], "total": n}。
  • 错误：HTTP 状态码 + {"code": "RESOURCE_IN_USE", "message": "中文说明", "detail": {...}}。错误码在 core/errors.py 统一定义。
  • OpenAPI 文档由 FastAPI 自动生成；前端执行 pnpm gen:api 生成类型，CI 检查生成结果与提交一致。

11. 前端

  • 页面、字段、操作以 A1 原型为准；布局为左侧菜单 + 顶栏（面包屑、用户菜单；用户菜单显示所属组织，进入个人中心）。
  • 菜单和按钮根据 GET /api/v1/me 返回的角色和权限码显示或隐藏，仅用于体验，安全以后端校验为准。终端用户登录控制台时只显示“没有控制台权限”的提示页（应用入口在 M3 中定义）。
  • 访问令牌过期时，请求拦截器自动调用刷新接口后重试一次；同一标签页里多个请求同时过期时只发一次刷新请求，其他请求等它完成。刷新失败跳转登录页。多个标签页之间靠服务端的刷新宽限期（见 8.1）。
  • 平台只在 PC 端浏览器使用（包括以后发布的问答页），按 1280px 及以上宽度设计，不做手机适配。

12. 部署

  • 一个 deploy/docker-compose.yml 启动 nginx、api、postgres、redis；PostgreSQL 数据目录挂载到宿主机卷。
  • 表结构迁移由单独的 migrate 容器执行 alembic upgrade head 后退出；api 容器通过 depends_on: condition: service_completed_successfully 等它完成再启动。这样以后 api 加副本时不会多个容器同时迁移。
  • 数据库用两个账号：迁移账号（表的所有者，可建表改表）和应用账号（只有业务表的读写权限，审计表只有 INSERT、SELECT）。两个账号由 postgres 容器首次启动时的初始化脚本创建，脚本里用 ALTER DEFAULT PRIVILEGES 让迁移账号以后新建的表和序列自动授予应用账号读写；审计表在创建它的那次迁移里收回应用账号的 UPDATE、DELETE。
  • HTTPS 证书由客户提供，挂载到 nginx 容器。
  • 环境变量（deploy/.env.example 给出示例）：
    • DATABASE_URL（应用账号）、MIGRATION_DATABASE_URL（迁移账号，只给 migrate 容器）、REDIS_URL：连接串。
    • JWT_SECRET：JWT 签名密钥，部署时随机生成。
    • MASTER_KEY：模型密钥加密主密钥，部署时随机生成，必须备份。
    • LITELLM_LOCAL_MODEL_COST_MAP=True。
  • api 容器需要能出网访问所用的云模型供应商；客户网络需要代理时通过 HTTPS_PROXY 配置。

13. 交付与验收

13.1 分两期，每期独立可用

期内容交付后可用的状态
第一期仓库骨架、部署脚本、登录与改密、个人中心、用户、组织、固定角色与资源权限、资源总览（空列表也可用）、审计日志、系统设置（本期用到的密码、会话、模型调用参数）可部署、可登录的管理后台

13.2 测试要点

  • 认证：同一用户名同一 IP 连续失败 5 次锁定、15 分钟后解锁，换 IP 不受影响；改用户名大小写、伪造 X-Forwarded-For 都不能绕过锁定；管理员解锁后可立即登录；不存在的用户名与密码错误提示相同；首次登录未改密时访问其他接口返回 403，改密成功后当前页面无需重新登录即可正常访问；停用后刷新令牌立即不可用；30 秒宽限期内用旧刷新令牌拿到同一个新令牌，超过宽限期复用旧令牌被拒绝并作废该次登录的全部刷新令牌；登出后该次登录的刷新令牌不可用。
  • 密码：不足 8 位、类别不足、等于用户名、在弱密码表中，均被拒绝。
  • 权限：各角色只能调用其权限码允许的接口，其余返回 403；终端用户调用控制台接口返回 403；调整用户的角色、所属组织后无需重新登录即生效；组织管理员能管理本组织和下级组织，不能管理平级、上级组织；组织管理员对同级、上级组织管理员和系统管理员执行重置密码、停用、改资料均返回 403；组织管理员只能把下级组织的用户设为组织管理员。
  • 资源权限：可见范围为“本组织”的资源，下级组织的用户能看到，平级、上级组织的用户看不到；协作者能查看和编辑，不能改可见范围、增减协作者或删除；创建人调到其他组织后失去创建人权限；组织管理员能管理范围内的全部资源；非系统管理员调用模型的添加、编辑、停用、删除接口返回 403；搭建者能在体验页选用所有已启用模型。
  • 组织删除：有下级、有用户、有资源时被拒绝。
  • 密钥：所有模型相关接口的响应中都不出现明文；数据库中的密文用错误主密钥无法解密。
  • 模型调用：用 LiteLLM 的 mock_response 参数模拟成功、超时、报错，验证重试次数（已输出片段后不重试）、RUN_ERROR 事件、用量记录；设置了限流的模型超过 QPS 或并发返回 MODEL_RATE_LIMITED；超过 60 秒的流式输出期间并发计数不丢失；入库请求不超过入库比例，入库和在线合计不超过模型限额；并发压测下并发数不超过上限；中途停止生成记录 CANCELLED；被引用模型删除返回 409；被知识库引用的向量化模型修改模型 ID 或维度返回 409。
  • 接口地址：指向内网、本机地址的模型保存和测试被拒绝；加入白名单后可用。
  • 审计：每类关键动作各产生一条记录；其他组织的协作者修改本组织的资源，本组织的组织管理员能在审计中看到；应用账号执行 UPDATE / DELETE 审计表失败。
  • 端到端（Playwright）：登录 → 首次改密 → 新建用户；添加模型 → 测试连通 → 体验页两模型对比。

13.3 开发和测试需要的凭据

  • 至少一个云模型供应商的 API Key，覆盖对话、向量化、重排三种类型（如阿里云百炼 DashScope），用于连通测试和体验页的人工验收。自动化测试使用模拟响应，不需要真实密钥。

15. 风险

  • LiteLLM 依赖风险：包大、发版频繁、出过投毒事件。对策：锁版本和哈希，升级单独评审；只在 gateway 中调用，以后要替换只改这一处。
  • 令牌失效窗口：停用、改密后旧访问令牌最多还能用 15 分钟，是 D5 接受的代价。
  • 审计丢失窗口：见 8.2，是 D7 接受的代价。
  • 主密钥丢失：模型密钥全部失效，需要重新录入。部署文档必须写明备份要求。
  • 知识库的检索仍放在 PostgreSQL（第 3 节“不换库”的前提），有两处需要在知识库技术方案中解决：
    • 中文全文检索：PostgreSQL 自带的全文检索不切中文词，需要 zhparser、pg_jieba 或 BM25 类扩展（如 pg_search），要评估扩展的维护情况和镜像构建。
    • 向量维度：pgvector 的 HNSW 索引要求列的维度固定，而不同知识库可以选维度不同的向量化模型。需要按维度分表，或按知识库建部分索引。
    如果两处都无法在 PostgreSQL 内满意解决，再考虑引入独立的检索引擎，届时需要新的决策记录。
