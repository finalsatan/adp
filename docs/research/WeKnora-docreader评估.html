WeKnora DocReader 能否直接复用

2026-10-20 · 依据本地 repos/WeKnora v0.8.2 源码（docreader/、internal/infrastructure/docparser、docker/Dockerfile.docreader）；依赖许可证查自 PyPI

只读了代码，没有实际运行。结论里的解析质量判断来自代码实现方式，需要用试点文档实测确认。

1. 结论

  • 能独立运行，但它只是“文件转 Markdown”的薄层，WeKnora 解析能力里最有价值的部分不在它里面。MinerU、PaddleOCR-VL 的对接，扫描页的 OCR/VLM，图片存储，HTML 表格规整，以及全部分块逻辑，都在 WeKnora 的 Go 主服务里（internal/infrastructure/docparser、internal/infrastructure/chunker），没法单独拿来用。
  • 对我们最重要的复杂 PDF 场景，它自己处理不好。内置引擎用 pdfium 抽取原生 PDF 的文字层，不识别表格和标题层级；扫描页只会渲染成图片交回调用方，自己不做 OCR。想要版面分析，得切到 OpenDataLoader 引擎（需要 Java 17），或者由调用方另接 MinerU。
  • 建议：不把 DocReader 当作我们的解析服务，而是参考它的代码自建。主解析器按开源复用调研的选型用 Docling，再加上 MinerU、PaddleOCR；DocReader 中设计得好的部分（见第 4 节）可以按 MIT 许可直接借用代码。在这之前，先用它的现成镜像和 Docling 在试点文档上做一次对比实测，用实测结果来验证这个结论。

2. 它是什么

项目情况
形态独立的 Python gRPC 服务，约 9300 行，有官方镜像 wechatopenai/weknora-docreader，无状态
接口Read（一次性返回）、ReadStream（先返回 Markdown，再逐张返回图片，适合几百页的扫描件）、ListEngines。输入文件字节或 URL，加上解析引擎选择
输出Markdown 正文 + 图片列表 + 元数据 + SourceBlock（Markdown 字符区间 → 原文位置：PDF 页和区域、Word 第 N 段、PPT 第 N 页、Excel 行范围）
解析引擎内置：docx 先用 MarkItDown，失败再用自研解析；pdf 用 pdfium 按页判断是否为扫描页；xlsx/xls 用 pandas，处理表头；另支持 epub、html、mhtml、xmind、图片。MarkItDown：Office、PDF、CSV。OpenDataLoader：PDF 版面分析，需要 Java
不负责的事OCR/VLM、MinerU 调用、分块、图片持久化（都在 Go 主服务里）
安全默认无认证、无 TLS，只供内网的主服务调用；可以开 TLS/mTLS 和 Token；URL 模式有 SSRF 防护
运行依赖镜像里装了 LibreOffice（转换 doc/ppt）、OpenJDK 17（OpenDataLoader）、Playwright（网页抓取），体积和内存占用都偏大；pdfium 不是线程安全的，PDF 解析是全局串行，默认并发也很低

4. 值得借用的设计和代码

  • SourceBlock 原文定位：解析时就记录每段 Markdown 对应原文的位置，分块后自动带上，用来实现“引用定位到原文”（v0.2 的 P0 需求）。docreader/parser/source_locator.py、proto/docreader.proto
  • PDF 按页判断是否扫描：根据图片面积占比判断，混合 PDF 也能逐页处理。原生页抽文字，扫描页交给 OCR/VLM。docreader/parser/pdf_parser.py
  • 流式返回图片：解决大扫描件超过 gRPC 消息大小上限的问题。
  • 解析链：一个格式按顺序尝试多个解析器，前一个失败就用下一个。chain_parser.py
  • Excel 表头规整和损坏 xlsx 修复：excel_parser.py、xlsx_repair.py
  • 引擎注册表：按“引擎 × 文件类型”注册，可以查询哪些引擎可用、为什么不可用。这正好对应我们“按文件类型配置解析方案”的需求。
  • Go 侧的 chunker（标题层级、启发式、自适应策略）可以参考思路；如果我们用 Python，需要重写。

5. 方案对比

方案优点缺点
A. 直接部署 DocReader 镜像零开发，马上可用；Office/HTML 的解析和原文定位现成复杂 PDF、扫描件、OCR、MinerU 对接还得自己做；接口跟着 WeKnora 版本变；镜像重；要去掉 AGPL 的 epub 依赖
B. Fork DocReader 自己维护起点高，原文定位、扫描页判断现成架构是“薄解析层 + 主服务做重活”，和我们想要的“解析服务一站式输出结构化文档”不一致，改动量不小
C. 自建解析服务（推荐）以 Docling 为主解析器（直接输出带标题层级和表格的文档树），MinerU/PaddleOCR 处理复杂版式和扫描件；按需借用 DocReader 的代码需要开发；解析效果要靠实测选型
