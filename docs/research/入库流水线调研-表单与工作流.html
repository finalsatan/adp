入库流水线调研：表单还是工作流

2026-10-22 · 讨论“入库方案是否改成工作流”时的参考材料，不改变需求文档 v0.3 的已定内容

依据：Dify、RAGFlow、Unstructured 的官方文档和博客（链接见第 6 节），本地 repos/WeKnora、repos/wanwu、repos/haystack。各产品版本迭代快，未注明的细节以官方最新文档为准；文档没有写明的行为标为“未说明”，没有替它们补。

1. 结论

  • 画布式入库已经是一个方向：Dify 1.9.0 推出 Knowledge Pipeline，RAGFlow 0.21.0 推出 Ingestion Pipeline，Unstructured 平台也有工作流编辑器。RAGFlow 明说动机就是“十几种固定分块模板应付不了生产中千差万别的文档”，和我们的担心相同。
  • 但它们的画布都是“固定骨架 + 可插节点”：都离不开 来源 → 解析 → （增强）→ 分块 → （增强）→ 索引 这条主线。灵活性主要来自三处：每种文件选不同解析器、在主线中间插 LLM / 代码节点、按条件分支。没有哪家让用户从零发明流程。
  • 画布带来新问题：节点顺序接错（RAGFlow 的标题分块必须在按长度分块之后；Unstructured 的分块必须在所有增强之后）、变量连线让人困惑、发布后分块结构不能改、改流水线后旧文档要不要重跑说得不清。大多数用户仍然从模板开始。
  • 对“千奇百怪的文档”，最难的部分是解析质量（扫描件、复杂表格、版面），这取决于解析引擎，画布本身不解决。画布真正多出来的能力是：插自定义清洗、用 LLM 抽取元数据、按内容分支、多数据源。
  • 建议：不整体改成画布；在现有入库方案的固定骨架上开放自定义步骤（插在“解析之后”和“分块之后”两个位置），覆盖画布能带来的大部分灵活性，同时保住解析结果编辑、仅重新分块、分块修订历史、引用定位这些依赖固定步骤的功能。数据按“有序步骤”存，以后要上画布只是换展示方式。详见第 4、5 节。

2. 各方案对比

方案形态可用的步骤 / 节点与知识库的关系改配置后旧文档备注
Dify
Knowledge Pipeline		画布，复用 Dify 工作流引擎 数据源（文件、网盘、在线文档、网页抓取，插件化）；解析（Dify Extractor、Unstructured 等插件，可按文件类型并行用多个解析器）；分块（通用、父子、问答三种）；知识库节点（定分块结构、索引方式、检索设置）；可嵌入 If-else、代码、LLM 节点；上传时可让用户填参数（文本、下拉、文件等 7 种） 用流水线创建知识库；必须先发布流水线才能上传文件。文档未明确说一个知识库能否挂多条流水线 未说明 “分块结构保存发布后不能修改”；试运行一次只能传一个文件；有逐节点调试和变量查看；内置 7 个模板（通用、长文档父子、表格问答、复杂 PDF、LLM 增强、转 Markdown、LLM 生成问答）；支持 DSL 导入导出；旧知识库可一键迁移
RAGFlow
Ingestion Pipeline		画布，基于其 Agent 框架 解析器（按 8 类文件分别配置，PDF 可选 DeepDoc / MinerU / 纯文本，图片可选 OCR / VLM，音视频要模型）；分块器（按 Token、按标题两种）；Transformer（LLM 生成摘要、关键词、问题、自定义元数据，可放在解析后或分块后，可串联）；Indexer（全文 / 向量 / 混合，可选匹配哪个字段） 每个知识库一条默认流水线，可随时更换；单个文件可另选解析方式 未说明 官方点名的坑：按标题分块必须放在按 Token 分块之后，否则部分文件格式报错；Transformer 的输入不取决于连线，而取决于提示词里引用的变量，串联时容易搞错。每个文件有逐节点的运行日志
Unstructured
平台工作流		线性节点编辑器 + API 来源 → 解析（Partitioner）→ 增强（图片摘要、表格转换、实体识别）→ 分块 → 向量化 → 目的地 工作流独立于存储，输出到外部向量库 改配置不会自动重跑，需在下次运行时勾选“全部重新处理” 分块节点必须放在所有增强节点之后；部分增强只在特定解析策略下生效；提供“自动”（默认参数）和“自定义”两种模式
LlamaIndex / Haystack代码级流水线 LlamaIndex：一串转换步骤（分块、抽标题、向量化…），带缓存。Haystack：组件组成有向图，有按文件类型、按元数据、按条件的路由器（FileTypeRouter、MetadataRouter、ConditionalRouter） 由开发者自己组织 由开发者自己处理 面向开发者，适合作为我们后端实现自定义步骤的积木，不适合直接给维护者用
WeKnora、万悟表单 WeKnora 后台是写死的流水线：解析 → 提取图片 → 分块 → 写库 → 向量化 → 富化（摘要、问题、图谱、Wiki），用户只在表单里调参数 按知识库配置 需重新解析 WeKnora 最近的改动集中在流水线分阶段的任务池、按模型限并发、卡住任务恢复，说明“跑得稳”比“能编排”更费工夫
华为云 AgentArts
（界面与扣子相近）		表单 自动分段、按长度分段、按层级分段 按知识库配置 修改分段策略后自动重新切分，人工编辑过的切片会失效 国内托管平台大多仍是表单

3. 几点观察

3.1 画布产品也有固定的“契约节点”

Dify 的知识库节点固定分块结构（通用 / 父子 / 问答），发布后不能改；RAGFlow 的 Indexer 必须是最后一步，并且沿用知识库创建时的向量化模型。也就是说，“最后产出什么样的分块”在画布里也是固定的，可变的是中间怎么加工。这和我们“解析结果 → 分块”两个固定产物的设计并不冲突。

3.2 文件类型的路由放在哪里

RAGFlow 在一条流水线里按文件类别分别配置解析器；Dify 可以并行用多个解析器；Haystack 用 FileTypeRouter。我们现在的做法（ADR 0001）是一个入库方案只针对一种文件类型，上传时按类型分组各选一个方案。两种做法都能覆盖“同类文件不同处理”，我们的做法对维护者更直观，暂时不需要改。

3.3 画布产品没有回答的问题

Dify、RAGFlow 的文档都没有说明：改了流水线后已入库的文档怎么办、人工编辑过的分块在重跑时怎么处理。这正是我们需求 4.5（解析结果编辑、仅重新分块、分块修订历史）已经定下来的部分。如果改成自由画布，需要先回答“哪个节点的输出算解析结果、从哪个节点开始重跑”。

3.4 灵活性的真实来源

文档上的“奇怪”靠什么解决我们现在能否覆盖
扫描件、复杂版面、表格、公式解析引擎（MinerU、OCR、视觉模型）能：入库方案选引擎
结构特殊（条款、附件、自定义编号）分块规则能：按规则（正则）、按标题、按页
页眉页脚、水印、噪声、固定格式的废话清洗：规则或代码部分：只有几条内置预处理规则
需要从正文抽字段（编号、生效日期、部门）做过滤LLM 或代码抽取元数据不能：元数据只能人工设
同一批文件里不同内容要走不同处理条件分支部分：按文件类型分组选方案，同类型内不能按内容分
内容要先改写（如口语化 FAQ、表格转问答）LLM 改写部分：分块增强只能追加内容，不能改写正文
来自网盘、Confluence 等外部来源数据源节点不能：本阶段不做（需求 4.12）

缺口集中在清洗、元数据抽取、改写三类，加上少量按内容分支。这些都可以作为固定骨架上的“自定义步骤”补上，不需要整条流程自由编排。

4. 三种做法

做法灵活性对已定需求的影响工作量与风险
A. 保持表单低：只能选引擎、调参数无最小；遇到表单表达不了的文档只能线下预处理
B. 表单 + 自定义步骤（建议）中高：在两个固定位置插任意多步清洗、抽取、改写；分支用多个方案解决小：解析结果、分块两个产物和它们的编辑、重跑规则都不变中：要做步骤执行器、试运行展示每步输出；代码步骤需要沙箱（可与 M2 Skills 的沙箱共用）
C. 全画布（同 Dify / RAGFlow）高：任意节点、任意分支、多数据源大：需求 4.4、4.5 要重写；方案与文件类型、上传批次的关系（ADR 0001）要重新设计大：依赖 M3 工作流引擎先完成；批量入库（排队、限流、重试、断点）和交互式工作流的执行模型差别大；维护者上手难

5. 做法 B 的草图（未定，供讨论）

解析（选引擎） ─► [解析后步骤 0..n] ─► 解析结果 ─► 分块（选分块方式） ─► [分块后步骤 0..n] ─► 分块 ─► 向量化
                     ▲ 输入输出：Markdown 全文                               ▲ 输入输出：分块列表 + 元数据
  • 步骤类型：内置清洗规则（现有的预处理开关并入这里）、LLM 处理（写提示词，改写或抽取）、代码（受限的 Python，在沙箱里运行）、调用外部接口。可选：调用 M3 发布的工作流（M3 做完后再开放）。
  • 两个插入位置，输入输出固定：解析后步骤只能接收和返回 Markdown 全文；分块后步骤只能接收和返回分块列表（可改内容、加元数据、删分块、拆分块）。这样“解析结果”“分块”的含义不变，人工编辑、仅重新分块、修订历史照旧。现有的分块增强可以看成分块后步骤的内置特例。
  • 元数据抽取：分块后步骤（或文档级步骤）可以把抽取结果写入知识库定义的元数据字段，补上“只能人工设元数据”的缺口。
  • 分支：先不做步骤内的条件分支，仍靠“按类型分组、每组选方案”；确有需要再加“满足条件才执行本步骤”的开关。
  • 试运行：沿用方案页的试运行，按步骤展示每一步的输出（参照 Dify 的变量查看、RAGFlow 的逐节点日志）。
  • 存储：方案保存为有序步骤列表（JSON），文档快照照常保存。以后如果要上画布，可以把同一份数据画成只读或可编辑的流程图。

6. 待讨论

  • 是否采用做法 B；如果采用，是现在写进需求 v0.3，还是等 M3 工作流定了再写。
  • 首批开放哪些步骤类型：代码步骤需要沙箱，安全和运维成本最高；只开放 LLM 处理和内置规则也能覆盖不少场景。
  • 手头是否有几份真实的“奇怪文档”，用它们检验 B 能否覆盖；覆盖不了的再考虑画布。
