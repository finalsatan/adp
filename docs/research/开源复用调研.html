开源复用调研

2026-10-20 · 许可证、Star 数、最近提交时间均于当日通过 GitHub API 核实

结论：平台大约 60% 的“轮子”可以直接以依赖或独立服务的形式复用，覆盖文档解析、检索管线、工作流引擎与画布、观测追踪、模型网关、沙箱、MCP、认证鉴权、对话前端。需要自研的集中在平台骨架（多租户资源模型、统一资源引用）、知识库与问答的配置编排、工作流 DSL 与节点、中文处理和全部业务界面。Dify、FastGPT、Open WebUI、LobeChat、Phoenix、New API 的许可证带附加限制，只读设计，不复用代码。

1. 判定标准

分类条件使用方式
直接复用宽松许可证（MIT、Apache-2.0、BSD、PostgreSQL），近 3 个月有提交，能作为库或独立服务接入，不需要 fork作为依赖锁版本引入，或作为独立服务部署
参考许可证宽松但和自身系统耦合太深，或者许可证有附加条款读源码借鉴设计；宽松许可证的项目可以按需摘抄代码并保留版权声明
不建议AGPL、商业限制、模型权重限制、已归档或长期无人维护不引入、不复制代码

前提：平台多租户、私有化部署，未来可能推广到外部公司。按这个前提，“禁止多租户运营”“禁止去品牌”“衍生作品需授权”这类条款都算风险。

3. 必须自研的部分

这些是平台的核心价值，没有现成的可用实现，或者现成的实现和多租户、本平台的资源模型耦合太深。

自研项原因站在谁的肩膀上
平台骨架：租户、资源模型、统一资源引用、API Key、审计所有模块的共同底座，外部项目都有自己的一套，无法拼接Casdoor + Casbin 负责认证和鉴权判定，资源模型自己设计
知识库配置与入库编排“每个知识库一套解析、分块、检索方案”是差异化核心Haystack Pipeline + Docling/MinerU/PaddleOCR
中文处理组件：分句、分块、标题路径、Word 自动编号还原现有开源库对中文支持弱（已验证 Haystack 分句不支持中文）Haystack 自定义组件；规则参考万悟的 chinese_text_splitter
知识问答应用：检索策略配置、引用溯源、调试回放产品形态需要贴合本平台Haystack + Langfuse 追踪 + assistant-ui
工作流 DSL、编译器、节点库DSL 是用户资产，必须平台自有FlowGram 画布 + LangGraph 引擎；节点设计参考 Dify 和 Coze
评测中心：评测集管理、策略对比要和知识库、问答配置联动DeepEval / Haystack 评测指标 + Langfuse 数据集
所有业务界面—Ant Design Pro / Refine + FlowGram + assistant-ui

4. 需要注意的风险

  • 依赖数量多：Langfuse 需要 ClickHouse、Redis 和对象存储；再加上 PostgreSQL、OpenSearch、Celery、模型服务，私有化部署的组件会有 10 个以上。首版建议只引入 PostgreSQL（含 pgvector）、Redis、对象存储、Langfuse，OpenSearch 等到 BM25 有必要时再加。
  • 带附加条款的项目：MinerU、LiteLLM、Langfuse 都是“宽松许可证 + 商业部分隔离”的模式，只要不使用 enterprise/ 或 ee/ 目录下的功能就没有问题。在 CI 中加一道许可证扫描。
  • 新项目：OpenSandbox（2026-03 开源）、FlowGram 仍在快速迭代，版本要锁定，并留出替换的接口层。
  • 维护放缓：One API、Ragas、jieba 近期提交少，只依赖它们稳定的部分。
