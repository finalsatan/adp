### 2. 端到端用例 `frontend/e2e/tests/phase4.e2e.ts`

按应用技术方案 17.3 的“端到端”一条，做到“点踩并填写纠错”为止（用户决定；纠错加入问答库、问答库直答属第六期）：

1. 搭建者建应用 → 配置（回答模型、系统提示词、一个文档库与检索设置、兜底话术、开场白）→ 保存草稿。
2. 调试预览提问，展开处理过程（意图识别、改写、召回、重排、提示词、模型调用）→ 点召回结果看分块位置。
3. 发布（含发布校验失败场景：没选模型、没引用知识库、不同向量化模型未开重排）。
4. 终端用户登录 → “我的应用”出现该应用 → 提问（流式）→ 点角标预览 PDF、Word（固定样例）→ 下载原文件（开关开/关）。
5. 点踩并填写纠错内容 → 搭建者在“用户反馈”列表看到该反馈，打开对应“对话日志”看到这一问的回答与处理过程（含点踩原因）。
6. 再覆盖 17.3 里第四期能测的其他要点：
   - 权限：终端用户调用控制台接口 403；仅有“查看”权限的人读日志/反馈 403；使用范围三档（含指定组织含下级、指定用户、系统管理员）。
   - 版本：两个协作者基于同一 revision 保存，后者 `DRAFT_CONFLICT`；发布后改草稿不影响终端用户；恢复历史版本后草稿与该版本一致。
   - 生成控制：中途断开后回答状态 `stopped` 且保存已输出部分、用量记 `CANCELLED`；同一会话并发提问 `CONVERSATION_BUSY`；重新生成后旧回答在日志中可见；只能重新生成最后一问。
   - 引用预览与下载限制：他人的会话、被移出使用范围、应用停用后返回 403；关闭下载后立即不能下载；文档重新入库后旧回答仍显示快照片段。
   - 日志：终端用户删除的会话在日志中仍可见并标注“用户已删除”；删除应用后接口不再返回。
   - 反馈：同一用户对同一回答再次点踩为更新。
   - 引用检查：知识库缩小可见范围导致应用创建人看不到时被拒绝并列出该应用；添加知识库只列出操作人能查看且应用能引用的。

### Vitest 偶发超时的原因与稳定（2026-10-26）

用户指出 P4-14/P4-17 联调期间 `AppCreateModal` 的“重名时在名称输入框下显示错误”和 `SettingsPage` 等用例在高负载下偶发超时。排查与依据：

- 单独跑 `src/pages/apps/AppCreateModal.test.tsx`（本机 load≈1.6）：7 个用例共 16.0s，其中“重名”用例 2.15s；该用例只用 `await screen.findByText("名称已存在")`，用的是 Testing Library 默认的 **1 秒** `asyncUtilTimeout`（与 Vitest 的 `testTimeout` 无关）。再开 4 个 CPU 压力进程后，整个文件从 16s 涨到 55s（“重名”用例本身仍在 1s 内，但已贴近）。
- 单独跑 `SettingsPage.test.tsx`（空闲）：13 个用例共 23.6s，5 个交互用例每个约 5.7s；P4-17 记录的 30s 超时说明负载高时单个 AntD 表单用例的整段耗时超过了当时的 30s。根因是 jsdom + Ant Design 表单渲染本身很慢（每个用例渲染一整页表单），负载/换页时更慢，不是产品缺陷。
- 修复（不是只加大超时）：`vitest.setup.ts` 统一把异步查询超时放宽到 10s，并用 `ConfigProvider.config({ theme: { token: { motion: false } } })` 关掉 AntD 动效（实测 `AppCreateModal` 文件从 16.0s 降到 12.3s，“重名”用例从 2.15s 降到 1.39s）；`vite.config.ts` 把全局 `testTimeout` 从 30s 放宽到 60s，并去掉 `SettingsPage.test.tsx` 里每个用例冗余的 `}, 30000)`。
- 说明：这三处不在卡片“文件”清单里，是用户明确要求“查原因并稳定”后做的最小改动。
