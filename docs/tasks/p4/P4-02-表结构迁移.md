## 要做

### 1. 业务表 `app/apps/tables.py` 与 `app/chat/tables.py`（字段照应用技术方案 10）

`app/apps/tables.py`：

- `apps`：`id`（主键，同时外键 `resources.id` `ON DELETE CASCADE`）、`app_type`（`kb_qa`）、`draft_config`（jsonb，默认 `{}`）、`draft_revision`（int，默认 1）、`draft_updated_by`（可空）、`draft_updated_at`、`published_version_id`（可空外键 `app_versions.id` `ON DELETE SET NULL`）、`usage_scope`（`platform` / `orgs` / `users`）。名称、描述、所属组织、可见范围、启停状态在 `resources`（`type='app'`）。
  - `apps` 与 `app_versions` 互相外键（循环）：建表时先建两张表，再用 `ALTER TABLE` 补 `apps.published_version_id` 的外键（Alembic 里用 `op.create_foreign_key`；ORM 里用 `ForeignKey(..., use_alter=True)`），保证迁移在空库和已有数据上都能跑。
- `app_versions`：`id`、`app_id`（外键 `apps.id` `ON DELETE CASCADE`）、`version_no`、`config`（jsonb）、`config_hash`（text）、`note`（text）、`published_by`、`published_at`；唯一约束 `(app_id, version_no)`。插入后不修改（应用技术方案 5.2）。
- `app_usage_targets`：`app_id`（外键 `apps.id` `ON DELETE CASCADE`）、`target_type`（`org` / `user`）、`target_id`（bigint）；唯一约束 `(app_id, target_type, target_id)`。使用范围为 `platform` 时没有行（应用技术方案 11）。

`app/chat/tables.py`：

- `conversations`：`id`、`app_id`（外键 `apps.id`）、`user_id`、`title`（text）、`last_active_at`、`created_at`、`deleted_at`（可空，软删除；对话页不显示、日志照常显示并标注“用户已删除”）；索引 `(app_id, user_id, last_active_at)`。
- `chat_turns`：`id`、`conversation_id`（外键 `conversations.id` `ON DELETE CASCADE`）、`seq`、`question`（text）、`rewritten_question`（text，可空）、`current_answer_id`（可空，外键 `chat_answers.id` `ON DELETE SET NULL`）、`created_at`；唯一约束 `(conversation_id, seq)`（补充）。
- `chat_answers`：`id`、`turn_id`（外键 `chat_turns.id` `ON DELETE CASCADE`）、`seq`、`version_id`（可空外键 `app_versions.id` `ON DELETE SET NULL`）、`kind`（`generated` / `qa_direct` / `fallback` / `chitchat`）、`status`（`generating` / `done` / `stopped` / `failed`）、`content`（text）、`reasoning`（text）、`citations`（jsonb，引用快照，应用技术方案 8.2）、`cited`（bigint[]，实际引用过的编号）、`suggestions`（jsonb）、`error_code`、`input_tokens`、`output_tokens`、`first_token_ms`、`total_ms`、`updated_at`、`created_at`；索引 `(turn_id)`、`(created_at)`。
- `answer_traces`：`answer_id`（主键，外键 `chat_answers.id` `ON DELETE CASCADE`）、`app_id`、`created_at`、`trace`（jsonb，步骤数组）。处理过程体积大，单独成表。
- `answer_feedback`：`id`、`answer_id`（外键 `chat_answers.id` `ON DELETE CASCADE`）、`app_id`、`user_id`、`rating`（`up` / `down`）、`reasons`（text[]）、`correction`（text）、`handled_qa_id`（可空，第六期纠错加入问答库后生成）、`handled_by`（可空）、`handled_at`（可空）、`created_at`、`updated_at`；唯一约束 `(answer_id, user_id)`（同一用户对同一回答再次点击为更新，应用技术方案 12.3）。

说明：

- 枚举列加 CHECK 约束（照 P3-03 的做法），取值与 P4-01 的枚举一致。
- 用户、组织、模型列不加外键（照 P3-03 的最小改动）：`draft_updated_by`、`published_by`、`conversations.user_id`、`answer_feedback.user_id`、`handled_by`。
- 时间列用 `timestamptz`；主键 bigint 自增。
- `answer_traces`、`answer_feedback`、`chat_answers` 的 `ON DELETE CASCADE` 只在删回答时生效；第四期删除应用是软删除资源，不删这些行（应用技术方案 12.2）。

## 注意

- 有两组循环外键：`apps.published_version_id ↔ app_versions.app_id`、`chat_turns.current_answer_id ↔ chat_answers.turn_id`。迁移里都先建两张表，再用 `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY ... ON DELETE SET NULL` 补其中一条；ORM 里用 `ForeignKey(..., use_alter=True)`，否则建表顺序会互相等待。
- `apps.id` 同时是 `resources.id` 的外键，建应用时先建资源再插 `apps`（P4-03 照 P3-04 的做法）。
- 删除应用是软删除资源：`apps` 行保留（会话、日志、反馈都挂在 `apps.id` 上），不要给 `resources` 加级联删 `apps`（P4-03 的 `on_delete` 钩子只清 `resource_refs`，不删业务行）。P4-01 契约与本卡一致。
