## 要做

### 1. 资源类型注册 `app/apps/__init__.py`

- 注册资源类型 `app`：code `app`、label `应用`、`fixed_visibility=None`。
- `on_delete(session, resource)`：删除该应用的 `resource_refs`（`ref_resource_id = resource.id`，即它引用了哪些模型/知识库的登记，避免应用删除后挡住模型、知识库的删除检查）；**不删** `apps` 行、`app_versions`、`app_usage_targets`、会话、日志、反馈（应用技术方案 12.2：删除应用是软删除，会话、日志、反馈保留）。
- 在 `app/main.py` 启动时调用 `app.apps.register()`（纯内部细节）。

### 2. 业务逻辑 `app/apps/service.py`

路由只做参数接收、权限依赖、调用这里、写审计。

- `list_apps(session, ctx, pagination, app_type, status, visibility, org_id, include_sub, keyword)`：join `resources` + `orgs`，用 `resources.access.access_clause(ctx, VIEW)` 过滤（拼进 SQL 的 WHERE）；`status` 是推导状态（`disabled` → `resources.status='disabled'`；`unpublished` → 启用且 `published_version_id IS NULL`；`published` → 启用且非空）；按 `resources.created_at` 倒序；返回 `Page[AppOut]`。
- `get_app(session, ctx, app_id)`：`access.get_for(session, ctx, app_id, VIEW, type="app")`。
- `create_app(session, ctx, body)`：
  - 用 `resources.service.create_resource(session, ctx, "app", name, visibility, description, org_id)` 建资源（名称唯一、系统管理员必须给 `org_id` 的规则复用 P1-12）。
  - 插 `apps` 行：`app_type='kb_qa'`、`draft_config` 为默认 `AppConfig`（`app/apps/config.py` 的默认值序列化）、`draft_revision=1`、`draft_updated_by=ctx.user_id`、`draft_updated_at=now()`、`published_version_id=NULL`、`usage_scope='orgs'`。
  - 插 `app_usage_targets`：`target_type='org'`、`target_id=资源所属组织`（应用技术方案 10、11：默认为应用所属组织）。
- `update_app(session, ctx, app_id, body)`：只改 `name`、`description`；带 `app_type` 返回 422 `APP_TYPE_IMMUTABLE`（原型 `#v-appperm`“类型创建后不可修改”）。名称唯一性用资源表规则（冲突 409 `NAME_CONFLICT`）。
- `app_out(session, app)`：拼 `AppOut`（`org`、`owner`、`status`、`published_version`、`draft_has_changes`、`draft_updated_at`、`usage_scope`、`chat_path`、`editable`、`manageable`）。
  - `draft_has_changes`：`config_hash(draft_config)` 与当前发布版本的 `config_hash` 比较（没有发布版本时为 true）。
  - `editable` / `manageable` 用 `resources.access` 的同一套规则算（同 P3-04 的做法）。
- `config_hash(config)` 加到 `app/apps/config.py`：配置按键排序后序列化再取 SHA-256（应用技术方案 5.2），供 `app_out` 与 P4-04 的发布/恢复共用。
- 删除、停用启用、可见范围、增减协作者分别调 `resources.service.delete_resource` / `set_status` / `change_visibility` / `add_member` / `remove_member`，不要另写一套权限判断。

### 3. 路由 `app/apps/router.py`

实现 P4-01 契约里的应用接口（应用管理与可见范围、协作者；使用范围、草稿版本、kb-candidates、prompt-preview 仍是占位，P4-04/P4-05/P4-08）：

- 权限：列表和详情 `console.use` + 资源“查看”；新建 `resource.create`；编辑走资源“编辑”；可见范围、协作者、停用、删除走资源“管理”（由 `resources.service` 内部判断）。
- 写审计：路由用 `audited("app.xxx")`，成功调 `audit_success(request, target, detail)`，`AuditTarget("app", resource.id, resource.name, resource.org_id)`。
- 停用应用的引用清单：应用不被其他资源引用，不需要 `refs` 接口；停用只改状态（应用技术方案 14 的审计动作里没有引用清单）。

### 4. 审计动作 `app/audit/actions.py`

加动作与中文名：`app.create` 创建应用、`app.update` 修改应用、`app.delete` 删除应用、`app.change_visibility` 调整可见范围、`app.add_member` 添加协作者、`app.remove_member` 移除协作者、`app.disable` 停用应用、`app.enable` 启用应用；`TARGET_TYPE_LABELS` 加 `app`（应用）。发布、恢复、使用范围、草稿的审计在 P4-04/P4-05 加（应用技术方案 14：保存草稿不写审计）。

## 注意

- 权限一律复用 `resources/access.py`（P1-12），不要再写一套；列表过滤拼进 SQL 的 WHERE。
- 应用是软删除，`on_delete` 只清引用登记，不删 `apps` 业务行（P4-02 的约定）。
- `draft_config` 存默认 `AppConfig`（不是 `{}`），前端表单直接拿默认值；读取时仍按 `AppConfig` 解析，容错 `{}`。
