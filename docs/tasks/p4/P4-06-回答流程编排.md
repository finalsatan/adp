## 要做

### 1. 运行上下文与处理过程记录器 `app/chat/pipeline.py`、`app/chat/traces.py`

- `AnswerRun`（dataclass）：应用与当前发布版本、`AppConfig`、会话与轮次、当前问题、历史（最近 N 轮的问题与回答文字，角标已去掉）、处理过程记录器、各步骤结果（意图、改写后问题、召回结果、参考内容、提示词、回答文字与用量）。
- `TraceRecorder`（`app/chat/traces.py`）：`start_step(name)` / `finish_step(name, *, input=None, output=None, model=None, input_tokens=None, output_tokens=None, prompt_version=None)`，按顺序累积步骤（步骤名、开始时间、耗时、输入、输出、模型、token 数、提示词版本）；`build()` 返回 `TraceOut`。**只记录，不落库**（落库在 P4-09）。
- 流程函数 `run_flow(run, emit)`：`emit` 是 `async (event: ChatSseEvent) -> None` 的回调（P4-09 接到 SSE；测试里收集到列表）。流程按固定顺序调用各步，每步开始 / 结束调 `TraceRecorder` 并发 `STEP_STARTED` / `STEP_FINISHED`（应用技术方案 9.1）。`run` 上累积最终结果，供 P4-09 落库。

### 2. 模型可用性预检（应用技术方案 6.5）

- 提问开始时统一检查一次：回答模型、意图识别模型、问题改写模型、重排模型（文档库与问答库的），以及所引用知识库的向量化模型，存在且 `status='enabled'`、未删除；任一不可用直接抛 `MODEL_UNAVAILABLE`（409），对话页显示“模型不可用”。不在流程中途才失败。
- 检查复用 `app/gateway` 的模型读取；不实际调用。

### 3. 意图识别与问题改写（应用技术方案 6.2）

- 两步都开启时**并行**执行（`asyncio.TaskGroup`；一路出错时按 6.5 降级，不让另一路跟着失败）。输入是最近 N 轮（记忆轮数）的问题和回答文字加当前问题。
- 意图识别：提示词要求只返回 `{"intent": "knowledge"}` 或 `{"intent": "chitchat"}`，温度 0、最大输出 32 token、关闭深度思考；模型支持时用 JSON 模式，解析用 `json-repair`（补充：加 `json-repair` 依赖）。解析失败、超时、返回其他值一律按知识问题处理。关闭时所有问题都按知识问题处理。
- 问题改写：提示词要求只输出改写后的问题，温度 0、关闭深度思考；会话第一问不调用模型，直接用原问题；输出为空或明显过长（超过原问题加历史的总长度）时用原问题。关闭时用原问题。
- 两个提示词写在 `app/chat/pipeline.py` 里并带版本号（`INTENT_PROMPT_VERSION`、`REWRITE_PROMPT_VERSION`），处理过程记下版本；本阶段不开放修改。（回答提示词组装另在 P4-08 新建 `app/chat/prompts.py`，本卡不建这个文件。）
- 判为闲聊时丢弃改写结果；检索用改写后的问题（意图识别、改写都开启且改写成功时），否则用原问题。
- 模型调用都走 `gateway.chat`，`CallMeta(source="app", source_id=app_id, user_id=..., org_id=...)`；调试预览的来源 `app_debug` 由 P4-11 传入。

### 4. 闲聊、兜底与降级

- 闲聊（`kind=chitchat`）：判为闲聊问候时不检索；回答模型 + 搭建者的系统提示词 + 固定的闲聊要求（简短回应、引导用户提问、不回答事实性问题），带历史、不带参考内容。
- 兜底（`kind=fallback`）：检索结果为空（P4-06 的检索占位返回空）时，用一个 `TEXT_DELTA` 发出 `reply.fallback_text`，不调用模型。
- 降级（应用技术方案 6.5，本卡实现的部分）：
  - 意图识别失败 / 被限流 → 按知识问题继续，处理过程记失败原因；
  - 问题改写失败 / 被限流 → 用原问题继续，处理过程记失败原因；
  - 向量化、召回失败 → 出错的知识库跳过，其余照常；全部失败返回 `RETRIEVAL_FAILED`（本卡只处理检索步抛出的异常，具体在 P4-07）；
  - 重排失败 → `RETRIEVAL_FAILED`；
  - 回答模型被限流 → `MODEL_RATE_LIMITED`；报错、超时 → `RUN_ERROR`（生成在 P4-09）；
  - 除模型不可用外的降级都是本文补充。
- 流程结束时设置 `run.kind`、`run.citations`、`run.content`（或流式文字）、`run.suggestions`（第六期为空）、`run.error`。

### 5. 三步占位（后续卡替换）

- `_retrieve(run)`：P4-06 先实现为“返回空结果”，让兜底路径可测；P4-07 替换为真正的多知识库检索（复用 P3-13 的 `recall_and_fuse` / `rerank_and_expand`）。
- `_assemble_prompt(run)`：P4-06 先只放当前问题（无参考内容）；P4-08 替换为提示词组装、防注入与上下文预算。
- `_generate(run, emit)`：P4-06 先非流式返回一段占位文字（`kind=generated`），供编排测试；P4-09 替换为 `gateway.chat_stream` 流式输出、追问建议、停止 / 断开 / 重新生成。

## 注意

- 流程自己编排（Q1）：每一步一个异步函数，由固定流程函数按顺序调用；不要引入 LangGraph 等框架。
- 并行用 `asyncio.TaskGroup`，一路失败按 6.5 降级，不要让另一路跟着失败。
- 意图识别的解析用 `json-repair`（模型可能返回带多余文字的 JSON）；解析失败按知识问题处理，不要抛给用户。
- 检索、提示词、生成三步的占位要写清楚“由 P4-07/P4-08/P4-09 替换”，P4-06 的测试对占位行为断言（空结果 → 兜底），后续卡替换后同步更新占位相关的断言。
- 本卡不写接口、不落库、不发 SSE，测试直接调流程函数并收集 `emit` 的事件。
