## 要做

### 1. 草稿 `app/apps/draft.py`

- `get_draft(session, ctx, app_id)`：资源“编辑”权限；返回 `DraftOut`（`draft_revision`、`config`、`has_changes`、`updated_by`、`updated_at`）。
- `save_draft(session, ctx, app_id, body)`：资源“编辑”权限；`body.draft_revision` 与库中不一致返回 409 `DRAFT_CONFLICT`；保存只做**格式校验**（`AppConfig` 能解析）和“重排要求”检查（见第 3 节第 4 条），允许不完整配置；更新 `draft_config`、`draft_revision += 1`、`draft_updated_by`、`draft_updated_at`；**重新计算 `resource_refs`**（见第 4 节）。保存草稿不写审计（应用技术方案 14）。
- 草稿哈希用 P4-03 的 `config_hash`；`has_changes` = 草稿哈希 ≠ 当前发布版本哈希（没有发布版本时为 true）。

### 2. 发布、历史与恢复 `app/apps/versions.py`

- `publish(session, ctx, app_id, body)`：资源“编辑”权限。
  1. 发布校验（第 3 节），不通过返回 422 `PUBLISH_CHECK_FAILED`，`detail.problems` 为问题清单。
  2. 一个事务里：插 `app_versions`（`version_no` 在应用内递增，取当前最大 +1；存 `config`、`config_hash`、`note`、`published_by`、`published_at`），把 `apps.published_version_id` 指向它；**重新计算 `resource_refs`**；写审计 `app.publish`（`detail` 含 `version_no`）。
  3. 返回 `AppVersionOut`。正在生成的回答不受影响（发布只换版本指针，生成用的是开始时的版本）。
- `list_versions(session, ctx, app_id, pagination)`：资源“查看”权限；按 `version_no` 倒序；`AppVersionOut` 的 `is_current` = 是否为 `apps.published_version_id`。
- `get_version(session, ctx, app_id, version_no)`：资源“查看”权限。
- `restore_version(session, ctx, app_id, version_no)`：资源“编辑”权限；把该版本 `config` 复制成草稿，`draft_revision += 1`、更新 `draft_updated_by` / `draft_updated_at`；不检查引用是否有效（再发布时由发布校验拦下）；重新计算 `resource_refs`；写审计 `app.restore`；返回 `DraftOut`。
- 写审计 `app.publish`、`app.restore`，`AuditTarget("app", ...)`。

### 3. 发布校验 `app/apps/validation.py`

逐项检查，问题清单每项 `PublishProblemOut(code, message, field?)`：

1. 回答模型已选择且已启用（`model.status='enabled'`、未删除）；单独选了意图识别、问题改写、文档库重排、问答库重排模型的，同样要求存在且已启用。
2. 至少引用了一个知识库（一个也没有时每个问题都只能回复兜底话术）。
3. 每个引用的知识库都存在，且应用仍能引用它（第 5 节的 `app_can_reference_kb`）。
4. 所选文档库使用了不同的向量化模型时，必须开启文档库的重排；所选问答库使用了不同的向量化模型时，必须开启问答库的重排（需求 5.1.3）。**这一条在保存草稿时也检查**（`save_draft` 调同一个函数），不通过返回 422 `VALIDATION_ERROR`，`detail.problems` 同结构（草稿保存不是发布，不用 `PUBLISH_CHECK_FAILED`）。
5. 过滤条件引用的文件夹、元数据字段、问答库分类仍然存在（问答库分类第六期，字段先校验为空）。

已停用的知识库允许发布（检索时跳过，需求 5.1.3）。

### 4. 引用登记 `app/apps/refs.py`

- `recompute_refs(session, app_id, configs)`：`configs` 是“草稿 ∪ 当前发布版本”的配置列表（历史版本不算）。删掉该应用旧的 `resource_refs`（`ref_resource_id = app_id`），按去重后的引用重新插入：模型（回答、意图识别、问题改写、文档库重排、问答库重排，`target_type='model'`）和知识库（`target_type='resource'`）。保存草稿、发布、恢复时调用。
- 应用能否引用某个知识库 `app_can_reference_kb(session, app, kb)`（应用技术方案 5.4，2026-10-22 确认）：
  - 创建人有效（账号启用且仍属于应用所属组织；启用的系统管理员也算有效）时，对创建人按技术方案 7.3 的查看条件计算。
  - 创建人失效（停用，或已不属于应用所属组织）时，按应用所属组织计算：知识库 `visibility='platform'`，或 `visibility='org'` 且应用所属组织的 path 以知识库所属组织的 path 开头。`private` 的知识库和协作者关系都不算。
  - 不保存“失效”状态，每次按创建人当前状态和所属组织计算。
- 注册引用检查函数（`resources.registry.register_ref_checker`）：当知识库缩小可见范围或移除协作者时，按 `resource_refs` 找出引用它的应用，对每个应用用“修改后”的可见范围和协作者重新判断 `app_can_reference_kb`；有不能再引用的就返回 `RefBlocker(app.id, "app", app.name)`，让 P1-12 抛 409 `RESOURCE_IN_USE` 并列出这些应用（需求 4.1.2、10.4）。在 `app/apps/__init__.py` 的 `register()` 里注册。
- `list_kb_candidates(session, ctx, app_id)`：资源“编辑”权限；列出操作人能查看的知识库（拼进 SQL 的 WHERE，按技术方案 7.3），每个标 `added`（是否已在草稿里）和 `selectable`（操作人和应用创建人都能查看、且 `app_can_reference_kb` 为真），不可选的给 `reason`（中文，如“应用创建人不能查看”，原型 `#d-addkb`）。

### 5. 路由 `app/apps/router.py`

把 P4-01 契约里本卡的占位换成实现：`GET/PUT /apps/{id}/draft`、`GET /apps/{id}/prompt-preview`（仍占位，P4-08）、`GET /apps/{id}/kb-candidates`、`POST /apps/{id}:publish`、`GET /apps/{id}/versions`、`GET /apps/{id}/versions/{v}`、`POST /apps/{id}/versions/{v}:restore`。写 `app.publish`、`app.restore` 审计。

### 6. 审计动作

`app/audit/actions.py` 加 `app.publish` 发布应用、`app.restore` 恢复历史版本（P4-03 已加其余）。

### 和卡片不一致 / 自己补充的地方

1. **`app_can_reference_kb` 多了两个仅关键字参数 `visibility` / `removed_user_id`**：缩小可见范围 / 移除协作者时要在“修改后”的状态下预演，卡片只写了 `(session, app, kb)`，加参数是纯实现细节。
2. **复用 `access._can` 时用一个只带 `owner_id` / `org_id` / `visibility` 的轻量对象承载覆盖后的可见范围**：`access.py` 不在本卡文件清单里，不改它；`_can` 的查看分支只读这三个字段。
3. **`check_rerank` 对“单独选了意图 / 改写 / 重排模型”一律要求存在且启用（不看对应开关是否打开）**：按卡片第 3 节第 1 条的原文实现。
4. **问答库分类不校验**：卡片写“问答库分类第六期，字段先校验为空”，本卡不检查 `qa_category_ids`（第六期实现）。
5. **`list_kb_candidates` 的 `reason` 文案**：创建人有效时为“应用创建人 {name} 不能查看”（对齐原型 `#d-addkb`），创建人失效时为“应用创建人已失效，应用所属组织不能查看”。
6. **`parse_config` 放在 `validation.py`**：避免 `draft` 与 `validation` 的循环导入，纯实现细节。

### 缺陷修复（验收发现）

- 缺陷：`save_draft` 先读应用再比较 `draft_revision`，没有行锁；两个请求同时基于同一 revision 保存时都读到旧值、都通过比较，后提交的覆盖前者，乐观锁失效（应用技术方案 17.3）。
- 修复：`draft.py` 新增 `get_app_for_update`（`SELECT ... FOR UPDATE` + `populate_existing`），`save_draft`、`publish`、`restore_version` 都先锁 `apps` 行再读 revision / 算 `max(version_no)`，串行化对同一应用的草稿保存、发布与恢复；并发发布不再产生重复版本号。
- 测试：`test_app_draft.py::test_concurrent_save_draft_one_conflict`（两个独立 `AsyncClient` / session 用 `asyncio.gather` 真并发保存同一 revision，恰好一个 200、一个 409 `DRAFT_CONFLICT`）、`test_app_publish.py::test_concurrent_publish_unique_version_no`（并发发布都成功，版本号 1、2 不重复）。
