### 2. 写入 `app/audit/service.py`

- `AuditTarget(type, id, desc, org_id)`：desc 是给人看的对象描述，如用户名、组织名、资源名。
- `async record(ctx | None, action, target | None, result, detail=None, actor=None)`：
  - 用**独立的数据库会话**写入并提交，不参与业务事务（技术方案 8.2）。
  - 操作人从 ctx 取（id、用户名、组织 id、组织名）；ctx 为空时用 `actor` 参数（登录失败时由 P1-08 传入）。
  - 对象所属组织名：按 `target.org_id` 查 orgs（含已删除的）取名称，冗余存储。
  - ip、request_id 从 ctx 或请求上下文取。
  - detail 中键名含 `password`、`token`、`secret`、`api_key` 的项一律删除（补充，防止误记敏感信息）。
  - 写入失败：记 ERROR 日志并立即重试一次；仍失败不抛异常，不影响业务返回。
- 失败操作也要记（技术方案 8.2“需审计的动作失败时也记录一条 result=failure”）。做法（补充）：
  - 依赖 `audited(action)`：放在路由 `dependencies` 列表的**第一个**，在 `request.state.audit` 上记下动作，并标记“尚未记录”。
  - 路由成功时，在业务提交之后调用 `await audit_success(request, target, detail)`，写 success 并标记已记录。
  - 全局 `AppError` 处理器（P1-01）中：如果 `request.state.audit` 存在且尚未记录，并且 `request.state.ctx` 存在（已登录），写一条 failure，detail 为 `{"code": 错误码}`，对象取 `request.state.audit.target`（路由可以提前设置）或为空。未登录（401）的请求不记。
  - 这样权限不足（`require_perm` 抛出的 403）也能记下来，因为 `audited` 先于 `require_perm` 执行。
- 不在审计范围内的接口失败不进审计表，只写应用日志。

### 3. 查询接口

实现 P1-03 的 `GET /api/v1/audit-logs` 和 `GET /api/v1/audit-logs/meta`：

- 范围（需求 10.6）：系统管理员看全部；组织管理员看 `actor_org_id` 或 `target_org_id` 在管理范围内的记录（用 P1-06 的 `scope_org_ids_sql`，含已删除组织）。条件拼进 SQL。
- 筛选：时间范围；操作人关键字（匹配 actor_name）；动作；对象类型；对象关键字（匹配 target_desc）；组织（操作人组织或对象组织在该组织及下级中，同样要在管理范围内）；结果。
- 按 `at` 倒序分页。返回里带 `action_label`、`target_type_label`。
