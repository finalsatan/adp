# P1-11 用户管理接口

状态：待开始
前置：P1-08、P1-10
被依赖：P1-13、P1-14、P1-15

## 目标

实现用户管理的全部接口（含任命、撤销系统管理员）、个人中心改资料 `PATCH /api/v1/me`，以及选协作者用的用户搜索。

## 依据

- 需求 10.1、10.2、10.5
- 技术方案 6.1（users）、7.2（**账号管理的额外限制**、调整所属组织、任命系统管理员）、8.1（停用和重置后令牌的处理）、13.2（权限、系统管理员两条）
- 原型 `#v-users`、`#d-newuser`、`#d-edituser`、`#m-resetpw`、`#v-profile`
- P1-03 用户接口；P1-06 的 `can_manage_account`、`bump_perm_version`；P1-08 的 `lockout` 和作废刷新令牌的函数

## 要做

除用户搜索外，接口都要求 `user.manage`；写操作的路由依赖第一个放对应的 `audited(...)`，审计对象类型 `user`，desc 为用户名，对象组织为目标用户（变更后）的所属组织。

### 列表 `GET /api/v1/users`

- 范围：系统管理员看全部（含系统管理员）；组织管理员只看所属组织在管理范围内的用户（自然不含系统管理员）。
- 筛选：`org_id`（`include_sub` 为真时含下级，组织本身要在范围内，否则 403）、`role`（`sys_admin` 用于系统管理员单独成组显示，需求 10.1）、`status`、`keyword`（用户名、姓名、邮箱模糊匹配）。按用户名排序分页。
- 每项：`locked` 用 `lockout.is_locked` 判断（每页最多 100 个，可以用 Redis pipeline 一次查完）；`owned_resource_count` 为“所属组织等于该用户当前组织、由他创建、未删除”的资源数；`manageable` 用 `can_manage_account`。

### 新建 `POST /api/v1/users`

- 用户名去空格转小写，已存在（含停用用户）→ 409 `USERNAME_EXISTS`。
- 所属组织必须在操作人管理范围内；角色只能是 org_admin / builder / end_user。
- 角色为 org_admin 时：操作人是组织管理员的，所选组织必须严格在其组织之下（技术方案 7.2：只能把下级组织的用户设为组织管理员），否则 403。
- 初始密码按策略校验，不通过 422 `WEAK_PASSWORD`。`must_change_password=true`，`created_by` 为操作人。
- 审计 `user.create`。

### 详情 `GET /api/v1/users/{id}`

目标用户的所属组织不在范围内（或目标是系统管理员而操作人不是）→ 404 `NOT_FOUND`。

### 修改 `PATCH /api/v1/users/{id}`

- `can_manage_account` 为假 → 403（包括改自己：自己的资料走个人中心）。
- 目标是系统管理员时，请求里不能带 `org_id`、`role`（改身份用撤销接口），否则 422。
- 改所属组织：原组织和新组织都要在操作人管理范围内（技术方案 7.2）。
- 改角色或组织后，若最终角色是 org_admin：操作人是组织管理员的，最终组织必须严格在其组织之下。
- 只要角色、组织有变化就 `bump_perm_version`。用户原来创建的资源不动（需求 10.2：留在原组织，他失去创建人权限）。
- 审计：资料字段变化记 `user.update`；角色变化记 `user.change_role`（detail `{"from": "builder", "to": "org_admin"}`）；组织变化记 `user.change_org`（detail 为原、新组织的 id 和名称）。一次请求可能产生多条。

### 停用、启用

- `:disable`：`can_manage_account` 为真才可以；目标是系统管理员时，如果它是最后一个启用的系统管理员 → 409 `LAST_SYS_ADMIN`。停用时 `token_version + 1`、作废该用户全部刷新令牌、`bump_perm_version`（技术方案 8.1、7.2）。审计 `user.disable`。
- `:enable`：同样的管理权限判断；审计 `user.enable`。
- 已是目标状态时直接返回当前数据，不报错（补充）。

### 重置密码 `:reset-password`

- 管理权限判断同上；新密码按策略校验（与该用户的用户名比较）。
- 设置新哈希、`must_change_password=true`、`token_version + 1`、作废全部刷新令牌。已签发的访问令牌最迟到期失效（需求 10.5，不做立即踢下线）。
- 审计 `user.reset_password`（detail 里不放密码）。

### 解锁 `:unlock`

管理权限判断同上；调用 `lockout.unlock`；审计 `user.unlock`（补充）。

### 任命、撤销系统管理员

- 两个接口都只有系统管理员能调用，否则 403（技术方案 7.2）。
- `:grant-sys-admin`：目标必须是启用的、非系统管理员的用户。把 role 改为 sys_admin、org_id 置空；他在原组织创建的资源留在原组织。`bump_perm_version`。审计 `user.grant_sys_admin`，对象组织为原组织。
- `:revoke-sys-admin`：目标必须是系统管理员；请求带 `org_id`（必须存在）和 `role`（org_admin / builder / end_user）。撤销后若已没有其他启用的系统管理员 → 409 `LAST_SYS_ADMIN`。可以撤销自己（只要不是最后一个，补充）。`bump_perm_version`。审计 `user.revoke_sys_admin`。

### 个人中心 `PATCH /api/v1/me`

- 只能改自己的 name、email、phone（需求 10.2：用户名、所属组织、角色只读）。
- 审计 `user.update`，操作人和对象都是自己。

### 用户搜索 `GET /api/v1/users:search`

- 要求 `console.use`（搭建者添加协作者时要用，可选任何组织的用户，原型 `#d-collab`）。
- 按用户名前缀或姓名包含匹配，只返回启用用户，最多 20 条，返回 `UserSearchOut`。

## 验收标准

- [ ] 测试 `test_users.py`（技术方案 13.2 的“权限”条逐项覆盖）：
  - 组织管理员能管理本组织和下级组织的搭建者、终端用户，以及下级组织的组织管理员。
  - 组织管理员对同级、上级组织管理员和系统管理员执行修改、停用、重置密码、解锁都返回 403。
  - 组织管理员只能把下级组织的用户设为组织管理员（新建和修改两种途径都测）。
  - 调整所属组织时新组织不在范围内返回 403。
  - 用户名大小写不同视为重复；弱初始密码返回 422 和原因。
  - 停用后：原访问令牌立即 401（P1-06 的缓存失效），刷新令牌不可用。
  - 调整角色后，被调整的用户不重新登录就获得新权限。
  - 重置密码后：该用户下次登录 `must_change_password=true`，原刷新令牌失效。
  - 锁定的用户在列表中 `locked=true`，解锁后为 false 且能立即登录。
  - 改自己返回 403。
  - 列表按组织含下级筛选正确；组织管理员看不到系统管理员。
  - 每个写操作产生正确的审计动作；调整角色的 detail 含 from、to。
- [ ] 测试 `test_users_sysadmin.py`：系统管理员任命另一个用户为系统管理员后其 org 为空、资源仍在原组织；撤销或停用最后一个启用的系统管理员返回 409；有两个时可以撤销其中一个并指定组织和角色；组织管理员调用任命、撤销返回 403。
- [ ] 测试 `test_me_update.py`：能改姓名、邮箱、手机；请求带 username、role、org_id 时返回 422（请求结构禁止多余字段，见 P1-03）。
- [ ] 用户搜索：搭建者能用，终端用户 403；停用用户不出现；最多 20 条。
- [ ] `make backend-lint backend-test` 通过。

## 注意

- “最后一个启用的系统管理员”的检查要在事务里加锁（如 `SELECT ... FOR UPDATE` 锁住全部系统管理员行），防止两个系统管理员同时互相撤销。
