## 要做

### 1. 资源类型注册 `app/resources/registry.py`

```python
@dataclass
class ResourceType:
    code: str                      # kb / scheme / app
    label: str                     # 知识库 / 入库方案 / 知识问答
    fixed_visibility: str | None   # 入库方案固定为 platform
    on_delete: Callable | None     # 删除时的类型专属处理（删表、删文件等），为空时只做软删除
    on_status_change: Callable | None
```

`register_resource_type(t)`、`get_resource_type(code)`、`list_resource_types()`。第一期不注册任何类型。`GET /api/v1/resource-types` 返回注册表内容。P1-07 审计中对象类型的中文名也从这里取。

### 2. 权限判断 `app/resources/access.py`

照技术方案 7.3。“创建人”只在创建人当前所属组织等于资源所属组织时有效（需求 10.2：调走后失去创建人权限）。

| 操作 | 满足任一即可 |
| --- | --- |
| view（查看、引用） | 系统管理员；visibility = platform；visibility = org 且用户所属组织的 path 以资源所属组织的 path 开头；有效创建人；协作者；资源所属组织在其管理范围内的组织管理员 |
| edit（编辑内容） | 系统管理员；有效创建人；协作者；范围内的组织管理员 |
| manage（改可见范围、增减协作者、停用、删除） | 系统管理员；有效创建人；范围内的组织管理员 |

- `access_clause(ctx, action) -> ColumnElement`：返回可直接放进 WHERE 的 SQLAlchemy 条件（联 orgs 取资源组织的 path；协作者用 EXISTS 子查询），列表查询用它，**不在内存里过滤**。
- `async get_for(session, ctx, resource_id, action, type=None) -> Resource`：不存在、已删除、类型不符、或连 view 都不满足 → 404 `NOT_FOUND`（补充：不暴露看不到的资源是否存在）；能 view 但不满足所需操作 → 403 `PERMISSION_DENIED`（补充）。
- 已停用的资源照常按上面规则判断权限（停用影响的是使用，不是管理）。

### 3. 创建资源的公共函数 `app/resources/service.py`

`async create_resource(session, ctx, type, name, visibility, description=None, org_id=None) -> Resource`（第一期没有调用方，但要实现并测试）：

- 要求 `resource.create`。
- 非系统管理员：所属组织取本人组织，请求里的 org_id 忽略。系统管理员：org_id 必填，否则 422 `ORG_REQUIRED`；组织必须存在（需求 10.4）。
- 类型有 fixed_visibility 时用它。
- 同类型、同组织、未删除的重名 → 409 `NAME_CONFLICT`。

### 4. 引用检查的扩展点

- `register_ref_checker(fn)`：fn 的签名为 `async fn(session, resource, new_visibility: str | None, removed_user_id: int | None) -> list[RefBlocker]`，返回“会因此不能再引用它”的引用方（id、type、name）。
- 缩小可见范围（platform → org / private，org → private）和移除协作者之前，调用所有已注册的检查函数；有返回就 409 `RESOURCE_IN_USE`，`detail.refs` 列出它们（需求 10.4）。
- 删除资源前：resource_refs 中只要有引用它的资源（`target_type='resource'`）→ 409 `RESOURCE_IN_USE`。
- 第一期没有注册任何检查函数；第四期应用模块会注册“应用创建人能否查看”的检查（应用技术方案 5.4）。

### 5. 接口

| 接口 | 要求 | 说明 |
| --- | --- | --- |
| `GET /api/v1/resources` | `overview.view` | 系统管理员不加范围条件；组织管理员限定资源所属组织在管理范围内（需求 10.7）。筛选：类型、组织（含下级）、创建人、可见范围、状态、关键字（名称）。排除已删除。按创建时间倒序 |
| `PATCH /resources/{id}/visibility` | manage | fixed_visibility 的类型 → 422 `VISIBILITY_FIXED`；缩小范围时做引用检查；审计 `resource.change_visibility`，detail `{from, to}` |
| `GET /resources/{id}/members` | view | 按添加时间排序 |
| `POST /resources/{id}/members` | manage | 用户必须存在且启用，任何组织都可以（需求 10.4）；已是协作者 → 409 `ALREADY_MEMBER`；**允许把创建人本人加为协作者**（需求 10.2：调走的创建人需要时可被加为协作者）；审计 `resource.add_member`，detail 含被加用户的用户名 |
| `DELETE /resources/{id}/members/{user_id}` | manage | 做引用检查；不是协作者时 404；审计 `resource.remove_member` |
| `POST /resources/{id}:disable`、`:enable` | manage | 调用类型的 on_status_change（有的话）；审计 `resource.disable` / `resource.enable` |
| `DELETE /resources/{id}` | manage | 先做引用检查，再调用类型的 on_delete，最后软删除；审计 `resource.delete` |

- 审计对象：类型为资源类型代码，desc 为资源名，对象组织为资源所属组织。
- 改动资源时更新 `updated_at`。

### 和卡片不一致 / 自己补充的地方

1. `ResourceType.on_delete` / `on_status_change` 的签名卡片没定，取 `async fn(session, resource)`；`on_status_change` 在状态已写入 ORM 对象、提交前调用，`on_delete` 在软删除前调用。属内部实现细节。
2. `create_resource` 没有 HTTP 入口（卡片也说明第一期没有调用方），所以“不带 org_id → 422 `ORG_REQUIRED`”“重名 → 409 `NAME_CONFLICT`”在 service 层断言异常的 `status`/`code`。
3. `GET /resources` 的资源总览按卡片接口表用“管理范围”条件（需求 10.7），未用 `access_clause`：`access_clause` 的 view 还会包含范围外的全平台资源，与 10.7 冲突。`access_clause` 供后续各资源类型自己的列表查询使用，本卡用一致性测试保证它与 `get_for` 结论相同。
4. 关键字 LIKE 用 `_escape_like` 转义 `\`、`%`、`_` 并带 `escape="\\"`。
5. `access_clause` 约定调用方 join `Org`（`Resource.org_id == Org.id`），已在 docstring 说明。
6. 没跑 `make frontend-check`：本卡未改前端，且同工作区有别的 agent 正在改 `frontend/`，避免互相影响。
