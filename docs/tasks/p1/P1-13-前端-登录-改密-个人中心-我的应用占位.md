# P1-13 前端：登录、首次改密、个人中心、“我的应用”占位页

状态：已验收

被依赖：P1-19

## 目标

做出登录页、首次改密页、个人中心，以及第一期的“我的应用”占位页。

## 依据

- 需求 10.2（个人中心）、10.5
- 技术方案 8.1、11
- 原型 `#v-login`、`#v-changepw`、`#v-profile`、`#v-myapps`
- 接口：`POST /auth/login`、`POST /auth/change-password`、`GET /auth/policy`、`GET /me`、`PATCH /me`

## 要做

### 1. 登录页 `/login`

- 照原型：平台名和副标题、用户名、密码、登录按钮、底部提示“首次登录或密码被重置后，需要先修改密码。”
- 提交失败时在表单上方用 Alert 显示后端返回的 message（`INVALID_CREDENTIALS`、`LOGIN_LOCKED`、`ACCOUNT_DISABLED` 都直接用后端文案）。
- 成功：`must_change_password` 为真跳 `/change-password`；否则跳 URL 参数 `redirect`（只接受以 `/` 开头的站内路径，防止开放跳转），没有则跳 `/`。
- 已登录用户打开 `/login` 时直接跳 `/`。

### 2. 首次改密页 `/change-password`

- 照原型 `#v-changepw`：标题“请修改初始密码”、说明、新密码、确认新密码、规则清单、“确认并进入平台”按钮。
- 规则清单根据 `GET /auth/policy` 和当前用户名实时打勾：不少于 N 位；包含大小写、数字、符号中至少 M 类；不与用户名相同；“不是常见弱密码”只能由后端判断，提交前不打勾，提交后若后端返回 `COMMON_PASSWORD` 则标红。
- 两次输入不一致时不允许提交。
- 调用 `change-password`（不带原密码）。成功后刷新 `/me` 缓存并跳 `/`。返回 `WEAK_PASSWORD` 时把 `detail.reasons` 对应的规则标红。
- 页面右上角提供“退出登录”（补充：用户不想改密时可以退出）。

### 3. 个人中心 `/profile`

- 照原型 `#v-profile` 两张卡片：
  - 基本信息：用户名、所属组织、角色只读（提示“用户名、所属组织、角色由管理员维护”）；姓名、邮箱、手机可改，保存调用 `PATCH /me`。
  - 修改密码：原密码、新密码、确认新密码，规则清单同上；说明文字“修改后当前页面保持登录；其他设备上的登录最迟 N 分钟后失效。”（N 取 `access_token_minutes`）。成功后清空表单并提示“密码已修改”。

### 4. “我的应用”占位页 `/my-apps`

- 用 P1-02 的 ChatLayout。标题“我的应用”，说明“你能使用的、已发布的应用。”
- 第一期还没有应用：显示 Empty“暂无可用的应用”（补充）。第四期替换为真实列表。

### 5. 规则清单组件

`PasswordRules`：输入密码、用户名、策略、后端返回的原因代码，输出每条规则的状态。逻辑写成纯函数 `evaluatePassword(password, username, policy)`，便于测试。

### 和卡片不一致 / 自己补充的地方

1. 卡片“文件”一节只列了页面和 `PasswordRules`，但页面要调接口，额外新建了 `frontend/src/api/auth.ts`；`frontend/vitest.setup.ts` 加了 matchMedia 兜底（两者都是页面能跑/能测的最小补充）。
2. 页面测试用 `vi.mock` 模拟 `api/auth`、`api/me`。原因：`api/client.ts` 的 `baseUrl: ""` 让 openapi-fetch 在 jsdom 里生成相对 URL 的 `Request`，Node 的 `Request` 解析相对 URL 会抛错；不动共用的 `client.ts`，改为在测试里模拟接口层。建议后续单独一张卡把 `baseUrl` 改成 `window.location.origin`（生产同源，行为不变），这样页面测试可以直接 mock `fetch`。
3. `LoginPage` 已登录判断用 `useOptionalMe`（直接 fetch，401 返回 null），避免登录页触发刷新失败后的跳转覆盖 `redirect` 参数。
4. `safeRedirect` 除 `//` 外还拒绝 `/\` 开头的路径（浏览器可能当协议相对地址处理）。
5. 改密/个人中心未加载到策略时用默认策略（8 位、3 类）渲染规则文案，策略到达后自动更新。
6. 联调时发现 `ChangePasswordPage.test.tsx` 的“两次输入不一致时不提交”用例在高负载（2 核、load 7+）下偶发超时：该断言用 `findByText`（默认 1s），antd 表单异步校验完成时已超时。把这一条的 waitFor 超时放宽到 10s，断言内容不变；修复后重跑 `make frontend-check` 全绿（lint/typecheck/test/build）。
