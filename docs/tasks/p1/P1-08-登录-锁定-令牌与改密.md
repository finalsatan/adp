## 要做

### 1. 登录 `POST /api/v1/auth/login`

1. 用户名去掉首尾空格并转小写（技术方案 8.1：锁定和计数也用小写后的用户名）。
2. 取来源 IP（P1-06 的取法）。若 Redis 存在 `login_lock:{username}:{ip}` → 429 `LOGIN_LOCKED`，消息中的分钟数取系统设置 `login.lock_minutes`；记审计 failure（detail `{"reason": "locked"}`）。
3. 查用户。用户不存在时对 `DUMMY_HASH` 做一次 verify，然后按“密码错误”处理。
4. 密码错误（或用户不存在）：
   - `INCR login_fail:{username}:{ip}`，第一次时设过期 `lock_minutes` 分钟。
   - 计数达到 `login.lock_threshold` 时：写 `login_lock:{username}:{ip}`（过期 `lock_minutes` 分钟），`SADD login_locked:{username} {ip}` 并设同样的过期（用户列表据此显示“已锁定”）。
   - 返回 401 `INVALID_CREDENTIALS`“用户名或密码错误”，不返回剩余次数。
   - 记审计 failure（detail `{"reason": "wrong_password"}` 或 `"no_such_user"`）。
5. 密码正确但用户已停用 → 403 `ACCOUNT_DISABLED`（补充），记审计 failure，不计失败次数。
6. 成功：
   - 删除该 IP 的 `login_fail` 键（只删这个 IP 的）。
   - 新建 session_id（uuid4 hex），签发访问令牌（`pwc` = `must_change_password`，有效期 `session.access_minutes`）和刷新令牌（有效期 `session.refresh_days`），refresh_tokens 插入一行（存哈希、token_version、ip、user_agent）。
   - 更新 `last_login_at`。
   - 设置 Cookie：`adp_at`（路径 `/api`，max-age 为访问令牌有效期）、`adp_rt`（路径 `/api/v1/auth/refresh`，max-age 为刷新令牌有效期）；HttpOnly、SameSite=Strict、Secure 取配置。
   - 返回 `{must_change_password}`，记审计 success。
- 登录的审计：对象为空；操作人用 `record(..., actor=...)` 传入：用户存在时为该用户及其组织，不存在时 actor_id 为空、actor_name 为输入的用户名。

### 2. 刷新 `POST /api/v1/auth/refresh`

1. 读 Cookie `adp_rt`，没有 → 401 `REFRESH_INVALID`。
2. 在一个事务里按哈希查出这行并加行锁（`SELECT ... FOR UPDATE`）。找不到 → 401。
3. 已作废（revoked_at 不为空）：
   - Redis 有 `rt_grace:{旧哈希}`（30 秒内）：取出其中缓存的新刷新令牌原文，重新签发访问令牌，再次设置两个 Cookie，返回成功（技术方案 8.1：多个标签页同时刷新时不互相踢下线）。
   - 没有：视为令牌被盗用，作废该 session_id 下全部刷新令牌，返回 401，并清除 Cookie。
4. 已过期 → 401。
5. 查用户：已停用，或 token_version 与这行记录的不一致 → 401。
6. 正常：生成新刷新令牌（同一 session_id）并插入；旧的写 revoked_at；把新令牌原文写入 `rt_grace:{旧哈希}`（30 秒过期），**在提交事务之前写**；提交；签发新的访问令牌；设置 Cookie。
- 失败时都清除两个 Cookie。

### 3. 登出 `POST /api/v1/auth/logout`

- 读 `adp_at`，用 `decode_access_token(verify_exp=False)` 取 sid（过期的令牌也照样处理，补充；签名不对时忽略），作废该 session_id 下全部刷新令牌。
- 清除两个 Cookie（Set-Cookie 时路径要与设置时一致，否则清不掉）。返回 204。不需要读刷新令牌 Cookie（它只发往刷新接口）。

### 4. 改密 `POST /api/v1/auth/change-password`（允许待改密）

- 令牌 `pwc=true` 时不需要原密码；否则 `old_password` 必填，错误返回 400 `WRONG_OLD_PASSWORD`。
- 新密码按当前策略校验，不通过返回 422 `WEAK_PASSWORD`，`detail.reasons` 为原因代码列表。文档没有“新密码不能与旧密码相同”这条规则，不要加。
- 成功：更新密码哈希，`must_change_password=false`，`token_version + 1`，作废该用户全部刷新令牌；`bump_perm_version`；然后为**当前会话**签发新的访问令牌（`pwc=false`、新 tv）和刷新令牌（沿用当前 session_id），设置 Cookie（技术方案 8.1：当前页面不用重新登录，其他会话的刷新令牌作废）。
- 记审计 `auth.change_password`（补充），对象为本人。

### 5. 密码策略 `GET /api/v1/auth/policy`（允许待改密）

返回 `{password_min_length, password_min_classes, access_token_minutes}`，取自系统设置。

### 6. 管理员解锁要用的函数

在 `app/auth/lockout.py` 中提供 `is_locked(redis, username) -> bool`（`login_locked:{username}` 存在且非空）和 `unlock(redis, username)`（删除该集合，以及集合中每个 IP 对应的 `login_lock:` 和 `login_fail:` 键）。P1-11 的用户列表和解锁接口调用它们。不要用 `KEYS` 或 `SCAN` 按模式查键（技术方案 8.1）。

## 验收标准

- [ ] 测试 `test_login.py`：
  - 同一用户名、同一 IP 连续失败 5 次后锁定，第 6 次即使密码正确也返回 429；换一个 IP（`X-Real-IP`）可以正常登录。
  - 用户名改成大写、首尾加空格，与原用户名共用失败计数和锁定。
  - 伪造 `X-Forwarded-For` 不影响计数（计数仍按 `X-Real-IP`）。
  - 把锁定时长设为 1 分钟，用 Redis 键的 TTL 验证到期自动解锁（不要真的等，检查 TTL 即可），以及调用 `unlock` 后立即能登录。
  - 不存在的用户名和密码错误返回相同的状态码、code、message。
  - 停用用户输对密码返回 403 `ACCOUNT_DISABLED`；输错仍返回 `INVALID_CREDENTIALS`。
  - 成功后 Cookie 的路径、HttpOnly、SameSite 正确；需改密用户登录后返回 `must_change_password=true`。
  - 修改系统设置的锁定次数为 3 后，第 3 次失败即锁定。
  - 每次登录成功、失败都有一条审计。
- [ ] 测试 `test_refresh.py`：正常轮换（旧令牌作废、新令牌可用）；30 秒宽限期内用旧令牌拿到的新刷新令牌与第一次相同；宽限期外（删除 `rt_grace` 键模拟）复用旧令牌返回 401，且该 session 的全部刷新令牌被作废；两个请求并发用同一个旧令牌刷新，最终数据库里该 session 只有一个未作废的令牌；用户停用后刷新返回 401；token_version 变化后刷新返回 401；登出后刷新返回 401；用过期的访问令牌登出也能作废刷新令牌。
- [ ] 测试 `test_change_password.py`：待改密时访问其他接口返回 403，改密成功后用响应里新设置的 Cookie 立即能访问其他接口（技术方案 13.2）；非待改密时不带原密码返回 422、原密码错误返回 400；四种弱密码各返回对应原因；改密后该用户其他会话的刷新令牌失效、当前会话的新刷新令牌可用。
- [ ] `make backend-lint backend-test` 通过。

## 注意

- 刷新时必须加行锁，否则两个并发请求会各自签发出一个新令牌。
- 设置和清除 Cookie 的路径要一致；测试里检查 Set-Cookie 头。
