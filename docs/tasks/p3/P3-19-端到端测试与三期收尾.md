### 验收复跑：不稳定的原因与修复（2026-10-26）

调度方在 2 核 3.6G、load≈3 的机器上复跑两次都没通过：第一次 phase2 第 1 条和 phase3 第 1 条都卡在“测试连通”（等 15 秒没出现“✓ 连通成功”），第二次 phase1 第 7 条审计日志点“解锁用户”超时 90 秒。排查到四处相互叠加的原因，都做了修复（产品侧的 10 秒连通超时未改，见“依据”）：

1. **e2e 的 Celery broker 用了 Redis 13，`e2e-prepare.sh` 会清它**：调度方的后端测试也用 13 号库，每次 prepare 清库会打乱对方，间接把机器负载顶上去。改成 Redis 10（避开 12~15），prepare 只清 12 和 10。
2. **连通测试首次调用超过产品 10 秒超时**：本地假模型服务（9999）在 phase1 的约 90 秒里完全空闲，内存紧张时会被换出；phase2 第一次“测试连通”要把它换回来，可能超过需求 3.4 的 10 秒。实测：预热后首次调用 0.94s、后续约 20ms；冷启/换出后会明显变慢（同一机器 4 个 CPU 压力进程下仍快，所以不是纯 CPU 瓶颈，而是内存/换页）。产品超时不动，在测试侧加 `warmUpFakeModel`（点“测试连通”前先打一次假模型服务把代码页拉热）+ 失败重试一次（`expectConnectivitySuccess`）。第一次复跑时该用例耗时 34.5s，就是首次超时、重试成功的体现；第二次 17.9s，一次就过。
3. **审计日志动作下拉是 AntD 虚拟列表**：原实现只在打开时量一次 `scrollHeight`，再每 32px 滚一格等 50ms；机器慢时 React 重渲染超过 50ms，目标项没渲染出来，量到的 `maxScroll` 也可能是 0，滚动根本不动，最后 `option.click()` 空等 90 秒。改为每滚一步重新量高度、等目标项真正挂到 DOM（`waitFor`），到底后绕回顶部再滚，最多 30 步。
4. **停用知识库确认弹窗的点击会落空**：弹窗 zoom 动画期间按钮位置还在变，Playwright 的稳定性判断过了但点击落在动画中的旧坐标上（trace 里点击点 `(1290, 341)` 不在按钮上，也没发 `:disable` 请求）。改为等 `ant-zoom-enter/appear` 动画类消失再点，必要时重试一次；顺带把只取 id 的用例改成读“进入”链接的 href，不再先跳文档页再跳回列表。

修复后 `make e2e` 连续两次通过（本次，均为 `sg docker -c`）：`19 passed (4.8m)`、`19 passed (4.7m)`。

修复涉及的文件：`frontend/e2e/config.ts`（broker 库号）、`scripts/e2e-prepare.sh`（清 Redis 12/10）、`frontend/e2e/helpers.ts`（审计下拉滚动、连通预热与重试）、`frontend/e2e/tests/phase2.e2e.ts`、`frontend/e2e/tests/phase3.e2e.ts`（停用弹窗点击）。

### 部署缺陷修复：beat 调度文件权限（2026-10-26）

调度方用 docker compose 起生产栈（跳过 parser）时，`smoke.sh` 6 项和 `/readyz` 的 `storage: ok` 都正常，但 `adp-prod-beat-1` 一直重启，日志 `[Errno 13] Permission denied: celerybeat-schedule`。

原因：后端镜像以非 root 用户 `adp`（uid 10001）运行，`WORKDIR /app` 归 root，beat 默认把调度文件写在当前目录 `/app/celerybeat-schedule`，写不了。

修复（只改 `deploy/`，不用重建镜像）：

- `deploy/docker-compose.yml`：beat 命令加 `--schedule /tmp/celerybeat-schedule`（`/tmp` 对任何用户可写）。调度状态丢失只会让 beat 重启后立刻补跑 `requeue-stale` / `redispatch-queued`，这两个任务本身幂等（知识库技术方案 8.3），不影响正确性。
- 检查了 `worker` / `worker-interactive`：两者只消费队列，日志写 stderr，没有 `--logfile` / `--pidfile`，也不会写调度文件；prefork 池的共享内存用 `/dev/shm`（可写）。没有同类问题，未改。
- `deploy/smoke.sh`：RustFS 检查前先用 `docker info` 判断能不能访问 Docker。当前用户不在 docker 组（`permission denied while trying to connect to the docker API`）时直接给出提示 `请用 sg docker -c 'deploy/smoke.sh' 重新运行，或把当前用户加入 docker 组后重新登录`；能访问 Docker 时，若容器没在跑或 `/health` 不可达，失败信息带上真实原因。
- `deploy/README.md`：2.8 补 beat 调度文件位置与原因，6.3 补不在 docker 组时用 `sg docker -c` 运行 smoke.sh 的说明。
