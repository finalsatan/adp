# P3-11 向量化与索引写入、新旧两代切换

状态：待验收

## 目标

把分块按向量化模型“单次请求最多条数”分批向量化，写入每库索引表；生效时在一个事务里切换新旧两代并更新计数。重新入库期间旧分块在被替换前仍可被检索。

- P3-01 契约；P3-03 的每库索引表建表函数；X09 报告与完成记录（全文召回参数写法）

## 要做

### 0. 接入分块步骤（2026-10-25 调度方补充）

P3-10 并行开发时按调度要求没有改 `backend/app/kb/pipeline.py`，分块步骤（知识库技术方案 8.1 第 3 步）还没接进流水线。本卡先把它接上：在解析步骤（P3-09）之后调用 P3-10 导出的 `chunk_document` / `ensure_within_limit` / `write_chunks` 生成新一代分块（未生效），再接本卡的向量化与两代切换；步骤状态、进度和心跳照 8.1 写回 `documents`。测试覆盖“解析 → 分块 → 向量化 → 生效”整条链路（用 P3-09 的假解析服务和固定向量的模型）。

### 1. 分批向量化

- 向量化文本 = 标题路径（方案开启“附带标题路径”时）+ 上下文说明 + 分块内容（9.4）。按知识库向量化模型的 `embedding_batch_size` 分批，走 `app.gateway.service.embed`。
- 用量 `CallMeta`：`source='ingest'`、`source_id=doc_id`、`user_id=documents.run_by`、`org_id=run_by 当时所属组织`（技术方案 6.3、知识库技术方案 17）。
- 入库额度限流（P2-04）：`embed` 抛 `RateLimited` 时任务稍后重试，不算失败、不计自动重试次数（8.3）。
- 分批向量化用 `asyncio.gather` 控制并发（8.2 补充）。

### 2. 写索引表（11.3）

- 每库一张 `kb_index.kb_{id}`（P3-03 的建表函数），本卡写入 `entry_type='chunk'`、`chunk_id`、`doc_id`、`generation`、`active=false`、`embedding`、`title`、`body`、`keywords`。
- `body` = 上下文说明 + 分块内容；`title` 在方案开启“附带标题路径”时存标题路径（否则为空）；`keywords` 本阶段为空（分块增强第六期）。
- 维度：≤2000 用 `vector(d)`，2000–4000 用 `halfvec(d)`（P3-03 建表时按 `embedding_dim` 决定；本卡按同一规则写）。BM25 索引随写入自动更新（8.4）。

### 3. 生效与两代切换（8.4）

- 生效时在**一个事务**里：本文档旧一代的索引条目 `active=false`、新一代 `active=true`、`documents.current_generation` 改为新值、更新文档和知识库的计数（`chunk_count`，以及知识库的 `doc_count`/`chunk_count`）。
- 重新入库时写入的是新一代，`active=false`；检索只看 `active=true` 的条目，因此“重新入库期间，旧分块在被替换前仍可被检索”（需求 4.1.5）。向量索引和 BM25 索引都随事务提交生效，不需要另外同步。
- 旧一代的分块和索引条目由 maintenance 任务异步删除（P3-12 的 maintenance 任务调用本卡提供的清理函数）（补充）。
- `active` 同时包含文档和分块的启用状态：启停文档或分块时更新对应条目的 `active`（本卡提供 `set_doc_active` / `set_chunk_active`，P3-12 调用）。
- 文档处理中时，接口拒绝编辑它的解析结果和分块（8.4；第五期才有编辑，本卡不做编辑接口）。

### 4. 超长检查的第二次确认

- 向量化前对实际内容再检查一次 90% 上限（9.4 的“增强后再按实际内容检查一次”中，本阶段没有增强，但写入前仍按实际内容确认）。

### 5. 检索用的 SQL 片段

- 提供全文召回的条件常量，供 P3-13 使用：`title ||| :q::text::pdb.boost(2) OR body ||| :q::text OR keywords ||| :q::text::pdb.boost(2)`（X09 报告 6a 实测写法；知识库技术方案 11.4 原文漏了 `::text`，直接照原文会在 psycopg3 下报 `invalid typemod -1`）。

### 和卡片不一致 / 自己补充的地方

1. **P3-09 测试文件的最小同步**：见“问题”。这是把步骤 3/5/6 接进 `run_pipeline` 后必须做的；没有改 P3-09 的断言，也没有放宽任何用例。
2. **知识库计数口径（卡片只写“更新计数”）**：`knowledge_bases.doc_count` 算本库全部文档数；`chunk_count` 取各文档 `chunk_count` 之和。`documents.chunk_count` 取新代分块数。
3. **超长检查做两次**：步骤 3 分块后按 `ChunkData` 检查一次（先触发，`failed_step=3`），步骤 5 向量化前按库里的分块再检查一次（9.4）；模型没配 `embedding_max_input` 时跳过。
4. **向量化的临时错误不另起重试循环**：gateway 的 `embed` 已按 `max_retries` 重试，最终失败即标文档失败（错误码取 gateway 的 `error_code`，`temporary=retryable`）；只有 `RateLimited` 转 `RetryLater`，由任务稍后重试、不计自动重试次数（8.3）。
5. **`set_doc_active` / `set_chunk_active` 的语义（卡片没写签名）**：停用把所有代的条目置 false；启用只把当前代（`documents.current_generation`）置 true。`set_chunk_active` 启用时还要求所属文档启用。
6. **`delete_old_generations` 同时删 `chunks` 与索引条目**：卡片说 maintenance 删“旧一代的分块和索引条目”。
7. **索引表不由本卡创建**：建库时 P3-04 调 `create_index_table`；本卡测试自己建表。
8. **`keywords` 写 NULL**、`body` 不带上下文（本阶段无增强，`enhance.context` 默认 false）。
