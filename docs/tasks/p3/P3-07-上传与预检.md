## 要做

### 1. 预检 `POST /api/v1/kbs/{id:int}/documents:precheck`

输入照 P3-01（`files: [{name, size, relative_path?, sha256}]`、`folder_id?`、`schemes`）。逐个文件：

- 从扩展名取文件类型（`parser/app/filetypes.py` 的同一套代码，在 `app/kb` 里复制一份常量或引用，补充）；不支持的扩展名进 `errors`（`UNSUPPORTED_FILE_TYPE`）。
- `size` 超过系统设置 `upload.max_file_size_mb`（P3-01 已定义，默认 200）进 `errors`（`FILE_TOO_LARGE`）。
- 解析方案：`schemes[file_type]` 指定优先，其次知识库默认方案，最后该类型内置方案（P3-06 的 `resolve_scheme_id`）；没有可用方案进 `errors`（`SCHEME_UNAVAILABLE`）。
- `name_conflict`：同一知识库、同一 `folder_id`（空为未分类）下已有同名文档（P3-03 的 `NULLS NOT DISTINCT` 唯一索引）。
- `duplicate`：同一知识库内已有相同 `sha256` 的文档（需求 4.1.3：只查同一文档库）。
- `too_long`：`方案最大长度（父子分块取子块最大长度）+ 标题路径预留 100 + 上下文说明预留 100` 与 `知识库向量化模型 embedding_max_input × 90%` 比较（知识库技术方案 9.4）；返回 `estimated_tokens` 和 `limit_tokens`。
- 预检不写库、不改状态；只读。

### 2. 上传 `POST /api/v1/kbs/{id:int}/documents`

multipart（P3-01 约定）：`files[]`、`relative_paths`（与 files 一一对应，可为空串）、`folder_id?`、`schemes`（JSON 字符串：文件类型 → 方案 ID）、`resolutions`（JSON 字符串：`{name_conflict: {文件名: "replace"|"keep"}, duplicate: {文件名: "skip"|"upload"}}`）。

逐个文件：

1. 按扩展名取类型；用 `filetype` 库按文件头校验真实类型（知识库技术方案 6.4），与扩展名不符 → 422 `UNSUPPORTED_FILE_TYPE`（整批拒绝，见“注意”）。
2. 大小超过 `upload.max_file_size_mb` → 413 `FILE_TOO_LARGE`。
3. 同名 / 重复按 `resolutions` 处理：`replace` 覆盖原文档（保留元数据与所在文件夹，换新内容、新 `sha256`，状态回“排队中”，生成新 `run_id` 重新入库）；`keep` 建新文档，命名为 `原名(1).扩展名`，序号从 1 递增取第一个不冲突的（如 `报销制度.docx` → `报销制度(1).docx`）（2026-10-25 用户决定）；`skip` 跳过并记入 `skipped`。
4. 文件夹：`folder_id` 为所有文件的落点；`relative_paths` 有值时按 `mkdir -p` 在 `folder_id` 下建出目录结构并落到对应文件夹（需求 4.1.3：上传整个本地文件夹保留目录结构；同一相对目录只建一次）。
5. 建文档记录（`status=queued`、`step` 为空、`queued_at=now()`、`run_id=uuid4`、`uploaded_by=run_by=ctx.user_id`、`scheme_id`、`enabled=true`），flush 拿到 `id`。
6. 流式写对象存储 `kb/{kb_id}/docs/{doc_id}/original.{ext}`（知识库技术方案 11.1）：一边上传一边算 SHA-256（用一个包装的只读文件对象，`Storage.upload_stream` 读它时顺带更新哈希，补充），不把整个文件读进内存。写库 `size`、`sha256`。
7. 元数据：不解析文档内容，不设元数据（P3-12 再设）。

全部处理完提交事务，然后投递调度：`celery_app.send_task("app.worker.tasks.dispatch_kb", args=[kb_id], queue="ingest")`（P3-08 的任务 `dispatch_kb`；用 `send_task` 按名字投递，避免和 P3-08 互相 import）。上传后直接进入入库流程，不中途等确认（需求 4.1.3）。

### 3. 快照与计数

- `knowledge_bases.doc_count` 在文档生效时更新（知识库技术方案 8.1 步骤 6，P3-11），上传时不动。

## 注意

- 多文件上传里有一个文件类型 / 大小不合格时，整批拒绝（HTTP 422 / 413），不做“部分成功”（补充，原型是“开始上传”一次性动作）；同名 / 重复是用户已经确认过的处理方式，按 `resolutions` 逐文件执行。
- 投递任务用 P3-08 的任务名 `app.worker.tasks.dispatch_kb`；P3-08 若不改任务名，Celery 默认就用这个模块路径。
- 系统设置的 `upload` 分组（含 `max_file_size_mb`）由 P3-01 契约定义，本卡只读取，不再改 `settings/schemas.py`。
- 流式上传不能先读进内存；SHA-256 与上传同一次读写完成。nginx 的 `client_max_body_size`、`proxy_request_buffering off` 在 P3-02 已配好。
- `sha256` 是 64 位小写十六进制；`replace` 覆盖时旧对象键不变（同一 `doc_id`），直接覆盖。

### 和卡片不一致 / 自己补充的地方

1. **`DocumentOut` 没有 `sha256` 字段**（P3-01 契约）：验收标准说“`size` / `sha256` 与源文件一致”，`sha256` 只能查数据库验证，测试里直接读 `documents.sha256`。
2. **`dispatch_kb` 只在有文档落库时投递，且投递失败不回滚上传**：全部被 `skip` 时没有排队文档，不投递；broker 临时不可用时只记日志，文档已落库，等 P3-08 的 beat 补发。
3. **`replace` 清 `parse_snapshot` / `chunk_snapshot` 并重置 `page_count` / `chunk_count`**：卡片只写“换新内容、新 `sha256`、状态回排队中、生成新 `run_id`”；不清旧快照会让 P3-09 的流水线误用旧方案，旧计数也不应保留。
4. **`edited` 在返回里固定 `false`**：`DocumentOut.edited` 表示解析结果 / 分块是否有人工修改，P3-14 才实现；上传的新文档没有解析产物，替换场景可能残留旧的 `edited` 解析行，等 P3-14 / P3-12 处理。
5. **`filetype` 认不出（txt / csv / md / html）时不拒绝**：这些类型没有文件头特征，按“能认出且不符才拒”实现（补充）。
6. **上传的 `relative_paths` 目录部分用 `posixpath.dirname`**：兼容浏览器 `webkitRelativePath`（含文件名），空串表示直接落在 `folder_id` 下。
