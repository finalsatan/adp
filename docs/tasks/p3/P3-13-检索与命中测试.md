## 要做

### 1. 检索服务 `app/kb/retrieval.py`

检索分成两段：“召回并融合”（下面第 1–6 步）和“重排与扩展”（第 7–9 步）。命中测试连续调用两段；第四期的问答应用在两段之间判断问答库能否直接回答（本卡不做问答库）。检索是服务内函数，供第四期调用，不单独对外暴露（知识库技术方案 16）。

1. 确定参与的知识库和检索配置（知识库默认值 `retrieval_config`，被调用方覆盖）。知识库已停用时跳过该库，若没有可检索的知识库则返回空结果（2026-10-25 用户决定）；向量化模型已停用时返回“模型不可用”（需求 3.4、4.1.7）。
2. 把元数据、文件夹条件转成文档子查询：前端提交一层“且 / 或”多条件（不嵌套，2026-10-25 用户决定），后端按字段类型转成对 `documents.metadata`（jsonb）的 SQLAlchemy 表达式；文件夹按物化路径前缀匹配（含下级）；停用的文档和分块通过索引条目的 `active` 排除（12.3）。
3. 用各知识库的向量化模型把问题向量化；同一模型在一次请求内只调一次，调用方可以传入查询向量缓存（第四期问答库和文档库分两次检索时共用）。
4. 每个知识库并行执行两路召回：
   - 向量召回（pgvector）：`ORDER BY embedding <=> :v`，`SET LOCAL hnsw.ef_search` 取召回数的 2 倍以上；有元数据或文件夹过滤时开启 `hnsw.iterative_scan`，避免过滤后结果不足（11.3）。
   - 全文召回（ParadeDB BM25）：`title ||| :q::text::pdb.boost(2) OR body ||| :q::text OR keywords ||| :q::text::pdb.boost(2)`，加 `active` 和文档过滤条件，按 `pdb.score(id)` 降序。**参数必须写 `:q::text`**：同一个占位符同时用于带 `::pdb.boost(...)` 和不带 boost 的位置时，服务端参数类型推断会失败（X09 报告 6a；知识库技术方案 11.4 原文漏了 `::text`）。
   - 各取召回数的 3 倍条目（同一分块可能有多条索引条目，留去重余量）。
5. 条目按分块去重，每路取该分块的最高分；对只出现在一路的候选，补算另一路的分数。
6. 计算融合分（12.2）：
   - 向量分 = 余弦相似度（1 − 余弦距离）。
   - 全文的关键词分 = 条目文字中出现的查询词权重之和 ÷ 全部查询词权重之和（0–1），用 SQL 的 `strpos` 判断查询词是否出现在 `title`、`body`、`keywords` 中。
   - 混合 = 向量权重 × 向量分 + 全文权重 × 关键词分，两个权重之和为 1。
   - 查询词的切分和权重封装在 `QueryTerms` 接口后面（11.4）：在数据库里用同一个分词器切出问题的原词 `SELECT :q::pdb.jieba('search_mode=false')::text[]`，去掉停用词（停用词表随代码发布），每个词的权重取 jieba 自带 IDF 词典中的值，词典里没有的词取中位数。
   - 不直接用 BM25 分数参与融合：按本次结果最高分归一化会让第一名总接近满分、阈值失去意义（K5）。
7. 阈值（需求 4.1.7、12.2）：开启重排时作用于重排分数，否则作用于融合分；只用一路时即该路分数，只用全文时按 BM25 排序、阈值作用于关键词分。
8. 重排：对前 Top K 个候选调用 `app.gateway.service.rerank`（文本为标题路径 + 内容），保留指定条数；用量 `source='kb_hit_test'`，`source_id` 为空，发起人为当前用户。
9. 返回分块内容、所属文档、`positions`（知识库技术方案 13）、各阶段分数和耗时。

- 父子分块：子块替换为父块、同一父块只保留一个（第五期才有父子分块，本卡预留这一步的位置，普通分块直接跳过）。

### 2. 命中测试接口 `POST /api/v1/kbs/{kb}/hit-test`（知识库“查看”权限）

- 请求：问题、临时检索配置（覆盖知识库默认值）、调试开关；结构以 P3-01 契约为准。

- 点击结果用的位置数据来自 `chunks.positions`（供 P3-14 原文读取和 P3-18 预览）。
- 文档库与问答库共用命中测试页面（需求 4.1.7）；问答库是第六期，本卡只支持文档库。

### 缺陷修复（2026-10-25，P3-17 联调发现）

#### 现象与根因

- 现象：P3-17 联调时命中测试首次请求 500，ParadeDB 报
  `stored tokenizer options could not be found`（`paradedb._typmod_cache has no entry with id 3`），
  重启后端后恢复（P3-17 完成记录“环境问题”）。
- 实测根因（与本卡原推测的“别的库索引表被删除/重建导致缓存失效”不同）：
  `build_query_terms` 用 `SELECT :q::text::pdb.jieba('search_mode=false')::text[]` 切查询词。
  ParadeDB 把 `pdb.jieba` 的切词选项写进 `paradedb._typmod_cache` 表（id 3 即
  `{search_mode=false}`），**这个写入随当前事务**；而 `build_query_terms` 的会话只读、不提交，
  首次解析时插入的行随会话关闭回滚。asyncpg 把首次解析的预编译语句缓存在连接池的连接上，
  计划里固化了类型修饰 id 3；下一次执行复用该语句时 `load_typmod(3)` 查不到行（表里没有、
  本后端内存缓存也在事务回滚时被清），就报这个错。错误只在进程内的预编译语句缓存里，
  所以重启后端恢复。
- 复现：同一连接上“解析 `pdb.jieba(<未用过的选项>)` → 回滚 → 复用同一条预编译语句”，
  稳定复现同样的 `InternalError`；用 `adp_e2e` 验证过，删掉别的知识库索引表本身**不会**清
  `_typmod_cache`（该表按选项全局共享、不随 DROP 清理），所以 DROP 只是同期的干扰因素。
  `paradedb._typmod_cache` 当前被 `adp_app` / `adp_migrator` 只读，测试无法删行，因此复现用例
  改用“没用过的 jieba 选项”来保证行初始不存在。

#### 修复与取舍

- 修复：`app/core/db.py` 的 `create_engine` 加
  `connect_args={"prepared_statement_cache_size": 0}`，关闭 SQLAlchemy asyncpg 方言的预编译语句
  缓存（即每条语句都重新 Parse/Describe）。重新解析时 ParadeDB 会重新写入类型修饰行（在当前
  事务里可见），执行就不再查不到。
- 为什么选“关缓存”而不是“回滚后重试”：SQLAlchemy 文档明确说明这类错误无法在方言层重试
  （PostgreSQL 事务已被标记失败），重试要自己识别错误串并在新连接上重跑，复杂且难覆盖
  “行没了但错误形态变化”的情况。
- 为什么选全局而不是只对检索：运行期会建/删每库索引表（API 进程和 Celery worker 都可能发 DDL），
  这些 DDL 用 `text()` 发出，SQLAlchemy 不认作 DDL、不会自动失效预编译语句缓存；全局关缓存能
  一并挡掉这一类“DDL 后旧语句失效”的问题，也避免以后别处再用 `pdb.jieba(...)` 时重犯。检索
  只有一条 `build_query_terms` 会碰类型修饰，但只对检索关需要再建一个引擎和连接池，改动和
  资源都更大。
- 代价（本机 Docker 实测，1 个简单参数化 `SELECT` 各 1000 次，预热 50 次）：
  `cache=100` 约 514–526 µs/次，`cache=0` 约 1130–1299 µs/次，约 2 倍；绝对增量约 0.6–0.8 ms/条。
  平台当前规模（内部控制台、非高 QPS）可接受，先保正确性；以后若成为瓶颈，可改为只给检索
  路径单独建一个 `prepared_statement_cache_size=0` 的引擎。
- 测试新增（`backend/tests/kb/test_retrieval.py`）：
  - `test_query_terms_typmod_cache_survives_rollback`：确定性复现，修复前报
    `InternalError: stored tokenizer options could not be found`，修复后通过。
  - `test_retrieval_after_other_kb_index_drop`：建库 A、B 并写索引，检索 A → 删 B 的索引表 →
    再检索 A（联调场景回归）。
- 未改 `retrieval.py` 本身；`backend/tests/kb/test_retrieval.py` 只加了两个用例。
