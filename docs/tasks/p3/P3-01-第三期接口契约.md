# P3-01 第三期接口契约

状态：待开始
前置：第二期全部（P2-12 已验收）

## 目标

写出第三期全部接口的请求、返回结构和路由签名（实现留空返回 501），生成 OpenAPI 和前端类型。之后后端 P3-02～P3-14 与前端 P3-15～P3-18 并行，前端先对着类型开发。

## 要做

### 1. 枚举（放 `app/kb/schemas.py`，中文名放代码里的字典）

- `KbKind`：`doc`（文档库）、`qa`（问答库）。
- `FileType`：`pdf`、`word`、`ppt`、`excel`、`csv`、`markdown`、`txt`、`html`、`epub`、`ofd`、`image`；代码与解析服务 `parser/app/filetypes.py` 的 `FILE_TYPES` 一致，中文名放 `FILE_TYPE_LABELS`。
- `DocumentStatus`：`queued`（排队中）、`parsing`（解析中）、`chunking`（分块中）、`enhancing`（增强中）、`embedding`（向量化中）、`done`（已完成）、`failed`（失败）（知识库技术方案 8.1、需求 4.1.3）。
- `ParseEngine`：`pypdfium`、`docling`、`markitdown`、`mineru`、`paddleocr`、`builtin`（内置文本 / 表格解析共用一个 `builtin` 引擎，补充）。
- `ScanMode`：`auto`（逐页自动判断）、`all`（全部按扫描件处理）。
- `MineruTier`：`flash`（快速）、`basic`（基础）、`standard`（标准）、`advanced`（高级）。
- `ChunkMode`：`auto`（自动）、`heading`（按标题）、`length`（按长度）、`rule`（按规则）、`page`（按页）、`whole`（整篇）、`semantic`（语义）。
- `MetadataFieldType`：`text`、`number`、`date`、`select`。
- `ReparseMode`：`reparse`（重新解析）、`rechunk`（仅重新分块）。
- `RetrievalMode`：`vector`（向量）、`fulltext`（全文）、`hybrid`（混合）。
- `DocumentBatchAction`：`set_metadata`、`move`、`enable`、`disable`、`delete`、`retry`、`reparse`。
- 用量来源复用第二期的 `UsageSource`（`ingest`、`kb_hit_test`、`scheme_trial` 已定义）。

### 2. 入库方案配置结构（知识库技术方案 14）

用 Pydantic 定义 `SchemeConfig`（判别联合，不同分块方式只接受各自参数），字段照知识库技术方案 14 的 JSON：

- `schema_version`（默认 1）、`file_type`。
- `parse`：`engine`；`scan_mode?`（Docling）；`mineru_tier?`（MinerU，PDF、图片）；`preprocess: {merge_whitespace, remove_header_footer, remove_links_emails}`。
- `table`：`rows_per_chunk`（默认 20）、`header_row`（默认 1）、`sheets`（`all` 或工作表名列表，仅 Excel）。
- `chunk`：`mode`（判别字段）；`max_tokens`、`min_tokens`、`title_path`（默认 true）、`parent_child: {enabled, parent_max_tokens, child_separators, child_max_tokens, child_overlap_tokens}`；按方式各自的参数：`heading_level`（按标题）、`separators`（按长度）、`rules`（按规则）、`pages_per_chunk`（按页）、`sensitivity`（语义）。
- `enhance`：`chat_model_id`、`context`、`questions: {enabled, count}`、`summary`、`keywords`、`table_summary`。

参数取值范围照需求 4.1.4 的括号默认值；解析引擎与文件类型的对应关系照需求 4.1.4 的表（校验在 P3-06 实现）。

### 3. 权限码

- 内置入库方案任何人只读（知识库技术方案 17）。

### 6. 系统设置：上传与解析分组

P1-03 说“上传与解析”这组到第三期再加（需求 10.8）。在 `app/settings/schemas.py`、`app/settings/service.py` 加 `upload` 分组，并加进 `SettingsOut` / `SettingsPatch` / `PlatformSettings`：

- `max_file_size_mb`（默认 200，1–2048）：单个文件大小上限（P3-07 用）。
- `parse_concurrency`（默认 4，1–32）：全局同时解析的文档数（P3-08 用）。
- `kb_parse_concurrency`（默认 2，1–16）：每个知识库最多占用的解析并发（P3-08 用）。

P3-08 的卡片写“分组键与字段名以 P3-01 契约为准”，这里定为 `upload` + 上面三个字段。

### 7. 路由占位与注册

- 每个路由函数只写签名、`response_model`、`status_code`、`dependencies`（权限依赖先用 P1-03 的 `require_perm` 占位；资源级判断留给实现卡），函数体 `raise NotImplementedError`，并写中文 `summary`。

## 问题

- 已定（2026-10-25）：解析结果接口返回 Markdown + 有序元素列表（`ref` / 类型 / 文本），PDF 高亮用检索结果里的 `positions`。知识库技术方案 13 只写了 Word 用“元素引用”，没有规定接口返回什么，本卡按此写。
- 已定（2026-10-25）：上传预检的 `sha256` 由前端在浏览器里计算（Web Crypto）后随预检请求提交。知识库技术方案 8.1 说上传时“边写边算 SHA-256”，但预检在写对象存储之前就要判断内容重复，因此预检阶段由浏览器算好哈希。
- 已定（2026-10-25）：`GET /kbs/{id}/refs` 保留，第三期返回空列表（没有应用）。知识库技术方案 16 没列这个接口，但需求 4.1.2 和原型 `#m-kbstop` 要“删除前列出引用它的应用”，P3-15 也按这个接口写。
