# P3-09 流水线转换与解析步骤

状态：待开始
前置：P3-08
被依赖：P3-11

## 目标

实现入库流水线的步骤 1（转换）和步骤 2（解析）：提交解析服务作业、轮询等待、进度与心跳、失败重试、取消；同时新建本地假解析服务，供测试、联调和 P3-19 端到端使用。

## 依据

- 知识库技术方案 8.1 的步骤 1、2、8.3（失败、重试与取消）、6.1（**作业接口逐条照做**）、6.2（转换与引擎）、6.3（超时与保护参数）、7、11.1（对象存储路径）、11.2（document_parses、parse_records）、19.3（解析测试要点）
- 需求 4.1.3（旧格式转换、预览转换失败不影响入库）、4.1.4（解析设置）、4.1.8（预览 PDF）
- P3-01 契约；解析服务 X01 的作业接口（假服务按它实现）；P3-02 的对象存储封装与 `PARSER_URL` / `PARSER_TOKEN`

## 要做

### 1. 解析服务客户端的轮询与重试

- `app/kb/parser_client.py` 的请求封装由 P3-02 建（2026-10-25 用户决定），本卡在其上补流水线需要的等待与错误处理：`submit_job` / `get_job` / `cancel_job` / `list_engines` / `convert` 带 `Authorization: Bearer {PARSER_TOKEN}`（知识库技术方案 6.1）。
- 等待用轮询（补充：间隔 2 秒），把 `progress.done_pages/total_pages` 写回 `documents.progress` 并更新 `heartbeat_at`。
- 查询作业返回 404 时按 6.1 重新提交（解析服务重启后作业只在内存、会丢）。
- 客户端等待超过解析服务作业超时（默认 30 分钟）时按临时错误处理（6.3、补充）。

### 2. 步骤 1 转换（`app/kb/pipeline.py`）

- 按方案快照里的引擎判断：选 Docling、MarkItDown、内置表格解析时，doc、rtf、odt、ppt、odp、xls、ods 先调 `POST /v1/convert` 转成 docx、pptx、xlsx，写 `kb/{kb_id}/docs/{doc_id}/converted.{docx|pptx|xlsx}`（8.1、11.1；K7）。
- Word、PPT 类另转一份预览 PDF 写 `kb/{kb_id}/docs/{doc_id}/preview.pdf`；**预览转换失败只记录日志，不让文档失败**（需求 4.1.8）。
- 真实格式转换依赖 X02（LibreOffice + unoserver），当前搁置（用户决定）：本卡用假解析服务的 `/v1/convert` 走通调用与落盘，真实转换效果待 X02 恢复后验证。

### 3. 步骤 2 解析

- 提交作业：`source_key`（原文件或转换后文件的对象存储路径）、`file_type`、`ext`、`engine`、`engine_params`（方案快照的解析设置）、`preprocess`、`table`、`output_prefix=kb/{kb_id}/docs/{doc_id}/parsed/original`、`images_prefix=kb/{kb_id}/docs/{doc_id}/images`、`remote`（MinerU 标准/高级档、PaddleOCR 的地址与密钥从系统设置取，第六期；本卡传空或按 P3-06 的引擎列表）。
- 成功结果写：
  - `document_parses`：`kind='original'`、`doc_key`、`md_key`、`engine`、`engine_version`、`pages`、`ocr_pages`、`created_by=run_by`。
  - `parse_records`：一条（`engine`、`pages`、`ocr_pages`、`duration_ms`、`ok=true`、`error_code=null`）。
  - `documents.page_count`、`status`、`step`、`progress`、`heartbeat_at`。
- 失败：临时错误（网络、超时、5xx、云端引擎 429、解析服务作业失败的临时码）自动重试 3 次，间隔指数增长；业务性错误（文件已损坏或加密、超过页数上限、引擎未配置、不支持的类型等）立即失败。失败原因面向用户书写、用中文（8.3）；写 `failed_step`、`error_code`、`error_message`。解析服务 404 重新提交不算业务性失败。
- 取消：每步开始前调 P3-08 的 `check_run_id`；`run_id` 变化时 `DELETE /v1/jobs/{id}` 取消解析服务上的作业并退出（8.3）。
- 每一步都写回 `documents` 的当前步骤、进度和心跳时间（8.1）。

### 4. 本地假解析服务 `backend/tests/fake_parser/`

- 一个小的 FastAPI 应用，实现解析服务 X01 已实现的作业接口：`POST /v1/jobs`、`GET /v1/jobs/{id}`、`DELETE /v1/jobs/{id}`、`GET /v1/engines`、`POST /v1/convert`、`GET /healthz`；除 `/healthz` 外用 Bearer 认证。
- 返回固定的统一解析结果：至少两套固定的 DoclingDocument 样例，一套 PDF（含页码、坐标、表格）、一套 Word（含元素引用如 `#/texts/12`，按知识库技术方案 7、13），导出 `doc.json` 和 `doc.md`，图片写 `images/`，落到请求的 `output_prefix` / `images_prefix`（对象存储用与主服务同一套 S3 配置；测试里可用 P3-02 的测试实现或 RustFS 开发容器）。按请求的 `file_type`/`ext` 返回对应样例，供 P3-18 的 PDF 高亮与 Word 段落定位测试和 P3-19 端到端使用。
- 请求参数可控制行为（补充）：按页报进度、延迟、返回指定错误码、`/v1/convert` 成功或失败，便于测试重试、取消、预览转换失败不影响入库。
- 只用于测试和联调，不进生产镜像。`make fake-parser` 启动（补充：默认端口 59010，可用 `FAKE_PARSER_PORT` 覆盖；避开 X01 已用的解析服务 59001 和 RustFS 控制台 59002）。

### 5. 对象存储

- 用 P3-02 的对象存储封装读写原文件、转换后文件、预览 PDF、解析结果和图片；路径按知识库技术方案 11.1。

## 验收标准

- [ ] 测试（连真实 PostgreSQL、Redis，用假解析服务）：
  - 解析成功：`document_parses` 有 `kind='original'` 一行、`parse_records` 一条 `ok=true`、`documents` 的 `page_count`/`step`/`status` 正确，对象存储里有 `doc.json`、`doc.md`、`images/`。
  - 临时错误自动重试 3 次后成功；仍失败时文档失败、`failed_step=2`、`error_message` 为面向用户的中文说明。
  - 业务性错误（如文件损坏）不重试，立即失败。
  - 解析服务返回 404（模拟重启）时重新提交，最终成功。
  - 取消：`run_id` 变化后任务退出，并调用 `DELETE /v1/jobs/{id}`。
  - 预览转换失败（`/v1/convert` 报错）时文档仍成功，只记录日志。
  - 转换成功后文件落到 `converted.*`；Word、PPT 类落到 `preview.pdf`。
- [ ] `make backend-lint backend-test` 通过；`make fake-parser` 能启动、`/healthz` 正常。
- [ ] 凡依赖 Docling 的效果（如 Word 元素引用定位）只用假解析服务的固定样例测试，并在完成记录里写明真实效果待 Docling 接入后验证。
