# 开发约定（按任务卡写代码时必读）

这份约定写给按任务卡开发的编程智能体。任务卡在 `docs/tasks/` 下，总表见 `docs/tasks/README.md`。

## 1. 一次只做一张卡

1. 读卡片全文。卡片“前置”里的任务必须已经是“待验收”或“已验收”，否则停下来报告。
2. 读卡片“依据”里列出的文档章节。文档是 HTML，**不要整份读**，用工具按章节取：
   - `python3 docs/tasks/tools/doc.py tech 8.1`：技术方案 v0.1 第 8.1 节（`prd` 需求文档、`kb` 知识库技术方案、`app` 应用技术方案）
   - `python3 docs/tasks/tools/proto.py v-users --text`：原型中的一个页面（`#v-xxx`）、抽屉（`#d-xxx`）或弹窗（`#m-xxx`）；去掉 `--text` 看 HTML 结构
   - 卡片里写“技术方案 8.1”指技术方案 v0.1（`tech`）；“知识库技术方案”（`kb`）、“应用技术方案”（`app`）、“需求”（`prd`）都写全称。
3. 把卡片顶部的“状态”改为“进行中”，开始开发。
4. 做完后跑卡片“验收标准”里的全部命令，全部通过后填写卡片末尾的“完成记录”，把状态改为“待验收”，然后提交（见第 6 节）。

## 2. 以什么为准，不清楚时怎么办

- 依据的优先级：需求文档 v0.3 和三份技术方案 > 任务卡 > 你自己的判断。卡片是从文档摘出来的，摘录和文档冲突时以文档为准，并在卡片“问题”一节记下冲突。
- 卡片里标了“（补充）”的内容是拆任务时补的实现细节，文档里没有，照卡片做即可。
- 文档和卡片都没写、或者有歧义时，**不要自己编需求**：
  - 影响接口字段、表结构、权限判断、安全、用户能看到的行为（文案、流程）的：在卡片“问题”一节写清楚问题和你建议的做法，**停下来等回复**。
  - 纯内部实现细节（函数怎么拆、变量名、私有工具函数）：选最简单的做法，在“完成记录”里提一句。
- 不许修改 `docs/prd/`、`docs/tech/`、`docs/adr/`、`GLOSSARY.md`。只能改自己这张卡片的“状态”“问题”“完成记录”。
- 不要动 `apps/`、`repos/`、根目录的 `node_modules/`、`test-results/`：前三个是旧分支的遗留产物和参考实现，不是本项目代码。`repos/` 里的开源项目只在卡片要求时作参考阅读。

## 3. 只改卡片范围内的东西

- 只新建、修改卡片“文件”一节列出的文件和目录。确实需要改别处（比如给共用的错误码表加一项），改动要最小，并在完成记录里列出。
- 不顺手重构、不升级无关依赖、不改别的卡片负责的接口结构。
- 接口的请求和返回结构以“接口契约”卡（P1-03、P2-01）定义的为准。实现时发现契约有问题，按第 2 节处理，不要直接改。

## 4. 代码约定

### 4.1 目录（技术方案第 5 节）

```
backend/            主服务（FastAPI）
  app/main.py       创建应用、注册路由
  app/cli.py        运维命令
  app/core/         配置、数据库、Redis、错误码、日志、中间件、安全工具
  app/<模块>/       auth iam resources settings audit models gateway usage（后续期加 kb apps chat）
  migrations/       Alembic
  tests/<模块>/     与 app 下的模块对应
frontend/           React 控制台
deploy/             Compose、nginx、数据库初始化脚本、部署文档
parser/             解析服务（独立项目）
Makefile            常用命令的统一入口
```

### 4.2 后端模块内的文件（补充）

| 文件 | 放什么 |
| --- | --- |
| `router.py` | FastAPI 路由，只做参数接收、权限依赖、调用 service、写审计 |
| `schemas.py` | Pydantic 请求和返回结构 |
| `service.py` | 业务逻辑，入参是数据库会话、请求上下文和普通参数 |
| `tables.py` | SQLAlchemy ORM 表定义。**不要叫 models.py**：`app/models/` 是“模型服务”模块，避免混淆 |

模块大了可以再拆（如 `auth/tokens.py`），但不另起层次。

### 4.3 接口

- 前缀 `/api/v1`，JSON 字段用 snake_case（前端直接用生成的类型，不转驼峰）。资源名用复数；非增删改查的动作用 `资源:动作`，如 `POST /api/v1/users/{id}:disable`。
- 分页：请求 `page`（从 1 开始）、`page_size`（默认 10，最大 100）；返回 `{"items": [...], "total": n}`。
- 错误：HTTP 状态码 + `{"code": "NAME_CONFLICT", "message": "中文说明", "detail": {...}, "request_id": "..."}`。错误码只在 `backend/app/core/errors.py` 定义，抛 `AppError` 子类，不要在路由里直接返回错误 JSON。
- 时间：数据库用 `timestamptz`，接口返回带时区的 ISO 8601。
- 权限：每个控制台接口都用 `Depends(require_perm("xxx"))` 声明权限码；资源类接口另用资源权限判断（P1-12）。不依赖前端隐藏入口。

### 4.4 数据库

- SQLAlchemy 2.0 异步写法 + asyncpg；表结构变更只通过 Alembic 迁移，迁移只写 `upgrade`（只做向前迁移）。
- 主键 bigint 自增；时间 `timestamptz`；需要软删除的表用 `deleted_at`。
- 列表查询的权限条件拼进 SQL 的 WHERE，不查出来再在内存里过滤。
- 数据库有两个账号：迁移账号（表的所有者）和应用账号（只读写业务表，审计表只能 INSERT、SELECT）。代码运行时用应用账号，迁移用迁移账号。

### 4.5 安全和日志

- 密码、令牌、模型密钥、主密钥一律不进日志、不进接口返回、不进审计详情。
- 日志用 JSON 写到标准输出，带请求 ID。

### 4.6 前端

- 页面、字段、文案以 A1 原型为准（用 `proto.py` 取页面）。用 Ant Design 5 的组件实现，不照抄原型的 HTML 和 CSS。
- 接口类型只用 `pnpm gen:api` 生成的类型，不手写接口字段。
- 界面只做中文；按 1280px 以上宽度设计，不做手机适配。

## 5. 测试

- 卡片“验收标准”里列的测试必须写，而且要真的覆盖到所说的行为。
- 后端测试连真实的 PostgreSQL 和 Redis（`make dev-up` 启动），不要用 SQLite 或假 Redis 代替。外部模型、外部 HTTP 服务一律模拟（LiteLLM 的 `mock_response` 或本地假服务）。
- 不许为了让测试通过而删除、跳过或放宽别的测试。别的卡留下的测试失败时，先确认是不是自己的改动引起的；不是的话在“问题”里记下来。
- 提交前必须通过：
  - 后端：`make backend-lint backend-test`
  - 前端：`make frontend-check`（lint、类型检查、单元测试、构建）
  - 改了后端接口：`make gen-api`，生成的 `frontend/openapi.json` 和类型文件一起提交
  - 解析服务：`make parser-lint parser-test`

## 6. 提交

- 在当前开发分支上提交，**不推送、不合并、不切换到别的分支**。
- 一张卡可以有多个提交，提交信息以卡片编号开头：`P1-08: 登录、令牌与改密`。
- 不提交：`.env`、密钥和证书、`node_modules/`、构建产物、`apps/`、`repos/`、`test-results/`。

## 7. 完成记录怎么写

在卡片末尾“完成记录”一节写：

- 新建和修改的文件（按目录列）
- 验收命令的结果（贴最后几行输出）
- 和卡片不一致的地方，以及原因
- 留下的问题、建议后续处理的事项
