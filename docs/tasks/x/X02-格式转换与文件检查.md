# X02 格式转换与文件检查

状态：已验收
前置：X01
被依赖：X06、X07

## 目标

在解析服务里实现格式转换（LibreOffice + unoserver）和解析前的文件安全检查。

## 依据

- 知识库技术方案 K7、6.1（`POST /v1/convert`）、6.4（安全）、8.1 第 1 步
- 需求 4.1.3（旧格式和开放文档格式的处理）、4.1.8（预览 PDF、预览失败不影响入库）

## 要做

### 1. 转换 `app/convert.py`

- 镜像安装 LibreOffice（writer、impress、calc 组件即可）、unoserver、中文字体 Noto CJK（**必须装，否则转出的 PDF 中文缺字**，知识库技术方案 4.1）。
- 服务启动时拉起一个 unoserver 常驻进程，挂了自动重启；转换用 unoconvert 客户端连它（知识库技术方案 K7：避免每次冷启动）。同一时刻只做一个转换（用锁串行，补充：LibreOffice 单实例不适合并发），超时后重启 unoserver。
- 支持的转换：

| 源 | 目标 |
| --- | --- |
| doc、rtf、odt | docx |
| ppt、odp | pptx |
| xls、ods | xlsx |
| doc、docx、rtf、odt、ppt、pptx、odp | pdf（预览） |

- 接口 `POST /v1/convert`（同步，Bearer 认证）：请求 `source_key`、`source_ext`、`target`（docx / pptx / xlsx / pdf）、`output_key`；从对象存储读、转换、写回；返回 `{output_key, size, duration_ms}`；超时 120 秒（知识库技术方案 6.1），失败返回 422 和错误码 `CONVERT_FAILED`、中文说明。
- 预览转换失败是否影响入库由 worker 决定（第三期），本服务只如实返回结果。

### 2. 文件检查 `app/filecheck.py`

在 `runner` 下载源文件后、交给引擎之前调用（知识库技术方案 6.4）：

- 真实类型：用 `filetype` 按文件头判断，与扩展名对不上 → `FILE_TYPE_MISMATCH`。纯文本类（txt、md、csv、tsv、html、htm、shtml、mhtml、mht）没有文件头，跳过这项，改为检查能否按常见编码解码（补充）。docx、xlsx、pptx、odt、ods、odp、epub、ofd 都是 zip，文件头只能识别出 zip，再看压缩包里的标志文件（如 `[Content_Types].xml`、`mimetype`）区分（补充）。
- 压缩炸弹：zip 类文件读取目录，解压后总大小超过上限（默认 1GB，补充，环境变量可调）或文件数超过 1 万 → `ARCHIVE_TOO_LARGE`。不实际解压。
- 加密：zip 中有加密条目、PDF 加密（第一页打不开）→ `FILE_ENCRYPTED`，说明“文件已加密，请去掉密码后重新上传”。
- 检查结果的错误说明面向用户书写。

### 实现细节与遗留

- LibreOffice 的 UNO 绑定使用 Debian 系统 Python，unoserver 服务端和 Python 3.12 应用客户端分开安装；转换和重启由同一把锁串行保护。转换预算 120 秒，进程退出由后台监视线程拉起。
- 文件检查不解压归档；按目录统计 1GB 默认解压总量上限和 1 万条目上限。PDF 检查实际打开第一页；Office OLE 与 ZIP 标志用于分类及识别加密文件。
- 最后一次 `make parser-test-docker` 在 Docker 基础镜像元数据请求处停滞并取消；同一测试镜像挂载最终源码后全套测试通过。此前该 Make 目标也完成过 114 项测试。本机 Docker 注册表连接恢复后可重跑该目标确认镜像重建。
- 除 Docker 注册表元数据连接需恢复后重跑 Make 目标外，无待解决的功能问题。
