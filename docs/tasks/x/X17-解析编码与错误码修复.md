## 要做

1. **HTML、MHTML 按实际编码读取。** `docling_engine.py` 读普通 HTML 时不再固定按 UTF-8 读、遇错替换。（补充）读取顺序：BOM → `<meta charset>` / `http-equiv` 声明的编码 → 严格 UTF-8 → `builtin_text.decode_text`。安全化后的 HTML 统一写成 UTF-8，原文里的编码声明改成 `utf-8`（MHTML 拆包后同样处理），避免 Docling 按旧声明再解一次。
2. **Markdown 按实际编码读取。** `markdown_doc.markdown_file_to_document` 不再交给 Docling 的 `decode_text`（只认 BOM、UTF-8、cp1252）。（补充）读取顺序：BOM → 严格 UTF-8 → `builtin_text.decode_text`，解码后的文字交给 `markdown_to_document`。
3. **文本检查不误拒正常文件。** `filecheck._check_text` 只要出现 `\t\r\n\f` 以外的控制字符就拒收，会误拒 Word 导出 txt 的 `\x0b`、DOS 文件尾的 `\x1a`、日志里的 ANSI 转义 `\x1b`。改为：解码后含 NUL（`\x00`）才判为不是文本，不再看其他控制字符的占比（2026-10-28 用户决定，见“问题”3）。
4. **Docling 按原因区分错误码。** 现在兜底的 `except Exception` 一律报 `FILE_CORRUPTED`。（补充）改为：Docling 判定输入无效或转换失败（`ConversionError`）、图片或 pptx 读不出来 → `FILE_CORRUPTED`；其他异常（模型缺失、OCR 运行时错误、代码缺陷等）→ `ENGINE_ERROR`，说明用错误码表里的通用说明，异常细节写日志。
5. **参数错误用专门的错误码。** `errors.py` 新增 `INVALID_PARAMS`，说明“解析参数不正确”（补充）。Docling 的 `scan_mode`、MinerU 的 `tier` 取值不对都返回它（MinerU 原来是 `ENGINE_ERROR`，后端会当临时错误重试）。后端假解析服务的错误码清单同步加上；后端 `TEMPORARY_PARSE_CODES` 不含它，确认不用改。

2. **2026-10-28 复审（对 7968a94）发现的问题，已在第二次实现里全部修完**（见“完成记录”）。第 1、2 条已用小脚本复现，其余来自读代码和 Docling 源码。
   1. **声明的编码比 UTF-8 先试，声明错时仍是乱码**（`builtin_text.py` 的 `read_text`）。gb18030、latin-1 这类编码几乎不会解码失败，
      实际是 UTF-8、却带着 `<meta charset="gbk">` 的网页会解成 `涓枃姝ｆ枃`（复现：`read_text('<p>中文正文</p>'.encode(), 'gbk')`）。
      现有用例 `test_utf8_html_with_wrong_declaration_still_readable` 能过只是因为样例字节数恰好让 gb18030 失败。
      建议：BOM → 严格 UTF-8 → 声明的编码 → `decode_text`；文件里声明 utf-16 但没有 BOM 的按 UTF-8 处理；补一个必然复现的用例。
   2. **MHTML 没用上新的编码识别**（`mhtml.py` 的 `extract_mhtml`）。HTML 部分仍用 `email` 的 `get_content()` 解码：
      MIME 头没有 charset 时按 ASCII 解，中文全变 `�`（已复现）；声明 gb2312、实际含 GBK 才有的字（如“堃”）也变 `�`。
      建议：改为 `read_text(part.get_payload(decode=True), part.get_content_charset() 或 meta 里的 charset)`，补这两种用例。
   3. **截断、过大的图片报成 `ENGINE_ERROR`**（`docling_engine.py`）。截断的 gif/bmp/tiff 在 `convert('RGB')` 时抛 `OSError`，
      过大的抛 `DecompressionBombError`，都不是 `UnidentifiedImageError`，后端会按临时错误重试 3 次。与“要做”4“图片读不出来 →
      `FILE_CORRUPTED`”不符。建议：图片打开和转换这一段单独 try，`OSError`、`DecompressionBombError` 报 `FILE_CORRUPTED`。
   4. **“文件已损坏”的说明里带 Docling 原始英文报错和临时文件名**（`docling_engine.py`，`f"Docling 解析失败：{exc}"`，改动前就有）。
      与“异常细节写日志”不一致。建议：说明用中文固定文案，细节写日志。
   5. **三套编码判断顺序不一致**（`filecheck._check_text`：utf-8、gb18030、自动识别；`decode_text`：自动识别、gb18030、utf-8；
      `read_text`：BOM、声明、utf-8、`decode_text`）。检查时判定“是文本”的编码，可能不是解析时实际用的编码。
      建议：`_check_text` 改为调用 `read_text`（txt、csv 等没有声明，传 None），对其结果做 `_looks_like_text`；和第 1 条一起改。
   6. （较小）**按异常类型分类还不够准。** Docling 管线内的错误一律包成 `RuntimeError("Pipeline … failed")`，格式有问题的文件也会报
      `ENGINE_ERROR` 被重试；反过来 `ConversionError("No pipeline could be initialized …")` 是配置问题却报 `FILE_CORRUPTED`。
      建议：看 `exc.__cause__`（如 `PdfiumError`、`UnidentifiedImageError`、`BadZipFile`）细分；分不清的维持现状。
   7. （较小）**gb2312/gbk 的别名没升级到 gb18030**：`euc-cn`、`x-gbk`、`csgb2312` 等直接查 `_SUPERSETS` 查不到。
      建议：先 `codecs.lookup(declared).name` 规范化再查表（`LookupError` 时当作没有声明）。
   8. （较小）**读 pptx 页数的 `except Exception` 太宽**：内存不足、依赖出错也会报“PPT 文件无法读取”。
      建议：只捕获 `BadZipFile`、`KeyError`、`PackageNotFoundError`、lxml 的 `XMLSyntaxError`，其余交给外层按 `ENGINE_ERROR`。
3. **文本检查的阈值（已定：B）。** 第一次实现先按 5% 写，测试时短文本（15 个字符里 1 个 `\x1a`）被误拒，实现者自行改成了 30%
   并改了“要做”，违反了“只改状态、问题、完成记录”的约定，现已把“要做”3 改回“待定”。复审另指出：随机二进制里控制字符约占 12%，
   30% 基本不会触发，实际只靠 NUL 拦截。可选：A. 保持 30%（主要靠 NUL）；B. 只看 NUL，去掉占比；C. 5%，但字符数少于某个值的文件
   不看占比。**2026-10-28 用户选 B：只看 NUL，去掉占比判断**（NUL 足够可靠；没有 NUL 的二进制极少，漏过也只是入库一段乱码）。
   已按 B 实现（第二次实现）：删掉 `filecheck.py` 的 `_MAX_CONTROL_RATIO` 和占比计算，`_looks_like_text` 只判断是否含 NUL；
   `test_text_check_rejects_mostly_control_chars` 改为断言“控制字符多但没有 NUL 的文件通过”，`bytes(range(256))`、含 NUL 的用例仍被拒。
