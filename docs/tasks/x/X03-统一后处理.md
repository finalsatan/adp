# X03 统一后处理：预处理、图片、导出

状态：已验收
前置：X01
被依赖：X04–X08

## 目标

实现所有引擎共用的后处理：在 DoclingDocument 上执行预处理规则、抽取图片、导出 JSON 和 Markdown。各引擎只负责产出 DoclingDocument，其余由这里统一做。

## 依据

- 知识库技术方案 K1、6.2 末尾的“预处理”“图片”两条、7（统一的解析结果）、11.1（存储路径）
- 需求 4.1.4 的“预处理规则”“图片”两条
- ADR 0005

## 要做

`app/postprocess.py`，接 X01 的占位函数：

### 1. 预处理（每项一个开关，需求 4.1.4）

- 合并多余空白（`merge_whitespace`）：对文字类元素，连续空白合并为一个，去掉首尾空白；中文之间不插空格。
- 删除页眉页脚（`remove_header_footer`）：删除引擎标为页眉、页脚的元素（DoclingDocument 的 page_header / page_footer 标签，或 furniture 内容层；pypdfium 引擎在 X05 中用重复行判断后同样打这个标签）。
- 删除链接和邮箱（`remove_links_emails`）：用正则从文字中去掉 URL 和邮箱地址。
- 预处理在引擎输出之后统一执行，不改元素的位置信息（prov）。

### 2. 图片

- 引擎抽取的图片（PictureItem 中带的图像数据）统一存成 PNG：命名 `{序号}.png`，上传到作业的 `images_prefix`。
- DoclingDocument 里图片元素改为引用图片文件（相对路径 `images/{序号}.png`），**不把 base64 图片内嵌在 doc.json 中**（补充：避免 JSON 过大）。
- 引擎识别出的图中文字作为图片的说明文字保存（知识库技术方案 6.2：分块时并入所在分块）。

### 3. 导出

- `doc.json`：DoclingDocument 的 JSON（用 docling-core 自带的序列化）。
- `doc.md`：`export_to_markdown`，图片用引用方式输出（不内嵌），表格输出为 Markdown 表格。
- 返回给 runner：页数、OCR 页数（引擎给出）、图片数。

### 4. 实用工具（供各引擎使用）

- `new_document(name)`、往文档里加标题（带级别）、段落、表格（带表头和合并单元格）、图片、页面的辅助函数，统一设置 `prov`（页码从 1 开始；坐标用 PDF 坐标系，单位点，原点在左下，知识库技术方案 7）。
- 这些函数先查清锁定版本 docling-core 的 API 再写，在完成记录里写明版本和主要用到的 API。

### 和卡片不一致 / 补充实现细节

- **图片不内嵌 base64**：先自己把 PictureItem 的图像存成 `{序号}.png` 并上传 `images_prefix`，再把图片元素改成 `ImageRef(uri=Path("images/{序号}.png"))`，最后用 `image_mode=PLACEHOLDER` 写 `doc.json`（不会重新内嵌图片）。Markdown 用 `image_mode=REFERENCED`，输出 `![Image](images/1.png)`。没有用 `save_as_json(REFERENCED)`：它会把图片另存成 `image_000000_<hash>.png`，与卡片要求的 `{序号}.png` 不一致。
- **合并空白的中文处理**：“中文之间不插空格”实现为——连续空白先合并成一个空格，但两侧都是中日韩字符时整段空白直接去掉（如“中文\n之间”→“中文之间”，“第一段   文字”→“第一段文字”）。卡片没有举例，按这个读法实现。
- **预处理顺序**：先删链接和邮箱、再合并空白（去掉删除后留下的多余空格），最后删页眉页脚。卡片只列了三项规则，未规定顺序。
- **页眉页脚删除**：`DoclingDocument.delete_items` 只从 body 树里找元素，删不掉挂在 `furniture` 组下的页眉页脚。实现时先把这些元素临时挂到 body 下、再从 `furniture.children` 摘掉，让 `delete_items` 统一删除并重编号引用；其他元素的 `prov` 不受影响。
- **图中文字作为图片说明**：约定两种来源——引擎可直接用 `doctools.add_picture(caption=...)` 给说明；引擎把文字放在图片元素的子元素里时（Docling 全页 OCR 的做法），后处理会把这些文字子元素挂为图片的 `captions`。两种方式下说明都会并入所在分块。
- **图片数返回 runner**：`postprocess` 返回 `PostprocessResult(output, images)`，runner 把 `images` 放进作业结果字典；平台接口契约（知识库技术方案 6.1）的结果字段里没有图片数，`JobResult` 会忽略这个多余字段，所以 API 响应不暴露它。
- **纯内部实现**：图片 `dpi` 沿用引擎给的，缺省 72；图片序号按实际保存的图片顺序从 1 开始。
