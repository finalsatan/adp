# X12 解析实测在镜像内运行

状态：待验收
前置：X10、X11
被依赖：人工实测 H2

## 目标

`make parser-bench-docker` 在 parser 镜像里跑 X10 的实测脚本，宿主机不用装 LibreOffice 和 Docling 模型；doc、ppt、xls 的转换也能实测，耗时和内存是 Linux 容器里的数字。

## 依据

- X10 卡（脚本参数与输出）、X10 完成记录（本机缺 LibreOffice，旧格式转换报 `CONVERT_FAILED`）
- X02 卡（镜像内的 LibreOffice、unoserver）
- 决定（2026-10-27 用户确认）：实测改为在镜像内运行。

## 要做

1. 根目录 Makefile 加 `parser-bench-docker`：用 `adp-parser:test` 镜像（`--target test`，和 `parser-test-docker` 同一个镜像），把 `parser/bench` 和输入、输出目录挂进容器运行 `bench/run.py`。参数通过环境变量传：`PARSER_BENCH_INPUT`（宿主机输入目录，只读挂载）、`PARSER_BENCH_OUT`（宿主机输出目录）、`PARSER_BENCH_ENGINES`、`PARSER_BENCH_REPEAT`。输出文件属主是宿主机当前用户能读写的（必要时 `--user`）。
2. 只选本地引擎时用 `--network none`；选了 `mineru-*` 时允许容器访问宿主机上的 mineru 服务（Docker Desktop 用 `host.docker.internal`，Linux 用 `--add-host host.docker.internal:host-gateway`），`MINERU_URL`、`MINERU_API_KEY` 可通过环境变量覆盖，默认对应 `parser/compose.dev.yml` 的 mineru 服务。
3. 容器内的内存峰值仍按 X10 的方式（`RUSAGE_CHILDREN`）记录；在 `parser/bench/README.md` 写明镜像内运行的用法，以及“宿主机运行”和“镜像内运行”的区别。
4. 只在镜像内跑不通时才改 `run.py`（例如路径、转换器启动），改动最小。

### 改动

- 根目录 `Makefile`：新增 `parser-bench-docker` 和它用到的变量（`PARSER_BENCH_IMAGE`、`PARSER_BENCH_INPUT`、`PARSER_BENCH_OUT`、`PARSER_BENCH_ENGINES`、`PARSER_BENCH_REPEAT`、`MINERU_URL`、`MINERU_API_KEY`）。
  - 输入目录只读挂到 `/bench/input`，输出目录挂到 `/bench/out`，`parser/bench` 只读挂到 `/app/bench`，容器里跑 `python bench/run.py`（镜像的 `WORKDIR` 是 `/app`，`run.py` 自己把 `/app` 插进 `sys.path`，不用额外设 `PYTHONPATH`）。
  - 容器用 `--user "$$(id -u):$$(id -g)" -e HOME=/tmp` 运行：`--user` 让输出文件在 Linux 上归宿主用户（macOS 的 Docker Desktop 本来就会映射成宿主用户）；`HOME=/tmp` 是因为这个 uid 在镜像里没有 home，避免库写缓存时找不到可写目录（旧格式转换用的是 `Converter` 自己建的 `--user-installation` 临时 profile，不依赖 `HOME`）。
  - 引擎列表里出现 `mineru-` 时改用默认网络，传 `MINERU_URL`、`MINERU_API_KEY`，Linux 上另加 `--add-host host.docker.internal:host-gateway`；否则 `--network none`。
  - `PARSER_BENCH_INPUT`、`PARSER_BENCH_OUT` 必填（缺了给中文提示并报错），没给输出目录默认值：默认到仓库里容易误提交。
- `parser/bench/README.md`：拆成「在宿主机跑」和「在 parser 镜像里跑」两节，写了全部环境变量、断网/联网规则、镜像内跑的命令，并加了一张两种跑法的区别表（前置环境、旧格式转换、耗时和内存是哪台机器的数字、MinerU 地址、网络）。另补了一句内存峰值的口径（`RUSAGE_CHILDREN` 是「一个解析进程」的上限，含启动和预热）。
- `parser/bench/run.py`：**未改**，镜像内直接跑通（第 4 条不需要）。

### 验收命令结果

样例：用 `/tmp/x12-make-samples.py`（临时脚本，未提交）现场生成到 `/tmp/adp-x12-validation`，共 16 个文件：X04 的 `semicolon.csv`、`table.xlsx`；X05 的 `multipage.pdf`；X06 的 `text.pdf`、`scan.pdf`、`sample.webp`、`headings.docx`、`table.pptx`；X07 的 `office.docx`、`office.pptx`；X08 的 `mineru-sample.pdf/docx/pptx`；仓库里的 `sample.doc`、`sample.ppt`、`sample.xls`。

- 全引擎两轮（镜像 `adp-parser:test`，即 X11 构建的同一个镜像）：
  - `make parser-bench-docker PARSER_BENCH_INPUT=/tmp/adp-x12-validation PARSER_BENCH_OUT=/tmp/adp-x12-a PARSER_BENCH_ENGINES=docling,docling-force,pypdfium,markitdown,mineru-flash,mineru-basic,builtin PARSER_BENCH_REPEAT=1`（输出目录换成 `/tmp/adp-x12-b` 再跑一次）。
  - 两次都是 `results.csv`、`report.html`、`documents/` 生成成功，各 112 个组合（16 文件 × 7 引擎），`成功 67、不支持 45`；不支持的组合如实记 `UNSUPPORTED_TYPE`，脚本没有中断。
  - 两轮逐项比较状态、错误码、页数、OCR 页数、各级标题数、表格数、图片数、文字字数：`组合数 112 / 112`，`结构差异: 0`。
  - 旧格式（都在容器里真转换成功，`conversion_s` 有值）：`sample.doc` → docling、markitdown 成功（`conversion_s=5.426`）；`sample.ppt` → docling、markitdown 成功（`conversion_s=5.281`）；`sample.xls` → builtin 成功（`conversion_s=5.329`）。X10 在宿主机上的 `CONVERT_FAILED` 问题在镜像内不再出现。
  - MinerU 两档共 26 个成功组合，走 `host.docker.internal:59003` 连上已在运行的 `adp-parser-mineru`（`adp-mineru:4.0.12`）。
  - 本地引擎峰值内存（`RUSAGE_CHILDREN`，累积口径，含前面跑过的子进程）：docling 1034～1515 MB，docling-force 最高 2069 MB，markitdown/pypdfium/builtin 约 1034 MB。
- 只选本地引擎的断网运行（实际执行的命令，日志里 `set -x` 打印）：

### 备注

- 容器内输出的文件属主是宿主机当前用户（`ls -ln` 显示 `501`），可以直接删改。
- 运行前的 `docker stats --no-stream`：mineru 约 1.9 GB、postgres 约 268 MB、rustfs 约 182 MB、redis 约 8.6 MB（共约 2.4 GB / 7.75 GB）；没有重建或删除任何镜像和容器。
- 本地引擎的峰值内存是 `RUSAGE_CHILDREN` 的累积最大值，同一个 bench 进程里前面跑过的引擎会抬高后面的读数，所以 README 里已注明它是「一个解析进程」的上限、不是增量；需要单个引擎的准确数字时用 `--engines` 只选一个引擎。
