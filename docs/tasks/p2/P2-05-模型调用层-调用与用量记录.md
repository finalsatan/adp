### 2. 调用入口 `app/gateway/service.py`

```python
@dataclass
class CallMeta:
    source: str           # UsageSource
    source_id: int | None
    user_id: int | None   # 发起人
    org_id: int | None    # 发起人当时所属组织（快照）

async def chat_stream(meta, model_id, messages, params) -> AsyncIterator[ChatChunk]   # ChatChunk: text / reasoning / usage
async def chat(meta, model_id, messages, params) -> ChatResult                          # 非流式，第四期意图识别、改写用
async def embed(meta, model_id, texts) -> EmbedResult
async def rerank(meta, model_id, query, documents, top_n) -> RerankResult
```

每次调用按顺序（技术方案 9.3）：

1. 读模型：不存在、已删除或已停用 → `MODEL_UNAVAILABLE`；类型不对（如对向量化模型调 chat）→ `MODEL_TYPE_MISMATCH`。模型不按组织隔离，不检查发起人权限。
2. `check_model_host(api_base, 白名单)`（技术方案 9.1：每次调用前都校验）。
3. 限流：`limiter.acquire(model, ingest=(meta.source == "ingest"))`；在线调用超限 → `MODEL_RATE_LIMITED`；入库超限时把 `RateLimited` 原样抛出，由第三期的任务处理。
4. 解密密钥，调用 `litellm.acompletion` / `aembedding` / `arerank`，传 `model=litellm_model`、`api_base`、`api_key`；**不用** LiteLLM 的 `num_retries`。
5. 记用量（见第 5 步）。

### 3. 超时与重试

- 两段超时：等第一个片段（非流式时等整个响应）用 `first_token_timeout_s`；整次调用（含全部重试）用 `total_timeout_s`。
- 只在**还没收到任何片段**时重试，最多 `max_retries` 次；每次重试前检查剩余时间，不够一次首字超时就不再重试，直接报错（技术方案 9.3）。
- 可重试的错误：超时、连接失败、供应商 5xx、供应商 429（补充）。不重试：密钥无效、模型不存在、请求参数错误、上下文超长。
- 已经输出了片段之后出错：不重试，直接以错误结束。
- LiteLLM 的异常映射成 P2-01 的调用错误代码（`UPSTREAM_AUTH`、`UPSTREAM_NOT_FOUND`、`CONTEXT_TOO_LONG` 等），并给出中文说明（如“密钥无效”“模型不存在”“连接超时”）。映射表集中写在 `app/gateway/errors.py`。
- 最终失败时抛 `ModelCallError(error_code, message)`；调用方（接口）把它转成 `MODEL_CALL_FAILED` 或 SSE 的 `RUN_ERROR`。

### 4. 流式细节

- 流式时传 `stream_options={"include_usage": True}`，从最后的用量片段取 token 数。
- 深度思考内容：LiteLLM 在 delta 中提供的思考字段（按锁定版本确认字段名，常见为 `reasoning_content`）产出为 reasoning 片段。
- 参数 `thinking`（开关）：各供应商的开关方式不同，按锁定版本 LiteLLM 文档的统一参数传；做不到统一的，在 `app/gateway/thinking.py` 里按供应商前缀映射。至少覆盖 `dashscope/`、`deepseek/`、`openai/` 三家，在完成记录写明每家的做法（补充）。模型 `cap_thinking` 为假时忽略该参数。
- 默认参数：调用时用 `default_params` 打底，再用请求参数覆盖。

### 5. 用量记录

- 每次调用结束（成功、失败、取消）写一条 model_usage：`model_id`、`model_name`（快照）、`user_id`、`org_id`、`source`、`source_id`、`input_tokens`、`output_tokens`、`first_token_ms`、`total_ms`、`ok`、`error_code`。一次调用内的重试只记一条（补充）。
- 用**独立的数据库会话**写（不受调用方事务影响），写入代码放在 `finally` 里并用 `asyncio.shield` 保护，取消时也能写完。写入失败只记 ERROR 日志。
- 取消（调用方任务被取消，如浏览器断开）：取消向上游的请求、释放租约（P2-04）、照常记一条，`ok=false`、`error_code=CANCELLED`；token 数取上游已返回的用量，没有时估算（技术方案 9.6）。
- 估算：输入按 messages 文本、输出按已产出文本，用 tiktoken `cl100k_base` 计数。tiktoken 的编码文件要能离线加载：构建镜像时预先下载到 `TIKTOKEN_CACHE_DIR` 指向的目录（知识库技术方案 18），本卡在 `backend/Dockerfile` 里加上这一步，并在测试环境同样设置。

### 6. 重定向

技术方案 9.1 要求调用时不跟随重定向。查清锁定版本 LiteLLM 对 openai 兼容供应商所用的 HTTP 客户端是否跟随重定向，若跟随则通过 LiteLLM 支持的方式关闭；在完成记录写明结论。

### 和卡片不一致 / 自己补充的地方

1. **服务函数签名多了两个依赖参数**。`chat_stream(sessionmaker, redis, meta, model_id, messages, params)` 等，而不是卡片写的 `chat_stream(meta, model_id, messages, params)`。原因：卡片要“每次调用写一条 model_usage，用独立的数据库会话”，需要会话工厂；限流需要 Redis。二者若用模块级全局注入，会被 `create_app` 的第二次调用（测试里 `test_readyz_redis_down` 用坏 Redis 建了一个临时 app）覆盖，导致后续调用连到坏 Redis。改成显式传参符合 `开发约定` 4.2“service 入参是数据库会话和普通参数”，也彻底避免全局状态。调用方（P2-06/P2-07 的 router）从 `request.app.state.sessionmaker` 和 `get_redis` 取即可。这是内部函数签名，不是 HTTP 接口，未改任何请求/返回结构。
2. LiteLLM 版本 **1.104.2**（PyPI 上传时间 2026-10-08，距 2026-10-24 满两周）。
3. `litellm.telemetry` 在 1.104.2 已不存在（该版本不再上报遥测），仍按卡片赋值 `litellm.telemetry = False` 作防御，属性不存在时赋值即可。
4. `thinking` 映射（`app/gateway/thinking.py`）：`dashscope/` → `extra_body={"enable_thinking": bool}`；`deepseek/` → `thinking={"type": "enabled"|"disabled"}`；`openai/` → 开启时 `reasoning_effort="medium"`，关闭时不传（OpenAI 推理模型没有真正的关闭取值，用模型默认）；其他供应商回落到 LiteLLM 统一 `thinking=bool`。`cap_thinking` 为假时忽略该参数。
5. **重定向结论**：1.104.2 的 `OpenAIChatCompletion._get_async_http_client` 用 `httpx.AsyncClient(follow_redirects=True)`，且优先返回 `litellm.aclient_session`。因此 `configure_litellm()` 设 `litellm.aclient_session = httpx.AsyncClient(follow_redirects=False)`，openai 兼容供应商不再跟随重定向。
6. 取消时的 token 估算：优先取上游已返回的用量片段，没有则输入按 messages、输出按已产出文本用 `cl100k_base` 估算（`test_cancelled...` 验证 output_tokens > 0）。
7. 一次调用内的重试只写一条用量（`_call` 的 `finally` 只执行一次）。
8. 未改任何接口，未执行 `make gen-api`（无 OpenAPI 差异）。
9. 按指令未构建镜像，`Dockerfile` 的 tiktoken 预下载步骤只做了静态检查，未实际 `docker build` 验证。
10. 测试首次运行需要联网下载 tiktoken 编码文件到 `TIKTOKEN_CACHE_DIR`；之后离线可用。镜像里已预下载。
